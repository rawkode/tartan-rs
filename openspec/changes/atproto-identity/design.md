# Design

## Context

See proposal.md for the motivation. Facts about the current code and tools that shape the approach:

- **Gateway authentication.** `crates/tartan/src/gateway.rs` puts every `/-/api` route behind `require_admin`, which compares a bearer token with `TARTAN_ADMIN_TOKEN` in constant time. `extension_routes.rs` hard-codes `const VIEWER: &str = "admin"` for `tool`, `render` and `act` calls. The WIT `actor` record (`kind: user|agent|ext|system`, `id`, `on-behalf-of`) can already describe a person or an agent acting for one, so the extension ABI does not change.
- **Actors.** Each Rivet actor has its own SQLite database, set up with `CREATE TABLE IF NOT EXISTS` (`apply_schema`). Events are appended with `event_log::append` in the same transaction as the change. Process-wide dependencies live in `Services` (a `OnceLock`).
- **Git host.** walgit hosts Git. Every push is made with one static token (principal `tartan`), so the forge cannot tell who pushed. walgit's ref events carry only `old` and `new`. walgit has no API that returns raw objects and no pre-receive hook, so the forge cannot refuse a push.
- **Deployment configuration.** `crates/tartan-config/src/deployment.rs` parses package `forge` and refuses any key other than `modules` and `sources`.
- **The forge is private today.** `require_admin` is a `route_layer` over every `/-/api` route, `GET` included (`crates/tartan/src/gateway.rs`), so nobody without the admin token can read anything. An upgrade must not silently open a forge to every ATProto account.
- **No command-line interface.** The workspace builds one binary, `tartan` (`crates/tartan/src/main.rs`), which takes no subcommands. There is no `tt` crate or binary.
- **Types.** `tartan.rawkode.academy/types@v0.1.0` defines `#Person` as a free-form principal id. Issues and Kanban mirror that regex. The web UI keeps an admin token in `localStorage`.
- **Tests.** One Forge and one gateway run per test process. `scripts/e2e.sh` never touches the public network.
- **Git's signing program interface** (`gpg-interface.c` in git): with `gpg.format=x509`, Git runs `gpg.x509.program` (default `gpgsm`) as a child process without a shell. To sign it runs `<program> --status-fd=2 -bsau <key>` (`sign_buffer_gpg`), which is the same argv for `openpgp` and `x509`, so a signing program cannot tell the two formats apart from its arguments; `--keyid-format=long` appears only when verifying OpenPGP (`openpgp_verify_args`: `<program> --keyid-format=long --status-fd=1 --verify <file> -`). Git picks the verifying program from the signature's armour (`get_format_by_sig`), never from `gpg.format`. It writes the payload to standard input, takes the signature from standard output, and fails unless standard error holds `[GNUPG:] SIG_CREATED `: from Git 2.40 at the start of the buffer or of a line, but before 2.40 only after a newline (`strstr(…, "\n[GNUPG:] SIG_CREATED ")` in v2.19 to v2.39), so it can never be the first line there. `<key>` is `user.signingKey`, or the committer identity when that is unset. Before 2.40 Git captures the program's standard error as status and discards it, printing only "gpg failed to sign the data"; from 2.40 it prints that standard error after the message (`gpg failed to sign the data:\n%s`). Git's own trust gates, `git merge --verify-signatures` and `git pull --verify-signatures`, refuse a signature whose `TRUST_*` level is below `MARGINAL` unless `gpg.minTrustLevel` is set (`builtin/merge.c` `check_trust_level`, `commit.c` `verify_merge_signature`). To verify it writes the signature to a temporary file and runs `<program> --status-fd=1 --verify <file> -` with the payload on standard input; it requires `\n[GNUPG:] GOODSIG ` (so not on the first line) or `EXPKEYSIG` on standard output, parses `GOODSIG`/`BADSIG`/`ERRSIG`, `VALIDSIG` and `TRUST_*` lines, and treats a signature as X.509 only when it starts with `-----BEGIN SIGNED MESSAGE-----`. Sigstore's gitsign uses this interface (it emits `BEGIN_SIGNING` before `SIG_CREATED`, and `NEWSIG` before `GOODSIG` and `TRUST_FULLY`).

## Goals / Non-Goals

**Goals:**
- Trust a DID only on cryptographic evidence: a replayed did:plc log, or a did:web document fetched over TLS. Never trust a PDS's or the directory's word alone.
- Make a signature an act of the DID itself: a record in the signer's own ATProto repository, signed by the repository's `#atproto` key, with no other key for the person to manage.
- Make every verification result reproducible offline from what the forge stored at push time.
- Keep secrets to a minimum: the forge keeps no OAuth tokens and only hashes of session and token secrets; `tt` keeps only a narrowly scoped OAuth session.
- Exercise the real code paths in development and tests, with only URLs changed and nothing on the public network.

**Non-Goals:**
- Org and repository membership or per-repository roles. Until a later change adds membership, a non-owner can read only when the deployment configuration's `readers` lets them (D13), and can never write.
- Per-person Git push credentials or refusing pushes. walgit has no hook for either. Pushes stay unattributed, and signatures provide the attribution.
- Verifying SSH, OpenPGP or X.509 (CMS) signatures, user-managed signing keys of any kind, and `mergetag` verification. Such signatures are shown as `unsupported_format`.
- Generic OIDC sign-in, and email addresses or email verification.
- The forge writing records into people's repositories. Only `tt`, acting for the person, writes `academy.rawkode.tartan.signature` records.

## Decisions

### D1. Sign-in is login-only ATProto OAuth, with a confidential client and no stored tokens

The forge acts as a backend-for-frontend client for the web UI. (The `tt` CLI is a separate, public OAuth client whose metadata the forge also publishes; see D7, *tt's OAuth client*.)

**Client metadata** is served at `<TARTAN_PUBLIC_URL>/-/auth/client-metadata.json`:

```json
{
  "client_id": "https://forge.example/-/auth/client-metadata.json",
  "client_name": "Tartan (forge.example)",
  "client_uri": "https://forge.example",
  "application_type": "web",
  "redirect_uris": ["https://forge.example/-/auth/callback"],
  "response_types": ["code"],
  "grant_types": ["authorization_code"],
  "scope": "atproto",
  "token_endpoint_auth_method": "private_key_jwt",
  "token_endpoint_auth_signing_alg": "ES256",
  "jwks_uri": "https://forge.example/-/auth/jwks.json",
  "dpop_bound_access_tokens": true
}
```

**Scope.** The web client declares and requests exactly `atproto`. Sign-in only proves the DID; the forge never writes to a person's repository, so it asks for no `repo:` permission. Authorization servers compare requested scope tokens literally with the declared `scope` (the reference implementation, `@atproto/oauth-provider` `client.ts` `validateRequest`, splits the declared `scope` on spaces and refuses any requested token not in it with `invalid_scope`), so declaring exactly what is requested also keeps older servers that do not know granular scopes from refusing the client.

**Reachability.** The person's authorization server fetches the `client_id` URL and `jwks_uri` itself, over public HTTPS. A forge whose `TARTAN_PUBLIC_URL` is not reachable from the internet cannot offer ATProto sign-in, and `tt` cannot use its CLI client metadata (D7); it is administered with operator-minted tokens (`tt admin token create`).

**`TARTAN_PUBLIC_URL` is the browser-facing origin.** It is the origin that serves the web UI and forwards `/-/` (and so `/-/auth/*`) and `/v2/` to the gateway, not the gateway's listen address. The gateway serves no UI: the web UI is a static site, or the Astro dev server, behind a proxy (`web/astro.config.ts`, `docs/src/content/docs/web.mdx`). The `client_id`, the redirect URI, the `return_to` target and the CSRF `Origin` check (D4) all use this one origin, so production must serve the UI and `/-/` from it. In development it is the Astro origin (`http://127.0.0.1:4321`). Tests and the e2e harness that run no web server use the gateway's origin.

**Validation.** In production, `TARTAN_PUBLIC_URL` must be `https`. The ATProto profile requires an `https` `client_id` without a port; the client_id URL itself has a path. Requiring `TARTAN_PUBLIC_URL` to have no path is Tartan's own choice, so the `__Host-` cookies with `Path=/` work. Under dev-identity it may be `http` with a port, and its host must be `127.0.0.1`, not `localhost`: jacquard-oauth treats an `http://localhost` client_id as a public loopback client, which would skip the confidential `private_key_jwt` path. The development sign-in clients (*Development sign-in clients* below) require exactly `http://127.0.0.1:<port>`.

**Browser binding.** Every pending sign-in is bound to the browser that started it (RFC 9700 §4.7.1); the `state` alone is not enough, because the forge holds the PKCE verifier server-side. `POST /-/auth/login` sets a pre-auth cookie `__Host-tartan_oauth` (`tartan_oauth` under dev-identity over HTTP): HttpOnly, Secure (not in dev over HTTP), SameSite=Lax, Path=/, Max-Age 600. Its value is 32 random bytes in base64url, and the pending row stores its SHA-256 in `browser_sha256`. SameSite=Lax still sends the cookie on the top-level GET redirect back from the authorization server.

**Flow.** The person enters a handle or DID on the sign-in page (the forge trims whitespace, strips one leading `@` or an `at://` prefix, and lowercases a handle before resolving it, so a pasted `@Alice.Example ` works), which submits it as a top-level form `POST` (so the browser follows the 303 and stores the cookie). The forge then:
1. Resolves the DID and its PDS (D9).
2. Fetches `PDS/.well-known/oauth-protected-resource`, then `AS/.well-known/oauth-authorization-server`, and checks `issuer`. Authorization server metadata without `authorization_response_iss_parameter_supported: true`, which the ATProto OAuth profile requires, is a malformed document (`server_unreachable`).
3. Sends a PAR with `login_hint` and scope `atproto` (see *jacquard integration*). The authorization server metadata's `authorization_endpoint`, `pushed_authorization_request_endpoint` and `token_endpoint` must be `https` URLs (http only under dev-identity), else the request fails with `server_unreachable` before any redirect. They need not share the issuer's origin, which the ATProto OAuth profile does not require; the PAR and token endpoints are fetched only through the fetch-safe client (D9), whose host checks apply to them, and the authorization endpoint is only a browser redirect. jacquard's `par()` generates the `state`, the PKCE verifier and a fresh DPoP key, and the PAR request already carries the client assertion and a DPoP proof made with that key, handling AS nonces, as ATProto requires DPoP from PAR onward.
4. Only after PAR succeeds, stores the pending request in the identity actor: `state`, the whole serialized `AuthRequestData` `par()` returned (PKCE verifier, DPoP private key and AS nonce, `request_uri`, scopes, token and revocation endpoints, account DID), so `ClientAuthStore::get_auth_req_info` can return it intact; issuer, expected DID, PDS, the validated `return_to` (D15; it is never taken from the callback query), `browser_sha256` and a 10-minute expiry. A PAR failure therefore stores nothing.
5. Answers 303 to `authorization_endpoint?client_id&request_uri` and sets the pre-auth cookie.

On callback, the forge:
1. Consumes the `state`, so it is single-use, whatever the outcome.
2. Requires the pre-auth cookie, and requires its SHA-256 to equal the row's `browser_sha256`. Otherwise it fails and creates no session.
3. If the callback carries `error` (for example `access_denied`) instead of `code`, it stops there and reports it (see *Failures*).
4. Requires `iss` and checks it against the issuer; a callback without `iss` fails with `wrong_issuer`.
5. Exchanges the code with DPoP (handling server nonces) and an ES256 client assertion (`iss`=`sub`=client_id, `aud`=issuer, unique `jti`).
6. Requires `sub` to be the expected DID and the granted scope to contain `atproto`. jacquard-oauth does not compare `sub` with the expected DID, so this check is ours. Because every flow starts from a DID the forge resolved itself (D9) and whose PDS named this issuer, comparing `sub` with that stored DID is ATProto's identity-authentication check; jacquard's `exchange_code` still calls `verify_issuer`, which resolves `sub` again through our `OAuthResolver`; that resolver answers it from the evidence cached for this pending request, so a second PLC fetch cannot fail a sign-in that otherwise succeeded.
7. Runs `RefreshIdentity{did}` (D10, *Account status*) synchronously, before any session exists; each of its fetches is bounded by the 10-second timeout (D9, *Fetch safety*), so the step takes at most about 20 seconds, well under rivetkit's 60-second `action_timeout` for the gateway's HTTP-dispatched call to the identity actor. A transport failure or malformed answer keeps the previous status, as D10 says. If the refreshed DID document names a PDS other than the pending row's `pds` (a migration finished within the 10-minute window), the outcome is `wrong_issuer`: the authorization server that answered no longer speaks for the DID. If the resulting status is inactive (D10), the forge creates no session, records no `person.signed_in`, and the outcome is `account_inactive`, redirected to `/#/-/sign-in?problem=account_inactive&status=<status>&outcome=<id>` with `return_to` kept. `status` is put in the URL only when it is one of the statuses D10 names, otherwise `inactive`; the PDS host goes into the outcome record (*Outcome details*), never the URL. A stored inactive status that the PDS now reports active is overwritten by this refresh, so that sign-in succeeds. Without this step the callback would set a cookie that `Authenticate` refuses on the next request, and the UI's 401 redirect would loop back to sign-in with no message. Step 7 only decides the outcome: steps 8 and 9 always run before the response is sent, whatever it decided.
8. Revokes the tokens if the server lists a `revocation_endpoint`, and drops them, whatever step 7 decided.
9. Clears the pre-auth cookie. It is cleared on every callback outcome, success or failure. A sign-in failure whose outcome has details also sets the outcome cookie here (*Outcome details*).

Steps 1 and 2 of the callback run against our pending row before any code exchange. The forge does not use jacquard's `OAuthClient::callback` at all (*jacquard integration*): it calls `jacquard_oauth::request::exchange_code` itself, after its own `state`, cookie and `iss` checks.

**Failures.** No sign-in failure answers a raw 500. Every failure answers 303 to the sign-in page with a problem code, `/#/-/sign-in?problem=<code>`, keeping the original `return_to` as a query parameter so "try again" returns the person to where they started, and the page explains it. The redirect carries only fixed-list values, the validated `return_to` and, for an outcome with details, an `outcome` id; hosts and server messages are kept server-side and shown only to the browser that ran the flow (*Outcome details*). Every query value in the fragment is percent-encoded, so `return_to=/#/acme/api/issues?x=1` travels as `return_to=%2F%23%2Facme%2Fapi%2Fissues%3Fx%3D1`:
- `handle_not_found`: the handle or DID does not resolve. No pending request is stored.
- `server_unreachable` (details: the host): the PLC directory, the person's PDS or its authorization server could not be reached: a connection, DNS, TLS or timeout failure, or a response that is not a well-formed OAuth or ATProto document. The page says the person's server could not be reached, naming the host when the outcome record is readable (otherwise "your server"), not that the handle was not found. No pending request is stored.
- `client_rejected` (details: the host, and the server's `error` and `error_description`): PAR or the token endpoint answered an OAuth error about the client or its request, such as `invalid_client`, `invalid_client_metadata`, `unauthorized_client` or `invalid_scope`. The page says the person's server refused this forge's configuration and that the forge's operator should be told, and shows the server's `error` and `error_description` from the outcome record as escaped text (at most 300 characters). The usual causes are a `TARTAN_PUBLIC_URL` the server cannot reach over public HTTPS, a mistyped `TARTAN_PUBLIC_URL`, or a stale JWKS. The pending request, if one was stored, is deleted.
- `denied` (details: the server's `error_description`): the callback carries `error` (for example `access_denied`). The pending request is consumed, and the page says sign-in was cancelled or refused, showing the `error_description` from the outcome record as plain text (escaped, at most 300 characters).
- `expired`: the `state` is unknown or past its expiry. The page says the sign-in took too long and offers to try again.
- `browser_mismatch`, `wrong_issuer`, `wrong_subject`, `missing_scope`: the request fails, and the page offers to try again.
- `account_inactive` (a known `status` in the URL; details: the PDS host): the callback's status refresh (callback step 7) found the account inactive, for example `deactivated` (a deactivated Bluesky account can still complete OAuth at its PDS, so it can reactivate or migrate) or `takendown`. No session is created. The page's words depend on the status, because only a deactivation is the account holder's to undo: `deactivated` says to reactivate the account at its PDS and sign in again; `takendown` and `suspended` say to contact the hosting provider; `deleted` says the account no longer exists; any other value says the account is not active at its PDS. The PDS host is named only from the outcome record.
- `rate_limited`: the client address hit the gateway's sign-in rate limit or its 20 pending sign-ins (D3, *Housekeeping*). The page says to try again in a few minutes. No pending request is stored.
- `busy`: the forge-wide cap of 10,000 pending sign-ins is reached. The page says the forge is busy and to try again shortly. No pending request is stored.

Because `POST /-/auth/login` is a top-level form POST, these limits answer with the 303 above, never a bare 429 or 503 that the browser would show as an unexplained error page. The 303 also carries `Retry-After`, for non-browser callers.

A panic inside jacquard on hostile input (D2, *panic paths*) becomes `server_unreachable`, not a dropped connection.

**Outcome details.** The web UI is a static, hash-routed page (D15), so anything it reads from a redirect URL may have been written by whoever made the link. Escaping stops script injection, not spoofed text such as "reactivate your account at bsky-recovery.evil.example". Problem redirects therefore carry only fixed-list values: the `problem` code, a `status` from D10's list for `account_inactive`, an `outcome` id, and the validated `return_to`. They never carry a host, a server's `error` or `error_description`, or a PDS message. Those details go into a row of the identity actor's `auth_outcomes` table (D3), which only the browser that ran the flow can read:
- The id is 16 random bytes in base64url. The row holds the code, the details as JSON (each text at most 300 characters, a host at most 253), the client address and a 10-minute expiry.
- The row is bound to a fresh outcome cookie, `__Host-tartan_outcome` (`tartan_outcome` under dev-identity over HTTP): HttpOnly, Secure (not in dev over HTTP), SameSite=Lax, Path=/, Max-Age 600, holding 32 random bytes whose SHA-256 the row stores. It is set on the same 303 that carries the code, from `POST /-/auth/login` or from the callback. The pre-auth cookie cannot serve, because callback step 9 clears it.
- The page reads the details with `POST /-/auth/outcome {id, code}`, which passes the `Origin` check of D4. It answers them only when the row exists, has not expired, has that code, and the outcome cookie's hash matches. It deletes the row on that read and clears the outcome cookie. Otherwise it answers 404, and the page shows the generic message for the code, with no host or server text.
- It is a `POST` because the read consumes the row, and because browsers send `Origin` on a same-origin `fetch` only for methods other than `GET` and `HEAD` (Fetch standard, *append a request `Origin` header*), so an `Origin` check on a `GET` would refuse the forge's own page.
- Binding matters even for genuine ids: an attacker can run a real flow against their own PDS or authorization server and get back any `error_description` they choose, but the row that holds it answers only the attacker's own cookie.
- Rows are capped at 20 per client address and 10,000 in all; beyond a cap the oldest row is dropped, which only loses its details. They are deleted on read, on expiry and by the `Sweep`, are secret-free bookkeeping, and record no events.

So a crafted link such as `/#/-/sign-in?problem=account_inactive&status=deactivated&host=evil.example&error_description=…` shows the fixed text for a deactivated account and nothing from `host` or `error_description`.

**jacquard integration.** The callback calls `jacquard_oauth::request::exchange_code` directly with the pending request's PKCE verifier and DPoP key, then `request::revoke`, rather than `OAuthClient::callback`. `callback()` would call `ClientAuthStore::upsert_session` and, in `callback_core`, `Scopes::new(scope).expect(…)` on the token response's `scope`, a panic on hostile input; calling the request functions directly needs no `ClientAuthStore` at all, keeps the token set in one stack frame (never in SQLite or any store), and lets the forge read the granted scope itself (split on spaces, `missing_scope` without `atproto`). The pending request lives in the identity actor (`BeginAuth`/`CompleteAuth`, D3). The resolver passed to `exchange_code` delegates to the verifying resolver except `verify_issuer`, which answers from the pending row: it accepts only the row's DID and issuer and returns the row's PDS, so the exchange's second resolution of `sub` needs no network. We implement jacquard's `HttpClient`, `IdentityResolver` and `OAuthResolver` traits on `tartan-atproto`'s verifying resolver (D9) and fetch-safe client (D9, *Fetch safety*), so `exchange_code` → `verify_issuer` never trusts the PLC directory and every PAR, token and revocation request goes through the fetch-safe client. If a jacquard entry point cannot take an injected client, we wrap or replace that call rather than let it build its own. The forge does not use `OAuthClient::start_auth`: it builds the `OAuthMetadata` itself (its fields are public), with `server_metadata` from its own resolution (D9 and step 2), and calls `jacquard_oauth::request::par` directly, so it controls when the pending row is stored (after PAR) and which resolver answers.

**Why.** Sign-in only has to prove the DID. Without refresh tokens there is:
- no long-lived bearer secret to encrypt;
- no single-use refresh lock;
- no 180-day refresh horizon;
- no coupling between client-key rotation and live sessions. Rotating a key just means listing the new key first.

**Alternatives.**
- *Keep OAuth sessions with refresh*: rejected. They are needed only for ongoing PDS writes, which the forge does not make; `tt` makes the only writes, with its own session (D7).
- *Public client*: rejected. Sessions would be limited to 2 weeks, there would be no client authentication, and its AS-side trust is weaker.
- *Generic OIDC*: rejected per the defaults. It also does not give a DID.
- *The localhost client_id as the forge's client*: rejected. It is public-only and optional per AS, so it would not exercise the confidential path. tartan-devnet (D12) exercises the confidential path instead; the localhost client is kept only as a development switch (below).

**Development sign-in clients.** A forge on a developer's machine at `http://127.0.0.1:<port>` cannot be reached by real authorization servers, so the confidential client cannot sign in against a real PDS from there. Two switches, compiled only into `dev-identity` builds (a release build refuses to start with either variable set, naming it) and never on by default, replace the confidential client; both require `TARTAN_PUBLIC_URL=http://127.0.0.1:<port>`, need no `TARTAN_OAUTH_KEYS_FILE`, and are independent of `TARTAN_DEV_IDENTITY` (without it they use `plc.directory`, DNS and the production fetch rules, so a developer can sign in as their real DID):
- `TARTAN_DEV_LOCALHOST_CLIENT=1`: ATProto's `http://localhost` client, client id `http://localhost?redirect_uri=<TARTAN_PUBLIC_URL>/-/auth/callback&scope=atproto`, a public client (`token_endpoint_auth_method` `none`) the authorization server derives from the client id. Checked against the real network: bsky.social accepts its PAR (`a_real_authorization_server_accepts_the_localhost_client`, an ignored test in `crates/tartan/src/auth.rs`). The PDS behind `did:web:rawkode.dev` (not the reference implementation) refuses it at PAR with `invalid_client` "client_id must be a safe https metadata URL", although resolving that DID, its PDS and its authorization server all succeed.
- `TARTAN_DEV_CLIENT_METADATA_URL=https://…`: for such servers, a public native client whose metadata document the developer hosts at that `https` URL (the client id); the forge serves the document to copy at `/-/auth/client-metadata.json` (`application_type` `native`, the loopback redirect `<TARTAN_PUBLIC_URL>/-/auth/callback`, `token_endpoint_auth_method` `none`, scope `atproto`). The devnet tests it with the gateway's own copy as the client id; no hosted document was available to test it against rawkode.dev.
Both are public clients, so sign-in has no client authentication; that is acceptable only on a developer's loopback origin. A tunnel that gives the local forge a public `https` origin is the other option: it runs the normal confidential client.

**Checked when the dependencies were added (task 1).**
- *jacquard-oauth as `tt`'s public client.* `jacquard_oauth::request::{par, exchange_code, refresh}` take an `OAuthMetadata` whose fields are public: the server metadata, an `OAuthClientMetadata` the caller builds, and `keyset: Option<Keyset>`. With `keyset: None` and `token_endpoint_auth_method: "none"`, `build_auth` sends only `client_id` (provided the authorization server lists `none`), and PAR and the code exchange use `redirect_uris[0]` as the `redirect_uri`. So `tt` builds the client metadata itself (client_id = the forge's https metadata URL, one redirect `http://127.0.0.1:<port>/callback`, `application_type` `native`), drives these three functions with `JacquardResolver<C>` over its own HTTP client (which implements `OAuthResolver` and `DpopExt`), and runs its own tokio listener; it does not call `atproto_client_metadata`, which would label an https client without a keyset `web`. A scratch crate calling all three with such a client compiles against 0.12.2. `par` also calls `Scopes::new(..).expect(..)`, on the client's own `scope`, which `tt` writes, so it cannot panic on server input.
- *jacquard-repo's cost.* On the development machine (32 threads), a clean `cargo build -p tartan-forge` took 92 s and 4.8 GiB with every new dependency, 91 s and 4.4 GiB with jacquard-repo (and so jacquard-api) left out, and 84 s and 3.7 GiB before the change: jacquard-repo adds about 2 s and 0.4 GiB, well under the 3-minute and 1 GiB limits, so the atrium-repo fallback is not needed.
- *rivetkit in `tt`.* With `tartan-identity-api` depending on the rivetkit server SDK, a clean `cargo build -p tt` took 77 s and 3.1 GiB (464 crates); without it, 20 s and 2.1 GiB (407 crates). That is heavy, so rivetkit is an optional feature of `tartan-identity-api` (D16).
- *Licences.* `cargo tree --workspace -e normal --target all` lists no git source and no GPL or LGPL-only crate (r-efi is `MIT OR Apache-2.0 OR LGPL-2.1-or-later`; cuengine is AGPL like the forge). The MPL-2.0 crates are the seven jacquard crates. keyring brings keyring-core, apple-native-keyring-store, windows-native-keyring-store, zbus-secret-service-keyring-store, secret-service and zbus, all MIT or MIT OR Apache-2.0, and no libdbus binding. The repository has no closed licence allowlist (no `deny.toml`), so none was changed.

**Licences.**
- MPL-2.0 is file-level copyleft and explicitly compatible with (A)GPL (MPL §3.3).
- It appears only in the AGPL crates (`tartan-atproto`, `tartan`, `tt`, `tartan-devnet`). The MIT SDK and extensions never depend on it.
- We use jacquard unmodified. If we ever patch a jacquard file, that file stays MPL.

**Why jacquard.** It is the only family with confidential-client DPoP OAuth, typed granular scopes, configurable resolution and a ready record-proof verifier in one type system.

**Known gaps in jacquard, closed by our code in `tartan-atproto`:**
- Its CAR reader does not re-hash blocks. We read the CAR with `jacquard_repo::car::parse_car_bytes` and re-hash every block before calling `verify_proofs`, so no direct CAR crate is needed.
- With p256 0.13, `Commit::verify` accepts high-S. We verify the repository commit's signature with atrium-crypto first.
- `jacquard-identity` trusts the PLC directory. We verify the PLC log ourselves (D9).
- *Panic paths on untrusted input.* atrium-crypto 0.1.3 `parse_multikey` indexes `decoded[..2]` without a length check, so we check the length first. jacquard-oauth 0.12.2 `callback_core` calls `Scopes::new(scope).expect(…)` on the token response. Identity, proof and OAuth work runs in a spawned task whose `JoinError` becomes an error (`unverifiable` in actors, `server_unreachable` at sign-in), and the gateway has tower-http's `CatchPanicLayer`.

**Rejected or fallback alternatives.**
- *atrium-oauth/-identity/-repo (MIT, most used)*: our fallback if jacquard 0.12 fails our build or audit. It has no proof verifier, so we would walk the MST ourselves on atrium-repo's hash-checking CarStore (about 150 lines).
- *rsky-\**: too little adoption (tens of downloads), and rsky-pds is not on crates.io.
- *atproto-plc 0.2.0*: about 89 downloads and a year without releases. The PLC rules fit on one page and we need control over the evidence we keep, so we write the verifier.
- *sequoia-openpgp*, *ssh-key*: OpenPGP and SSH signatures are out of scope (D7, *Rejected alternatives*).
- *A keyring wrapper of our own over each platform API*: keyring 4 already splits the platform stores into separate crates, so `tt` takes only the pure-Rust ones.

### D3. A forge-singleton `identity` actor

The new actor type `identity` is keyed `[forge_id]` and logs to source `identity`. Like the Forge actor it always runs in the default pool: placements name only org and repository targets (spec: actor-placement), so it is never moved, and `Services` (owners, the object store, the fetch-safe client) is available wherever it runs. It keeps identity state out of the Forge actor's tables and serialises session, token and signature-record writes. Schema:

```sql
CREATE TABLE IF NOT EXISTS people (
  did TEXT PRIMARY KEY, handle TEXT, handle_checked_at INTEGER,
  pds TEXT, atproto_key TEXT,                -- did:key of #atproto
  status TEXT NOT NULL DEFAULT 'active',     -- 'active', or the verified account status (D10, *Account status*);
                                             -- every value but active, throttled and desynchronized is inactive
  status_checked_at INTEGER,
  known_as TEXT NOT NULL,                    -- JSON set: owner, signed_in (readers only, D13), signer, rule_signer
  first_seen_at INTEGER NOT NULL, last_signed_at INTEGER,
  last_credential_at INTEGER);               -- when the DID last held a live session or token (the 30-day sweep)
CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY,                       -- ULID, shown in the session list
  secret_sha256 BLOB NOT NULL UNIQUE, did TEXT NOT NULL,
  kind TEXT NOT NULL,                        -- 'browser' (cookie) or 'cli' (tartan_cli_ bearer, D16)
  device TEXT,                               -- user agent, or the device name tt sent
  created_at INTEGER NOT NULL, expires_at INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS tokens (
  id TEXT PRIMARY KEY, secret_sha256 BLOB NOT NULL UNIQUE, did TEXT NOT NULL,
  name TEXT NOT NULL, scopes TEXT NOT NULL, repos TEXT,   -- JSON
  created_at INTEGER NOT NULL, expires_at INTEGER NOT NULL,
  last_used_at INTEGER, revoked_at INTEGER, revoked_by TEXT);
CREATE TABLE IF NOT EXISTS oauth_requests (
  state TEXT PRIMARY KEY, did TEXT NOT NULL, issuer TEXT NOT NULL, pds TEXT NOT NULL,
  auth_request TEXT NOT NULL,                           -- serialized jacquard AuthRequestData (PKCE verifier,
                                                        -- DPoP private key and nonce); private, deleted on use or expiry
  return_to TEXT NOT NULL,
  client_ip TEXT NOT NULL,                              -- client address (D4), for the per-address cap
  browser_sha256 BLOB NOT NULL,                         -- SHA-256 of the pre-auth cookie
  created_at INTEGER NOT NULL, expires_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS auth_outcomes (                -- failure details for the browser that ran the flow (D1)
  id TEXT PRIMARY KEY,                                  -- 16 random bytes, base64url; the redirect's `outcome`
  code TEXT NOT NULL, details TEXT NOT NULL,            -- JSON: host, error, error_description, message
  browser_sha256 BLOB NOT NULL,                         -- SHA-256 of the outcome cookie
  client_ip TEXT NOT NULL,
  created_at INTEGER NOT NULL, expires_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS cli_codes (                    -- one-time codes of the tt login hand-off (D16)
  code_sha256 BLOB PRIMARY KEY, did TEXT NOT NULL,
  challenge TEXT NOT NULL,                              -- PKCE S256 challenge sent by tt
  device TEXT NOT NULL, client_ip TEXT NOT NULL,
  created_at INTEGER NOT NULL, expires_at INTEGER NOT NULL);   -- 60 seconds
CREATE TABLE IF NOT EXISTS signature_records (            -- records that verified a stored result (D7, D8)
  did TEXT NOT NULL, rkey TEXT NOT NULL, cid TEXT NOT NULL,
  rev TEXT NOT NULL,                                    -- repository revision of the proof
  first_proved_at INTEGER NOT NULL, revoked_at INTEGER, revoked_reason TEXT,  -- deleted | replaced | withdrawn
  pre_withdrawn INTEGER NOT NULL DEFAULT 0,             -- 1: inserted by a withdrawal before any proof (rev '',
                                                        -- first_proved_at the withdrawal time); never deleted
  PRIMARY KEY (did, rkey));
CREATE TABLE IF NOT EXISTS jetstream (id INTEGER PRIMARY KEY CHECK (id = 1), cursor_us INTEGER);
```

**Housekeeping.**
- Expired `oauth_requests`, `auth_outcomes`, `cli_codes` and sessions are deleted when the actor wakes and by its scheduled `Sweep` (below).
- The DPoP key inside `auth_request` is the only private key stored, and only for at most 10 minutes.
- At most 20 `oauth_requests` are pending per client address, and at most 10,000 in all; beyond either cap, and beyond the gateway's per-address rate limit, `POST /-/auth/login` answers 303 to `/#/-/sign-in?problem=rate_limited` (per address) or `?problem=busy` (global), keeping `return_to` and adding `Retry-After` (D1, *Failures*). `cli_codes` are capped at 20 per DID; `POST /-/auth/cli/token` is rate-limited per client address. The per-address limits are token buckets in each gateway process: `POST /-/auth/login` 30 at once then one every 6 s, `POST /-/auth/cli/token` 10 then one every 6 s, `POST /-/api/people/resolve` 30 then one every 2 s, and `GET /-/api/people` lookups of uncached DIDs 200 then one every 0.5 s (over that limit such a DID is answered `null` without a lookup).
- The gateway also rate-limits `POST /-/auth/login`, `POST /-/api/people/resolve` and `GET /-/api/people` lookups of DIDs not yet cached, per client address (D4, *Client address*). The identity actor makes at most 50 new DIDs known as `signer` per push (the push path counts them, `tartan_identity_api::MAX_NEW_SIGNERS_PER_PUSH`) and 5,000 forge-wide (`KnowDid` refuses beyond it); a signer beyond the cap still verifies, but is not watched (D7, *Watching records*). The `Sweep` drops from `known_as` a DID known only as `signer` that has not verified a signature within 30 days (`last_signed_at`, else `first_seen_at`), and a non-owner DID known only as `signed_in` that has had no live session or token for 30 days (`last_credential_at`, set whenever a session or token of the DID is created, used, ended, revoked or expires, and the tokens' own expiry and revocation times).
- **Scheduled sweep.** The identity actor owns a recurring scheduled action, `Sweep`, registered on every start with Rivet's named recurring schedule `ctx.cron().every(CronEveryOptions { name: "sweep", interval: 15 min, action: "sweep", .. })` (rivetkit 3.0.6 `context.rs`; `ctx.cron().list()` lists entries). Re-registering the same name replaces the existing entry and does not count against the actor's 1000-schedule capacity, so starts never pile up duplicates, and it survives the actor sleeping. It deletes expired rows and runs `RefreshIdentity` for every DID in `known_as` whose `status_checked_at` is older than 6 hours, in batches, so account status is re-learned even with Jetstream disabled and an inactive DID becomes active again without another event. Rivet persists schedules and wakes the actor for them, so nothing depends on the actor staying awake.
- These rows are bookkeeping and secret-bearing state, and record no events (event-delivery carve-out). So are `sessions.last_used_at`, `people.handle_checked_at`, the Jetstream cursor and housekeeping deletes.

**Event source.** The identity actor owns an `Outbox` (`Outbox::new("identity")`) like the Forge and Repo actors: it has a `Flush` handler, calls `flush_later(SubscriberSource::Forge)` after each append and in `on_start`, and registering a forge subscriber also sends it `Flush`, so a new subscriber gets identity history without waiting for the next identity event. Extension installations never receive identity events, because `Outbox::reaches` requires a repository.

**Actions:**
- `SignInCapacity{client_ip}`: whether the address and the forge are under their pending caps, checked before any network work
- `BeginAuth{pending}` (stores the pending row after PAR, re-checking the caps; the `auth_request` column holds jacquard's serialized `AuthRequestData` together with the handle the person typed when it verified in both directions, which `SignedIn` records) / `CompleteAuth{state}` (deletes the row whatever happens and answers it unless it expired)
- `PutOutcome{code, details, browser_sha256, client_ip}` / `TakeOutcome{id, code, browser_sha256}` (D1, *Outcome details*)
- `Authenticate{secret_sha256, kind}`: returns the principal, or nothing
- `CreateSession{did, kind, device}`, `EndSession`, `ListSessions`
- `IssueCliCode{did, challenge, device}`, `RedeemCliCode{code, verifier}` (D16)
- `CreateToken`, `RevokeToken`, `ListTokens` (the gateway's path, after it has authorized the session)
- `AdminCreateToken{did, name, scopes, repos, expires_in_days}`, `AdminListTokens{did}`, `AdminRevokeToken{did, id}`: the operator path used by `tt admin` (D16); each refuses, with an error naming the DID, any DID that is not in `Services.owners`, so the owner check is made by the forge itself, against the owner list it is running with
- `KnowDid{did, because}`
- `SignedIn{did, handle}`: called by the sign-in callback after the session is created; records `person.signed_in` and `KnowDid(did, "signed_in")` only for a DID with `read` rights (D13, *Who becomes known*), and answers whether it did
- `RefreshIdentity{did}` (no other payload; D10, *Account status*)
- `RecordSignature{did, rkey, cid, rev}`: adds a `signature_records` row if none exists (an existing row, revoked or not, is left as it is) and makes the DID known as `signer` within the caps (D8 step 6)
- `ReproveSignature{did, rkey}`: fetches and proves the record again, never from the proof-reuse cache, and marks it revoked on a proved absence or another CID only after confirming it against freshly re-resolved DID evidence; it never clears `revoked_at` (D7, *Watching records* and *Confirming before revoking*)
- `WithdrawSignature{did, rkey, cid}`: marks the record revoked (`withdrawn`) on the DID's own word, whatever `cid` says, and fetches nothing; when no row exists it inserts an already-revoked `pre_withdrawn` row within the pre-withdrawal caps (D7, *Watching records*), and a tracked row is always revoked
- `People{dids}`
- `SignerStanding{pairs: [{did, rkey}]}` (at most 1000 pairs; the caller de-duplicates pairs and splits a larger set into batches of 1000): for each pair, whether its `signature_records` row is revoked (a pair with no row yet, D8 step 6, is not) and whether the DID's status is inactive. It reads only `signature_records` and `people` and fetches nothing (D8, *Standing*)
- `GetJetstreamCursor` and `SetJetstreamCursor{cursor_us}`
- `WatchedDids`: the DIDs whose `known_as` is not empty, sorted: Jetstream's `wantedDids` and the consumer's own filter
- `SignatureRecordQuery{did, rkey}`: the tracked row of one record, if any, without fetching (the refresh route uses it to answer 404 for an untracked record and to rate-limit only untracked withdrawals and re-proofs before anything is fetched)

The pre-withdrawal caps are read from `tartan_forge::Services.identity_limits`; the `tartan` binary always installs the values above (`IdentityLimits::default()`), and tests install lower ones so a cap can be reached.
- `Sweep` (scheduled, see *Housekeeping*), and `Schedules`, which lists the actor's recurring schedules by name for operators and tests

**Alternative.** Tables in the Forge actor: rejected. Every authenticated request would contend with org and placement writes, and the event source would be mixed.

### D4. Principals and authorization in the gateway

`require_admin` becomes `authenticate`. It builds a `Principal { did, kind: User{session_kind} | Agent{token_id}, rights, repos }` and puts it into the request extensions.

**Resolution order:**
1. A bearer token: a `tartan_pat_…` access token (an agent, D5) or a `tartan_cli_…` CLI session (the person, D16).
2. Otherwise, the session cookie.
3. Otherwise, anonymous.

**Lookups.**
- The gateway hashes the secret and asks the identity actor.
- Positive and negative answers are cached per process for 30 seconds, keyed by hash. A revocation clears the local cache entry at once, and other processes catch up within 30 seconds. The same lag applies to signing out, ending a session, removing an owner and a DID becoming inactive or active again: another gateway process may answer from its cache for up to 30 seconds. `Authenticate` refuses any credential whose DID's `people.status` is not `active`, so the cache TTL bounds the lag; there is no cross-process eviction. identity.mdx states the lag.
- `last_used_at` is written at most once an hour per credential.

**Rights.**

| Caller | Rights |
| --- | --- |
| owner (browser or CLI session) | `read`, `write`, `admin` |
| reader: a non-owner the deployment configuration's `readers` admits (D13) | `read` |
| any other signed-in person | none: 403 on every `/-/api` route except `GET /-/api/me`, which answers `rights: []`, their own sessions (`/-/api/sessions`), and the `self` routes |
| token | its scopes ∩ the rights its DID has now, limited to `repos` when that is set |

`readers` defaults to `"owners"`, so a forge upgraded without setting it stays as private as the admin token kept it: only owners read. A person without rights can still sign in and sign out (`/-/auth/*` is outside `/-/api`), so the web UI can say who they are and that the forge is private (D15). Their sign-in records no `person.signed_in` and does not make their DID known (D13).

**Route classes:**
- `read`: `GET` routes, plus extension `render` calls. Because the session cookie is SameSite=Lax and so reaches top-level cross-site `GET`s, it matters that a `render` call cannot change state: the host already allows only a single `SELECT` or `WITH` query and refuses effects and calls during `render` (specs: extension-runtime, extension-calls), so `render` is no CSRF vector; writes go through `tool` and `act`, which need `write` and the `Origin` check.
- `write`: extension `tool` and `act` calls.
- `admin`: `POST /orgs`, `POST /orgs/{org}/repos`, `PUT /placements`, `PUT /subscribers/{name}`, `GET /subscribers/{name}/events` (the forge-wide event stream).
- *own sessions*: `GET /-/api/sessions`, `DELETE /-/api/sessions/{id}` and `DELETE /-/api/sessions/current`, open to any session principal (browser or CLI) whatever its rights, since they touch only the caller's own sessions; otherwise `tt logout` could not end a non-reader's CLI session. `/-/api/tokens` needs a session principal with some right (a token of a DID without rights would be inert).
- `self`: `POST /-/api/people/{did}/signatures/{rkey}/refresh`, allowed to any principal whose DID equals `{did}`, whatever its rights (readers and people with `rights: []` included), like `GET /-/api/me`. A signer must be able to reach their own records on any forge that judged their commits, and that forge's `readers` setting has nothing to do with it. Owners may also call it without a body for any DID (a re-proof). `{"withdraw": true}` is accepted only from a session principal (a browser session or a `tartan_cli_` CLI session) and answers 403 for every `tartan_pat_` token, whatever its scopes: a withdrawal is permanent and forge-wide (D7 *Watching records*, D8 *Standing*), so a leaked token, read-only CI tokens included, must not be able to void every signature its person has made. A body-less self re-proof is allowed to tokens, since it only fetches and can only confirm what the PDS proves. The class also covers the signer's own re-check, `POST …/commits/{sha}/signature/recheck` by the principal whose DID is the DID stored on that `unverifiable` result (D8, *Statuses are final*); for any other oid such a caller gets 404, so a non-reader learns nothing beyond their own signed object. The routes are non-GET, so a cookie call needs the `Origin` check (*CSRF*). A DID whose `people.status` is inactive cannot use them, because `Authenticate` refuses its sessions (D10): a taken-down account withdraws forgeries only once reactivated, which signing.mdx says.
  - *Rate limit.* Every `self` call that inserts a row or makes the forge fetch (a withdrawal of an untracked record, a body-less re-proof, a signer's re-check) is limited per principal DID to 600 an hour with bursts of 100, answering 429 with `Retry-After`, because each re-proof makes the forge fetch from a host the caller chooses (its own PDS). Withdrawing a record the forge already tracks only sets `revoked_at`, so it is never rate-limited or capped.
  - *Storage.* Self-withdrawal lets any ATProto account that can sign in insert already-revoked `pre_withdrawn` rows. These are never deleted (*Watching records*: a revoked row is never un-revoked, and deleting it would be exactly that), so storage is bounded by caps instead: at most 1,000 per DID and 100,000 forge-wide, and a DID that has no `read` right and is not in `known_as` (a stranger on a private forge) may add one only while the forge-wide count is below 50,000, so strangers cannot use up the room that readers and known signers need. Beyond a cap only new untracked inserts answer 429; 100,000 rows of under 200 bytes are about 20 MB of identity-actor SQLite.
- Outside `authenticate`: `/-/hooks/git-host` (HMAC-authenticated walgit webhooks) and the public read-only CUE registry at `/v2/`, as today (`crates/tartan/src/gateway.rs`). The middleware is layered on the `/-/api` router only, so `CUE_REGISTRY` evaluation and walgit webhooks keep working.
- **Registry responses on the forge origin.** `/v2/` is now served from `TARTAN_PUBLIC_URL`, the origin that carries the session cookie, and its manifests are mirrored from operator-listed upstream `sources`. `registry.rs` `manifest()` sets `Content-Type` from the manifest's own `mediaType`, so an upstream could serve `text/html`. The gateway therefore answers manifests only with OCI or Docker manifest media types (falling back to `application/vnd.oci.image.manifest.v1+json`), and adds `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'` to every `/v2/` and `/-/api` response.

**Repository-limited tokens.** A token with `repos` is allowed only on routes addressed to a listed repository (`/orgs/{o}/repos/{r}/…`), and for reads also on its org's routes (`GET /orgs/{o}`, the org's repository list). Every other route answers 403, including `POST /orgs`, `PUT /placements`, `/subscribers/**` (and so the forge-wide event stream), `/-/api/tokens`, `/-/api/sessions` and the signature-record refresh. The exceptions are `GET /-/api/me` and `GET /-/api/people`. `org/*` lists every repository of that org. The check is a single match on the route's `{org, repo}` path parameters, so a new forge-wide route is refused by default.

**Client address.** Rate limits and the per-address pending cap key on a client address derived as follows. The gateway is served with `into_make_service_with_connect_info::<SocketAddr>()`, so every request carries its peer address. `TARTAN_TRUSTED_PROXIES` is a comma-separated list of CIDRs, empty by default. When the peer is not in that list, the client address is the peer address and `X-Forwarded-For` is ignored. When the peer is trusted, the gateway reads every `X-Forwarded-For` header, walks the addresses from right to left, and takes the first one not in the trusted list; if all are trusted (or the header is absent or malformed), it uses the left-most valid one, or the peer. `Forwarded` is not read, so there is exactly one source. IPv6 addresses are bucketed by their /64. In development, `dev.sh` and `demo.sh` set `TARTAN_TRUSTED_PROXIES=127.0.0.1/32` and the Astro proxy sends `X-Forwarded-For` (`xfwd: true`); a production operator lists their reverse proxy's addresses.

**CSRF.** Cookie-authenticated non-GET requests (including `POST /-/auth/cli/approve`, D16), and the top-level form POST `/-/auth/login`, must carry `Origin` equal to the origin of `TARTAN_PUBLIC_URL` (the browser-facing origin, D1). A mismatch answers 403 with a plain-text body naming the expected origin, and the gateway logs a warning with the received one, so a misconfigured `TARTAN_PUBLIC_URL` or a proxy that rewrites `Origin` is easy to diagnose. With SameSite=Lax this blocks cross-site form posts; bearer credentials (`tartan_pat_` tokens and `tartan_cli_` CLI sessions) are exempt, since a browser never attaches them by itself. The Astro dev proxy rewrites only `Host` (`changeOrigin`), so the browser's `Origin` reaches the gateway unchanged and must equal `http://127.0.0.1:4321` in development.

**Extensions.** `VIEWER` goes away. `CallTool`, `Render` and `Act` take a `tartan_forge::Caller` (`{kind: user|agent|ext, id, on_behalf_of}`, the serializable form of the WIT `actor`, named so it does not clash with rivetkit's `Actor` trait) instead of a `String`, and `SlotContext.viewer` is built from it (spec: `extension-runtime`).

### D5. Access tokens

- **Format.** The secret is `tartan_pat_` followed by base64url (no padding) of 32 random bytes from the OS RNG, which is 43 characters. The prefix lets secret scanners recognise it.
- **Storage.** Only `SHA-256(secret)` is stored, together with `id` (a ULID), `did`, `name`, `scopes ⊆ {read, write, admin}`, optional `repos` (`org/repo` | `org/*`), and an expiry of 1–365 days.
- **Who creates them.** Tokens are created only from a session (the web UI, or `tt token create` with a CLI session, D16), never from another token. Operators can also run `tt admin token create`, which calls the identity actor's `AdminCreateToken` through the Rivet client (D16, *`tt admin` and the identity actor*) and prints the secret once. The identity actor refuses a DID that is not in the forge's `owners` (`Services.owners`, D13), and `tt admin` reports that refusal; `tt` never reads the deployment configuration itself.
- **Revocation.** The token's DID or any owner can revoke it.
- **Events.** `token.created` and `token.revoked` never carry the secret.

**Alternatives.**
- *JWT access tokens*: rejected. They cannot be revoked without a lookup, so they gain nothing here.
- *ATProto service auth* (`com.atproto.server.getServiceAuth` JWTs signed by the PDS): attractive for agents that already hold a PDS session. It is left for a later change because it needs a forge DID and service entry.

### D6. Sessions

- The cookie is `__Host-tartan_session`: Secure, HttpOnly, SameSite=Lax, Path=/.
- With the `dev-identity` feature over HTTP it is `tartan_session`, without Secure.
- The value is 32 random bytes in base64url, and the row stores its SHA-256.
- Sessions expire 30 days after creation (absolute) or after 7 days idle.
- The web client uses `credentials: "same-origin"` and stops sending `Authorization`. Cookies set by the gateway carry no `Domain`, so behind the proxy they belong to the `TARTAN_PUBLIC_URL` origin.
- A successful sign-in always issues a fresh session secret and ignores any session cookie the browser presented, so a cookie value fixed in advance is never adopted. If the browser presented a valid session cookie, that previous session is ended.
- **CLI sessions** (D16) are rows of the same table with `kind = 'cli'`. Their secret is `tartan_cli_` followed by 43 base64url characters (32 random bytes), sent as a bearer token, never as a cookie; they have the same expiry and rights as a browser session, and the prefix lets secret scanners recognise them.
- Signing out deletes the row. `GET /-/api/sessions` lists the person's own sessions (id, kind, created, last used, device) and `DELETE /-/api/sessions/{id}` ends one; `DELETE /-/api/sessions/current` ends the calling session, which is how `tt logout` ends its own.

### D7. A signature is a record in the signer's repository, written by `tt sign`

**The idea.** A person has exactly one key that the network already binds to their DID: the repository signing key `#atproto` in their DID document, which their PDS uses to sign every commit of their ATProto repository. Tartan signs Git objects with it, indirectly. To sign, `tt` writes a small record to the person's own repository saying "I sign the payload whose salted digest is this", and Git embeds a reference to that record (its `at://` URI and CID), plus the random salt, as the object's signature. The PDS signs the repository commit that contains the record, so anyone can prove, with `com.atproto.sync.getRecord`, that the DID's repository holds a record over exactly these bytes. Nobody generates, publishes, rotates or revokes a separate signing key.

**The lexicon.** `academy.rawkode.tartan.signature`, under the `tartan.rawkode.academy` domain that also names the CUE modules (`tartan.rawkode.academy/types`), published in this repository as `lexicons/academy/rawkode/tartan/signature.json`:

```json
{
  "lexicon": 1,
  "id": "academy.rawkode.tartan.signature",
  "defs": {
    "main": {
      "type": "record",
      "description": "The account signs the payload whose keyed digest is given, in the given namespace. The key (a random per-signature salt) travels with the signature, not in this record.",
      "key": "tid",
      "record": {
        "type": "object",
        "required": ["namespace", "algorithm", "digest", "createdAt"],
        "properties": {
          "namespace": { "type": "string", "knownValues": ["git"], "maxLength": 64,
                         "description": "What kind of payload is signed. `git`: a Git object without its signature, as Git hands it to its signing program." },
          "algorithm": { "type": "string", "knownValues": ["hmac-sha256"], "maxLength": 32,
                         "description": "How `digest` is computed. `hmac-sha256`: HMAC-SHA256 keyed with the signature's 32-byte salt, over the exact payload bytes." },
          "digest": { "type": "bytes", "minLength": 32, "maxLength": 32,
                      "description": "The keyed digest, under `algorithm`, of the exact payload bytes." },
          "createdAt": { "type": "string", "format": "datetime",
                         "description": "Required. When the signer signed, to the second, by the signer's own clock." }
        }
      }
    }
  }
}
```

- `namespace` plays the part of SSHSIG's namespace: a later use of the lexicon (release artefacts, for example) gets its own value, so a record made for one purpose cannot be presented for another. Verifiers accept only `git` here.
- `algorithm` leaves room for another construction; only `hmac-sha256` verifies today. Git's payload is hashed with HMAC-SHA256 whatever the repository's object format, so the record does not depend on SHA-1. The salt is the HMAC key, so the digest cannot be recomputed from a guessed payload without the signature (*What the record reveals*).
- The record has no version field: a change of meaning would get a new NSID, and new optional fields can be added under this one as Lexicon evolution allows.
- Nothing else is in the record: no repository name, object id, ref, author, message or forge. See *What the record reveals*.
- Records are written with `validate` unset, because PDSes that do not know the lexicon refuse `validate: true`. Publishing the lexicon for resolution (`_lexicon.tartan.rawkode.academy` and a `com.atproto.lexicon.schema` record) is a release task outside the forge's code.

**The signature Git stores.** Git recognises an X.509 signature only by its first line, `-----BEGIN SIGNED MESSAGE-----`, and passes the whole block back to the program on verification. `tt` writes exactly six lines, each ending in LF:

```
-----BEGIN SIGNED MESSAGE-----
Tartan-Signature: 1
Record: at://did:plc:abcdefghijklmnopqrstuvwx/academy.rawkode.tartan.signature/3lbmxyz2abc2k
CID: bafyreib…
Salt: 9yJk3c…
-----END SIGNED MESSAGE-----
```

The `Record` URI always names the DID, never a handle, because handles change. `Salt` is 32 bytes from the operating system's CSPRNG, fresh for every signature, in unpadded base64url (exactly 43 characters); it is the HMAC key of the record's `digest`. Parsers are strict: those lines in that order, the version `1`, a `did:plc` or hostname-only `did:web` authority, the collection `academy.rawkode.tartan.signature`, a TID record key, a CIDv1 with the dag-cbor codec and a sha2-256 multihash, and a salt of exactly 43 base64url characters that decodes to 32 bytes; at most 517 bytes. Each field must also equal its canonical re-encoding byte for byte: the `Salt` re-encoded from its 32 bytes (so its last character carries zero spare bits; 43 characters hold 258 bits), the `CID` exactly as the `cid` crate's `to_string()` writes a CIDv1 (lowercase base32 with the `b` prefix, never `z…` base58btc or `B…` base32upper), and the URI exactly as the writer writes it. So every accepted block has exactly one spelling, and nobody can mint a second object id with the same payload and a still-valid signature. The longest legal block (a 253-character `did:web` host) is 517 bytes, which is the cap: 31 and 20 bytes for the first two lines, 322 for the `Record` line (`Record: at://did:web:`, the host, `/academy.rawkode.tartan.signature/` and a 13-character TID), 65 for the `CID` line (a 59-character CID), 50 for the `Salt` line and 29 for the last. An earlier draft gave 505 bytes and a 512-byte cap, which would have refused that block.

The salt sits in the signature block, and Git signs the object *without* its signature (D8 step 1), so the salt is outside the signed payload: someone who has only a guess at the payload does not have the salt. A block that starts with `-----BEGIN SIGNED MESSAGE-----` but whose next line is not `Tartan-Signature: ` is someone else's X.509 signature (gitsign's CMS, for example) and is `unsupported_format`; one that claims `Tartan-Signature` but breaks a rule is `bad_signature`.

The CID pins the record's content: a record later replaced under the same key no longer matches. `tt` can compute it before the PDS answers (DAG-CBOR of the record, sha2-256, CIDv1 dag-cbor), which is what makes offline signing possible (*Offline and rate limits*). Changing the `Salt` line of a signed object (which changes its object id but not its payload) either changes the decoded salt, so the digest mismatches, or re-spells the same bytes, which the canonical-form rule refuses; either way it is `bad_signature`; finding another salt and payload with the same HMAC-SHA256 output is a SHA-256 collision or second preimage.

**`tt sign` as Git's signing program.** Git runs `gpg.x509.program` without a shell (`gpg-interface.c`), so the configured program cannot be the two words `tt sign`. Instead:
- `tt` treats an invocation whose first argument is `--status-fd=<n>` or `--keyid-format=long` as `tt sign` (the second is Git's OpenPGP verify argv, handled below, so it reaches the hand-written parser rather than clap). Git's argv is parsed by hand, before clap: `--status-fd=<n>`, then either `-bsau <key>` (also accepted as separate `-b`, `-s`, `-a`, `-u <key>`, `--detach-sign`, `--armor`, `--local-user <key>`, as gitsign accepts) to sign, or `--verify <file> -` to verify. Anything else exits non-zero with a message on standard error.
- *Catching the OpenPGP misconfiguration.* The common mistake is `gpg.program=tt` with `gpg.format` left at its `openpgp` default. Git then signs with exactly the x509 argv, so `tt` cannot see the mistake in its arguments; if it signed, Git would create the commit, and on verification Git would route the `-----BEGIN SIGNED MESSAGE-----` block to `gpg.x509.program` (gpgsm by default), not to `tt`, leaving commits that look signed but that the person's own `git verify-commit` cannot verify. So before signing, `tt` reads `git config --get gpg.format` in Git's environment (the same way it reads `tt.trustedSigner`, so `-c` settings apply). Unless the value is `x509`, it reads standard input to its end, writes no record, and exits non-zero with "tt is Git's x509 program; set gpg.format=x509 (run `tt sign --setup`)". On the verify path, a first argument of `--keyid-format=long` (Git verifying a block it took for OpenPGP with `gpg.program=tt`) gets the same message and `[GNUPG:] ERRSIG`.
- *Other X.509 blocks.* Verifying a block that starts with `-----BEGIN SIGNED MESSAGE-----` but is not a Tartan signature (gitsign's CMS in an older part of the history, for example), `tt` writes `[GNUPG:] NEWSIG` then `[GNUPG:] ERRSIG unsupported`, exits 1, and says on standard error to use `git -c gpg.x509.program=gitsign verify-commit` (or `gpgsm`) for it.
- `tt sign --status-fd=…` with the same arguments behaves identically, so the documentation can say "Git runs `tt sign`". `tt` always reads standard input to its end before exiting, even when it is about to fail, so Git never meets a closed pipe.
- `tt sign --setup [--global] [--did <DID>] [--program <path>] [--no-tags] [--verify-only]` writes `gpg.format=x509`, `gpg.x509.program`, `user.signingKey=<DID>`, `commit.gpgSign=true`, `tag.gpgSign=true` (left unset with `--no-tags`: with it, a plain `git tag <name>` creates a signed annotated tag, opens the editor and costs a record) and adds the DID to `tt.trustedSigner` (*Verification by `tt`*), with `git config` (repository scope by default). `--verify-only` writes only `gpg.x509.program`, needs no signing session, and is for reviewers who verify but do not sign. It never writes `gpg.format`, `user.signingKey`, `commit.gpgSign` or `tag.gpgSign`: Git reads `gpg.format` only to choose how to sign (`use_format` in `gpg-interface.c` is read by `sign_buffer` and `get_signing_key`), and picks the verifying program from the signature's armour (`get_format_by_sig` in `check_signature`), so `gpg.format=x509` would do nothing for verification and would break a reviewer who signs with SSH or OpenPGP by sending their key to `tt`. `gpg.x509.program` is `tt` when the `tt` found on `PATH` is the running binary (so a package upgrade or a Nix profile switch keeps working), otherwise the running binary's absolute path; signing.mdx says that IDEs and GUI clients may have another `PATH`, and that `--program <absolute path>` fixes that. The DID is `--did`, else the default signing DID, else the only stored signing session's (D16, *When `config.toml` is written*); `--setup` never changes `config.toml`. It runs `tt sign --login` first if no signing session is stored (not with `--verify-only`). It prints the settings it wrote.
- `gpg.format=x509` means a repository cannot sign with gpgsm or gitsign and `tt` at once; `--setup` warns when it replaces an existing `gpg.x509.program`, `gpg.format` or `user.signingKey` (with `--global` these are shared with SSH or OpenPGP signing elsewhere), naming the old value.
- Only Git is a supported caller. Other tools that speak the gpgsm argv (Jujutsu's gpgsm backend, for example) set no `gpg.format=x509` in Git's configuration and are refused by the format check; signing.mdx says so.

*Rejected:* a separate `tt-sign` executable or link (a second artefact for packagers, lost by `cargo install` and some package managers), a wrapper script (needs a shell, differs per platform), and `gpg.format=openpgp` with `gpg.program=tt` (Git routes verification by the armour, so a `-----BEGIN SIGNED MESSAGE-----` block always goes to `gpg.x509.program`; openpgp mode would need `gpg.x509.program=tt` as well and gains nothing, and an OpenPGP-style armour would make other tools try to parse the block as OpenPGP).

**Signing (`--status-fd=<n> -bsau <key>`).**
1. Read the payload from standard input, at most 16 MiB (Git commits and tags are far smaller; push certificates too). Refuse unless `git config --get gpg.format` is `x509` (*Catching the OpenPGP misconfiguration*).
2. Choose the account. If `<key>` is a DID, use that DID's signing session; otherwise (Git passes the committer identity when `user.signingKey` is unset) use the default signing DID's session, else the only stored signing session (D16, *When `config.toml` is written*). With no session, fail: "no signing session for … — run `tt sign --login`". `tt` never prompts and never opens a browser: Git captures its standard error, and shows it only when signing fails and only from Git 2.40 (*Context*).
3. Draw a fresh 32-byte salt from the operating system's CSPRNG (never reused, never derived from the payload). Build the record `{"$type": "academy.rawkode.tartan.signature", "namespace": "git", "algorithm": "hmac-sha256", "digest": HMAC-SHA256(key = salt, message = payload), "createdAt": <now, RFC 3339, whole seconds, Z>}`, a fresh TID record key, and the record's CID. The salt goes only into the signature (step 5); it is not stored anywhere else, queued records included, since publishing a record needs only the record. In the `applyWrites` JSON, `digest` travels as `{"$bytes": "<base64>"}` in unpadded standard base64 (RFC 4648 §4, not base64url, unlike the `Salt:` line) and `$type` is included; the PDS converts that JSON to the IPLD data model before hashing, so `tt` computes the CID over the converted form (task 2.7 checks it against a CID captured from the reference PDS).
4. Write it, unless a stored rate-limit or back-off window is open (*Offline and rate limits*), in which case the record is queued at once without contacting the PDS: `com.atproto.repo.applyWrites` on the person's PDS with the DPoP-bound access token (refreshed first if needed, under the refresh lock of *tt's OAuth client*), holding exactly one `create`, this record's (with its `rkey`). Queued records are never in this call, so a bad queued entry can never make a new signature fail or queue (*Publishing the queue*). The call is bounded to 15 seconds. The answer must name the record with the expected URI and CID; a different CID fails signing.
5. Write the signature (above) to standard output, and to the status descriptor `[GNUPG:] BEGIN_SIGNING` then `[GNUPG:] SIG_CREATED D 0 8 00 <unix time> <at:// URI>`. `BEGIN_SIGNING` MUST come first: Git before 2.40 accepts `SIG_CREATED` only after a newline (*Context*), so it can never be the first line. The fields follow gpgsm's layout (detached, hash algorithm 8 = SHA-256) with the record URI in place of a key fingerprint.
6. If the record was written and queued records wait, drain the queue (*Publishing the queue*) with what remains of the 15 seconds, only if the queue lock is free at once; otherwise leave it to the process that holds it.

`git commit -S`, `git tag -s`, `git rebase` with `commit.gpgSign` and `git commit --amend` go through this path; each signed object gets its own record. A rebase, cherry-pick or amend signs only the commits it actually creates: picks that Git fast-forwards (a rebase without `--force-rebase` whose parent is unchanged) keep their existing signature and record, and `tt` is not called for them. `git push --signed` would also call `tt`, but walgit does not advertise push certificates, so Git refuses before signing, and the forge would not verify one; signing.mdx says so. A repository with `extensions.compatObjectFormat` (SHA-1 and SHA-256 interoperability) makes Git sign each object once per hash algorithm, so it costs two records and two PDS writes per object; signing.mdx says so, and D8 reads the header for the repository's own algorithm.

**Verification by `tt` (`--status-fd=<n> --verify <file> -`).** `tt` reads the signature from `<file>` and the payload from standard input and runs the forge's checks (D8 steps 2 to 5) with the same `tartan-atproto` code: DID evidence (did:plc log replay, or did:web over TLS), `getRecord`, block re-hashing, the low-S commit signature by `#atproto`, the MST path, the CID, the namespace, the algorithm and the digest (HMAC-SHA256 of the payload keyed with the block's `Salt`). On the status descriptor it writes `[GNUPG:] NEWSIG` first (Git looks for `\n[GNUPG:] GOODSIG `, so it cannot be the first line), then:
- `[GNUPG:] GOODSIG <DID> <name> (<DID>)`, `[GNUPG:] VALIDSIG <record CID> <YYYY-MM-DD> <unix time of the proving repository revision>` and a trust line, exiting 0, when everything holds. `<name>` is `@<handle>` only when the handle is bidirectionally verified (D9), otherwise the DID again, so `git log --show-signature` never prints an unverified handle. Git then reports `%GK` as the DID, `%GS` as `<name> (<DID>)` and `%GF` as the record CID.
- **Trust is not identity.** Proving the DID says who signed, not whether this person trusts them. The trust line is `[GNUPG:] TRUST_UNDEFINED 0 tartan` by default, and `[GNUPG:] TRUST_FULLY 0 tartan` only when the proved DID is in the local trust list, the multi-valued `git config --get-all tt.trustedSigner` (read by running `git config` in Git's own environment, so `-c` settings and the repository's configuration apply; values that are not valid DIDs are ignored with a warning). `tt sign --setup` adds the person's own DID. So `git verify-commit` exits 0 for any proved signature, while `git merge --verify-signatures`, `git pull --verify-signatures` and `gpg.minTrustLevel` refuse a stranger's signature exactly as they refuse an unknown gpg key, and a free ATProto account cannot pass them. Whether a DID may sign for a project on the forge is the signing rule (D11), which `tt` does not know.
- `[GNUPG:] BADSIG <DID> <DID>` for a CID that differs from the proved record, or a digest, namespace or algorithm that does not match; `[GNUPG:] BADSIG tartan-invalid tartan-invalid` (a fixed placeholder, never an echoed value) for a block that claims `Tartan-Signature` but does not parse. Exit 1.
- `[GNUPG:] ERRSIG <DID>` when the DID, the record or the proof cannot be fetched or verified, or the record is absent. If the record is in `tt`'s own queue, the message says it has not been published yet. Exit 1.
- *Status-line hygiene.* Every value written to the status descriptor (DID, handle, CID, URI) has passed its type's syntax check and never contains whitespace or a newline, because Git searches for `\n[GNUPG:] GOODSIG ` and an echoed newline could forge a status line.

A human-readable line goes to standard error ("Good signature by @alice.example (did:plc:…), record at://…, in the account's repository since 2026-11-09 12:00 UTC"), which `git verify-commit` and `git log --show-signature` print. A proved result is cached under `$XDG_CACHE_HOME/tt/verified/`, keyed by URI, CID and the keyed digest HMAC-SHA256(salt, payload) (a local cache key only, never published; keying on the salt too means an altered `Salt:` line misses the cache and `tt` and the forge always agree), for at most 24 hours, so `git log --show-signature` over a long history does not refetch; `TT_NO_CACHE=1` bypasses it. Verification fetches from the PDS and DID host that the signature names, which whoever wrote the signature chooses: running `git log --show-signature` over a cloned hostile repository tells those hosts the viewer's address and when they looked, much like a tracking pixel. signing.mdx says so, and verification fetches use a 3-second connect timeout and a two-minute per-host back-off window after a connection failure or timeout (like signing's window in *Offline and rate limits*, kept in `$XDG_CACHE_HOME/tt/`), so an offline or captive-portal network costs one timeout per host, not one per commit. `TT_VERIFY_OFFLINE=1` answers from the cache only and gives `ERRSIG` otherwise, for reviewing untrusted clones without contacting their hosts. A signature revoked within those 24 hours can therefore still show as good locally; signing.mdx says so next to `TT_NO_CACHE`. The trust line is computed on every run from the current `tt.trustedSigner`, never cached. Local verification never consults a forge and says nothing about a project's signing rule.

**tt's OAuth client.** Signing needs an ATProto OAuth session with the right to create `academy.rawkode.tartan.signature` records, held by `tt` on the person's machine.
- *Client identity.* `tt` is a public native client. Its `client_id` is a client metadata document that the configured forge serves at `<TARTAN_PUBLIC_URL>/-/auth/tt/client-metadata.json`:

  ```json
  {
    "client_id": "https://forge.example/-/auth/tt/client-metadata.json",
    "client_name": "tt (forge.example)",
    "client_uri": "https://forge.example",
    "application_type": "native",
    "redirect_uris": ["http://127.0.0.1/callback", "http://[::1]/callback"],
    "response_types": ["code"],
    "grant_types": ["authorization_code", "refresh_token"],
    "scope": "atproto repo:academy.rawkode.tartan.signature?action=create repo:academy.rawkode.tartan.signature?action=delete",
    "token_endpoint_auth_method": "none",
    "dpop_bound_access_tokens": true
  }
  ```

  The reference authorization server accepts loopback redirect URIs only for `native` clients, and ignores the port when the registered URI has none (`@atproto/oauth-provider` `client-manager.ts`, following RFC 8252 §7.3), so `tt` listens on any free port, or `--port <n>`. Serving the document from the forge keeps Tartan free of a central endpoint, and the consent screen names the forge the person uses.
  - *Rejected: the `http://localhost` client_id.* The ATProto profile describes it as a development exception that authorization servers may refuse, and it shows as a development client on consent screens. `tt` offers it only as `tt sign --login --client localhost`, for a forge that is not reachable over public HTTPS. Its client_id carries `redirect_uri=http://127.0.0.1/callback`, `redirect_uri=http://[::1]/callback` and a `scope=` query holding `atproto` and both `repo:academy.rawkode.tartan.signature` tokens, since the authorization server reads that query as the declared scope; `tt` listens on the path it declares.
  - *jacquard-oauth's loopback helper.* In 0.12.2, `login_with_local_server` always builds the localhost client (`build_localhost_client_data`, with the path `/oauth/callback`), so it cannot serve the forge-hosted client_id. `tt` builds its own `ClientData` (client_id = the forge's metadata URL, redirect `http://127.0.0.1:<port>/callback`, no keyset), runs its own listener on tokio, and calls jacquard-oauth's PAR, code-exchange and refresh functions directly, for `--client localhost` too (with its own `/callback` path); task 1.1 confirms those entry points accept a discoverable public client.
  - *Loopback redirects for an https client_id.* The reference `@atproto/oauth-provider` accepts `127.0.0.1` and `[::1]` redirects for `application_type: native` clients, but the ATProto OAuth profile describes loopback redirects plainly only for the localhost exception, so another authorization server may refuse them; `tt sign --login` then reports its `invalid_redirect_uri` or `invalid_client_metadata` and suggests `--client localhost`.
  - *Rejected: a client metadata document on a Tartan project domain.* It would make every forge's signing depend on one operator's endpoint.
  - *Rejected: a confidential client.* A CLI cannot keep a client secret, and ATProto offers no dynamic registration.
- *Flow.* `tt sign --login [--handle <h>]` resolves the person (D9, in `tt`), sends a PAR with PKCE S256, DPoP from the first request, `login_hint`, the loopback `redirect_uri` with the chosen port, and scope exactly `atproto repo:academy.rawkode.tartan.signature?action=create`, opens the authorization URL (or prints it with `--no-open`), receives the code on `http://127.0.0.1:<port>/callback`, checks `state` and `iss`, exchanges the code, and requires `sub` to be the resolved DID and the granted scope to include the create permission, compared by meaning with jacquard-oauth's `Scopes`. A refusal of the `repo:` scope fails with an explanation; `tt` never falls back to `transition:generic`, which would let it write anything in the person's repository. With no forge configured and none given with `--forge` or `TT_FORGE`, it fails with "no forge configured: run `tt login --forge <url>` or pass `--forge`" before any request. `tt login` runs this flow right after the forge login on first run, for the forge session's DID (D16, *Forge login hand-off* step 6).
- *Least privilege.* `tt`'s stored session can only create signature records. That limits what `tt`'s own credential exposes; it does not make `tt` the only thing that can sign (*Trust*). `tt sign revoke` (below) authorizes once more for the delete permission and, after one call, revokes those tokens at the authorization server's `revocation_endpoint` (as D1 step 8 does for the web client), so the one-off session does not linger in the account's app sessions. Both tokens are declared verbatim in the metadata, because authorization servers compare scope tokens literally (D1, *Scope*).
- *Lifetime.* ATProto asks authorization servers to limit a public client's whole session, and each refresh token, to two weeks. `tt` therefore re-authorizes about every two weeks; signing fails with a message naming `tt sign --login` once the session ends, and `tt status` shows when it will. Because Git shows nothing from a successful signing, `tt status`, `tt sign --flush` and the `pre-push` hook warn when fewer than two days remain. Access tokens live up to 60 minutes on the reference server (`@atproto/oauth-provider` `oauth-constants.ts` `TOKEN_MAX_AGE`, capped by the session), and `tt` uses the server's `expires_in` and refreshes on demand. The two-week figure is the reference server's `SESSION_LIFETIME` and `REFRESH_LIFETIME` for public clients, in the same file.
- *Refresh.* Refresh tokens are single-use, so `tt` takes an exclusive lock (`std::fs::File::lock` on `$XDG_STATE_HOME/tt/locks/<did>.lock`, the *refresh lock*) around every refresh and re-reads the stored session after taking it, so parallel signing (two Git processes, or an editor and a terminal) refreshes once. DPoP nonces are tracked per server and stored with the session. A refresh refused with `invalid_grant` fails with a message naming its possible causes, since the protocol does not tell them apart: the session ended, was revoked, or was refreshed by a copy of it on another machine ("signing sessions cannot be shared between machines; run `tt sign --login` here"). After every refresh `tt` checks that the token response's `sub` is still the session's DID, and whenever it re-resolves the DID it checks that the DID's current PDS still names the stored issuer; if the account has migrated, signing fails with "run `tt sign --login`" rather than writing to a stale PDS. Wherever `<did>` appears in a file name in this section it is the DID in unpadded lowercase base32, because `:` is not allowed in Windows file names.
- *Refresh failures are split.* Only `invalid_grant`, or a session the authorization server refused or revoked, is an *authorization error*. An authorization server that cannot be reached or times out, a 5xx, or a token-endpoint `invalid_client_metadata` or `invalid_client` while the stored session is otherwise valid is *transient*. The reason for the last two: the session's `client_id` is the forge's metadata URL, and the reference authorization server (`@atproto/oauth-provider` `oauth-provider.ts` `authenticateClient`, used by every grant, refresh included) loads the client metadata on every token request and caches it for only 10 minutes (`clientMetadataCache`, `ttl: 600e3`). When the forge is down for longer than that, refreshes fail with `invalid_client_metadata` although nothing is wrong with the session, and `tt sign --login` could not help, because PAR needs the same document. A transient refresh failure is handled like an unreachable PDS (*Writes that cannot be made now are queued*): under `sign.offline=queue` the record is queued, the back-off window opens, and the last-failure message names the cause ("the client metadata at <forge>/-/auth/tt/client-metadata.json could not be loaded by your authorization server; is the forge down?") rather than `tt sign --login`.
- *Sessions belong to their forge.* A signing session is tied to the client metadata it was created with. `tt login --forge <other>` or a new default forge leaves it alone; `tt status` shows which forge's `client_id` each signing session uses. A decommissioned forge, or a changed `TARTAN_PUBLIC_URL`, ends every signing session made through it at the next refresh; people run `tt sign --login --forge <new>` (signing.mdx and deploying.mdx say so).
- *Storage.* The refresh token, the access token and the DPoP private key (ES256) are stored together as one secret in the credential store (D16, *Credentials*).

**Offline and rate limits.** A signature needs a PDS write, so signing needs the network. Decisions:
- *One record per signed object.* Git asks for each signature synchronously, before the object exists, and embeds what the program returns; the program never learns that a batch has ended. A batch record over many digests would have to be written after the last signature was already returned, so every signature would point at a record that does not yet exist, and a lost batch would orphan all of them. Per-object records keep each signature independently verifiable.
- *Writes that cannot be made now are queued.* When the PDS cannot be reached, times out, or answers 5xx or 429, or a token refresh fails transiently (*Refresh failures are split*), and `sign.offline` in `$XDG_CONFIG_HOME/tt/config.toml` is `"queue"` (the default), `tt` appends the record (DID, rkey, record, CID, and `state`) to `$XDG_STATE_HOME/tt/queue/<did>.jsonl` (mode 0600) and still returns the signature, whose CID it already knows. So commits work on a train. `"fail"` makes signing fail instead, for people who want every signature published before the object exists. An authorization error (an expired or revoked session, or `invalid_grant`) always fails, because the queue could never be published with that session.
- *Outcome unknown.* A timeout, a dropped connection or a 5xx after the request was sent does not say whether the PDS committed the write. The reference PDS commits and can then fail to answer; and a later plain `create` for a key that already exists fails the whole atomic `applyWrites` with a 500, not a client error (`packages/repo/src/mst/mst.ts` throws a plain `Error` "There is already a value at key", which the `applyWrites` handler does not map to 400). So a queued record is never resent blindly: every queued entry is *unconfirmed* until a read says otherwise.
- *Publishing the queue.* Draining runs under the queue lock (below), oldest first:
  1. *Reconcile.* For each queued record, read it with `com.atproto.repo.getRecord` (public, so it needs no scope or session). Present with the same CID: published, dropped from the queue. Present with another CID: dropped and reported in `tt status` and on standard error, since the signature that names it can no longer verify. Absent (`RecordNotFound`): to be sent. A read that fails leaves the record queued for the next drain.
  2. *Send* the absent ones in `applyWrites` calls of at most 200 creates (the reference PDS's limit per call). A call that succeeds drops its records. A call that times out or answers 5xx leaves its records queued, still unconfirmed, so the next drain reads them first. A call that answers 4xx other than 401, 403 or 429 is retried once after reconciling its records again (step 1); if it fails again those records stay queued and are reported.
  3. *Rewrite* the queue file with what remains (write to a temporary file in the same directory, then rename).

  Drains happen after a successful signing (step 6 of *Signing*, only if the queue lock is free), with `tt sign --flush`, and from the `pre-push` hook that `tt sign --setup --hook` installs (`tt` never prompts, so the hook is never installed without the flag). The hook drains every queued DID, not only the repository's `user.signingKey`: the records are already promised by signatures that exist, so publishing them early only helps. `tt sign --setup` without `--hook` prints a one-line hint recommending it, and `--setup --global` prints that the hook is per repository: run `tt sign --setup --hook` in each repository where offline work is pushed, or `tt sign --flush` before pushing. `tt status` counts what waits.
  - *Where.* The hook goes at the path `git rev-parse --git-path hooks/pre-push` gives, so linked worktrees are respected. `--hook` with `--global` is refused, because hooks are per repository and `tt` never sets `core.hooksPath`. When `core.hooksPath` is set and the resolved path is outside the repository's common Git directory (`git rev-parse --git-common-dir`, not `$GIT_DIR`, which in a linked worktree is `.git/worktrees/<name>`, so a `core.hooksPath` pointing at the repository's own `.git/hooks` is accepted from any worktree; a shared hooks directory, which other repositories use, is refused), or the path is tracked in the working tree (`git ls-files --error-unmatch`, as with husky's `.husky/`), `--hook` refuses and changes nothing, unless `--hooks-path-ok` is given.
  - *Idempotent install.* The script `tt` writes carries the fixed marker line `# tt-sign-hook v1`. If the current `pre-push` carries the marker, `--hook` rewrites it in place and renames nothing. If it has no marker and `pre-push.tt-chained` does not exist, it is renamed to `pre-push.tt-chained`. If it has no marker and `pre-push.tt-chained` already exists, `--hook` refuses and changes nothing, so a person's original hook is never overwritten and a `tt` hook never chains to itself.
  - *What it runs.* `tt sign --flush --hook`, through the same program path `gpg.x509.program` gets (`tt`, or `tt`'s absolute path when the `tt` on `PATH` is not this binary or `--program` was given), so GUI clients with another `PATH` find it; if that program is missing the hook prints a warning and skips the flush. It then runs `pre-push.tt-chained`, when present and executable, with the same arguments and standard input (the flush runs with standard input from `/dev/null`, so it cannot consume the ref list Git sends), and exits with the chained hook's status, so a chained hook can still refuse a push. Only `tt`'s own flush always counts as success.
  - *Undo.* `tt sign --setup --undo [--global]` unsets each setting `--setup` writes whose value is still the one `tt` wrote (`gpg.format`, `gpg.x509.program`, `user.signingKey`, `commit.gpgSign`, `tag.gpgSign`, and the DID in `tt.trustedSigner`), leaves values someone changed since, and in a repository removes a marked `pre-push` hook and renames `pre-push.tt-chained` back. It needs no session.
- *The queue lock.* Git signs from separate processes that can run at once (commits in two repositories, an IDE and a terminal, a rebase next to `tt sign --flush`). Every queue operation holds an exclusive `std::fs::File::lock` on `$XDG_STATE_HOME/tt/queue/<did>.lock` from reading the queue to rewriting it: appending a record, a drain (reconcile, every `applyWrites`, rewrite), `--flush`, the hook, and `tt sign revoke` of a queued record. Appending waits for the lock (a drain holds it for at most about 15 seconds per call); a signing that finds it held skips its drain rather than wait; `--flush` and the hook wait. Lock order: the queue lock may be held while the refresh lock is taken, never the reverse. With it, a drain's rewrite never drops a record appended meanwhile, and two drains never send the same create.
- *Signing never sleeps.* `tt` keeps, per DID in `$XDG_STATE_HOME/tt/queue/<did>.state.json`, a rate-limit window (until the `ratelimit-reset` of the last 429) and a back-off window (two minutes after a connection failure or timeout, so a captive-portal network does not cost 15 seconds per commit of a 50-commit rebase). While either window is open, signing queues the new record at once without contacting the PDS, and no drain runs. `tt` never waits for `ratelimit-reset` inside Git's signing call. A large rebase therefore completes locally and its records drain later as the budget allows.
- *`tt sign --flush`* drains everything the budget allows and exits 0 when the queue is empty. When records remain, it prints how many, the reason (rate limit, PDS unreachable, records reported) and when it will next be worth retrying, and exits 1. `tt sign --flush --hook` does the same but always exits 0, printing the remaining count and reason on standard error, so a push is never blocked by the PDS: the forge keeps a missing record's check pending for up to seven days (below), and a push before the queue is flushed costs only a delay.
- *The forge waits for late records.* On a ref the signing rule covers, a record of a signer the rule allows that is proved absent, or such a signer's PDS that cannot be reached, keeps the check `pending` for up to seven days (one hour otherwise), retried at least hourly (D8, *A missing record is not final*), so a record published the next morning verifies without anyone acting. After seven days the object is `unverifiable`, and the signer (`tt sign recheck`) or an owner can re-check it once the record is published.
- *Rate limits.* The reference PDS currently meters repository writes per account, by default, at 5,000 points an hour and 35,000 a day, a create costing 3 points (other PDSes and later versions may differ, and nothing in `tt` depends on these figures, since it follows `ratelimit-reset`): about 1,666 records an hour and 11,666 a day. Ordinary work is far below this; a rebase that re-signs thousands of commits in an hour is not. applyWrites saves round trips, not points. An online rebase makes one PDS round trip per commit it creates; signing.mdx gives the expected time.
- *Rejected: deferring every write to push time* (signing only queues; a `pre-push` hook publishes the records of the objects being pushed, so rebased-away commits never leave a record). It would publish less, but every push would depend on a hook that `--no-verify`, other Git clients and IDEs skip, and a signature would be unverifiable by anyone until then. The queue gives the offline benefit without making that the normal path.

**What the record reveals.** ATProto repositories are public, so every signature record is public, whatever the repository it signs.
- *Content.* The record holds HMAC-SHA256 of the signed payload (the tree id, parent ids, author, committer and message), keyed with a random 32-byte salt that only the signature carries. Without the object's signature block nobody can recover any of the payload or confirm a guess at it. Someone who has the object, signature included, can link it to the record, which is the point of a signature.
- *Decision: a per-signature random salt as the HMAC key.* An unsalted SHA-256 would let anyone confirm guesses at low-entropy payloads, because `createdAt` and the TID come from the same clock, at the same moment, as Git's committer time. Examples: a conflict-free merge of two public commits into a private fork (public parents, a deterministic tree, the default "Merge branch …" message), a revert or cherry-pick of a public commit, a tag of a public commit in a private repository (`object <public sha>`, `type commit`, `tag v1.2.3`, a known tagger and time), or a reworded amend. An observer of the public record could test a few candidates and confirm that a named person did that privately at that second. The salt stops this: it travels in the signature block, which is not part of the signed payload (Git signs the object without its signature, D8 step 1), so someone building a candidate payload does not have it, and 2^256 possible keys per candidate make guessing hopeless. A salt in the record would protect nothing, since the record is public. HMAC rather than SHA-256 over salt then payload, because HMAC is the standard keyed construction with no length-extension concerns and is in the `hmac` and `sha2` crates the workspace already depends on. The cost is 50 bytes in each signature.
- *Object ids.* A forge's object id (SHA-1 over the object with its signature) is not the record's digest, so an object id seen in a URL or a log does not find the record; an object id does not reveal the salt either.
- *Timing.* Each record shows when its signer signed something (the TID record key, `createdAt`, and the repository revision on the firehose). Signing work in a private repository therefore reveals the signer's activity pattern, though not the repository. This is accepted as inherent: removing `createdAt` would hide nothing while the record key and the firehose keep the time. People for whom the pattern itself is sensitive can sign with a separate ATProto account used for nothing else; signing.mdx says so.

**Revoking a signature.** `tt sign revoke <commit|at-uri>` (a commit is resolved through its signature) authorizes once with exactly `atproto repo:academy.rawkode.tartan.signature?action=delete`, deletes the record with `com.atproto.repo.deleteRecord`, revokes those tokens at the authorization server's `revocation_endpoint` (when it lists one) and drops them, and, when `tt` is signed in to a forge (D16), calls `POST /-/api/people/{did}/signatures/{rkey}/refresh`. Signed in with a CLI session (`tt login`) as the record's own DID, whatever that DID's rights on the forge, it sends `{"withdraw": true, "cid": "<record CID>"}`, and the forge marks the record revoked on the DID's word (*Watching records*), without depending on a proof of absence that a re-created record could win; signed in as someone else (an owner), or only with an access token (`tt login --with-token`, which cannot withdraw, D4 *Route classes*), it sends no body and the forge re-proves the record at once; with an access token for the record's own DID it also prints that withdrawing needs `tt login`. A record still in the local queue is instead removed from the queue under the queue lock, with no OAuth flow, since it was never published. Deleting a record is how a person withdraws a signature made by someone who stole their signing session, or by mistake. It does not rewrite history (D8, *Annotations*), but a revoked signature no longer counts toward a signing rule on any later judgement in any repository of that forge (D8 *Standing*, D11 *Compliance*).

**A compromised signing credential.** Forging a signature needs only a credential that can write to the account's repository, which need not be `tt`'s (*Trust*). Whoever holds one can also re-create a deleted record, since its content and record key are public, at the same key with the same CID. The procedure, in this order, is in signing.mdx and `tt sign revoke --help`:
1. Revoke every credential that can write to the account's repository, because the forger may not be using `tt`'s session at all: every app password, and every authorized app session with repository write access (`transition:generic`, `repo:*`, or a `repo:` permission covering `academy.rawkode.tartan.signature`), in the account's settings at the PDS; change the account password if it may be known. That includes `tt`'s own sessions there, because a thief may hold a refresh token rotated from the same session that `tt` never saw. `tt logout` is not needed and would end the forge CLI session that step 2 uses; `tt`'s stored signing session is useless once revoked and is replaced in step 3.
2. `tt sign revoke` each forged signature. Signed in to the forge as the account with `tt login` (a CLI session, not an access token), this withdraws it there on the account's word, whether or not the account can read the forge.
3. `tt sign --login` again for a fresh session.

A Tartan forge that recorded a revocation keeps it: a revoked `signature_records` row is never un-revoked (*Watching records*), so re-creating the record does not restore it there, and a withdrawal (step 2) needs no proof of absence, so a forger who re-creates the record before the forge looks cannot win the race. Anyone who never saw the revocation cannot tell: another forge, and `git verify-commit` on anyone's machine, prove whatever the repository holds now, so a revocation that someone still holding write access has undone is invisible to them. That is why revoking every writing credential comes first.

**Watching records.** A forge learns of revocations only for records it relies on: every record that verified a stored result has a `signature_records` row in the identity actor (D3), and the signer's DID is known as `signer` (within the caps of D3, *Housekeeping*). `ReproveSignature{did, rkey}` always fetches `getRecord` afresh and proves it (D8 step 5) without the 10-minute proof-reuse cache; a proved absence, or a proved record with another CID, confirmed as below, sets `revoked_at` and `revoked_reason` (`deleted` or `replaced`) and records `signature.revoked {did, rkey, cid, reason}`; anything that fails to prove or to confirm leaves the row as it is. **Revocation is permanent on the forge:** once a `(did, rkey)` row has `revoked_at`, nothing clears it: not a later proof that finds the record present with the original CID, not `RecordSignature`, not `ReproveSignature`, not a re-check. A person who deleted a record by mistake signs the object again. Triggers:
- a Jetstream commit event in `academy.rawkode.tartan.signature` with operation `delete` or `update` for a tracked `(did, rkey)` (D10); creates are ignored, so routine signing costs the forge nothing;
- `POST /-/api/people/{did}/signatures/{rkey}/refresh` by that DID or an owner (what `tt sign revoke` calls);
- a withdrawal: the same route called by the record's own DID with `{"withdraw": true, "cid"}` runs `WithdrawSignature{did, rkey, cid}`, which sets `revoked_at` with `revoked_reason` `withdrawn` and records `signature.revoked` without fetching anything, so it cannot lose a race with a re-created record. The record is revoked whatever `cid` the call sends, since only the DID can withdraw, and `signature.revoked` records the CID sent. For a record the forge does not track yet, it inserts a `pre_withdrawn` row that is already revoked, so a later push of an object signed by it, however much later, is judged against a revoked row. Those rows are never deleted, because deleting one would un-revoke it; storage is bounded by caps instead (D4, *Route classes*: 1,000 per DID, 100,000 forge-wide, and strangers only below 50,000), and beyond a cap only new untracked inserts answer 429, while withdrawing a tracked record always succeeds. Only the DID itself can withdraw, from a browser or CLI session and whatever its rights on the forge (the `self` route class, D4): an owner cannot withdraw someone else's signature, a `tartan_pat_` token cannot withdraw at all, and a withdrawal is only as strong as the forge session that sends it (D6). The caps mean a thief who creates more forged records than that cannot all be withdrawn in advance; the rest are withdrawn once they verify on a push, which signing.mdx says, together with the caps and that a pre-withdrawal never expires.
- an owner's re-check, and any later proof of the same record during verification.

**Confirming before revoking.** Revocation is permanent, so a proof that would revoke is never taken from stale evidence. Before any path sets `revoked_at` from a proof (`ReproveSignature`, D8 step 5.5 *replaced*, and the step 5.4 absence that marks a tracked row), the forge drops the reuse cache for the DID, runs `RefreshIdentity{did}` (re-resolving the DID evidence with no cache) and proves the record again, with a fresh `getRecord`, from the PDS and against the `#atproto` key that refresh found, in the same call. It revokes only when that second proof again proves absence or the same other CID. If the refresh or the second proof fails, nothing is revoked and the call is a transient failure; if the second proof finds the original CID, nothing is revoked and verification continues with that result. A proof whose repository commit `rev` is lower than the row's stored `rev` is stale (a caching proxy, a lagging replica or a replayed older state) and is likewise a transient failure, never a revocation; ATProto revs are TIDs that increase with every commit, so a PDS restored after data loss writes higher revs and its absence proofs still revoke. Two cases this rules out: a record deleted within ten minutes of being verified, whose Jetstream delete would otherwise be judged against the cached bundle that still shows it present, so the revocation would be lost (Jetstream does not redeliver it); and a PDS the account has migrated away from, still serving the old repository signed with the old key the forge holds, whose valid absence proof for a later record would otherwise revoke it, since a proved absence never triggers the identity refresh that a failed proof does (D8, *When the proof does not verify*).

A `RecordNotFound` error is not signed, so it proves nothing here: a re-proof that gets one changes nothing (transient), and only a signed absence proof, confirmed as above, revokes. (Verification treats it as a missing record, which is retried, D8 step 5.1, and never revokes.) When the first proof was not conclusive (a proof that did not verify against stale evidence), the confirming proof cannot agree with it, so after the identity refresh the forge proves twice more against the fresh evidence and revokes only when those two agree.

With Jetstream disabled, a revocation reaches the forge only through the refresh route or a later proof; the configuration docs say so. A record of a signer beyond the watch caps is still tracked and refreshable, but Jetstream does not report it.

**Trust.** A `verified` signature means: this DID's repository, as signed by its current `#atproto` key, holds a record over exactly these bytes. That key is normally held by the person's PDS, not the person, so the PDS operator can sign as any account it hosts; this is inherent to ATProto, where the PDS already speaks for the account in everything else. For a `did:web` signer, the domain is itself a signing credential: whoever controls the domain later (after it lapses or is transferred) can publish a new `#atproto` key and sign as the DID, and proofs are always checked against the current key. **Any credential that can write to the account's repository can sign Git objects as the account**: an app password, any app granted `transition:generic` or a `repo:` permission that covers `academy.rawkode.tartan.signature` (including `repo:*`), `tt`'s own session, and the PDS operator. The repository commit does not record which client wrote a record, so neither the forge nor `tt` can tell these records apart: they verify alike. `tt`'s narrow scope limits what a stolen `tt` session exposes; it does not limit who else can sign. People who use app passwords or broad-scope third-party apps on their account should know this, and people who need narrower exposure sign with a separate ATProto account used for nothing else (*What the record reveals*), which they never give to other apps. A stolen `tt` session can sign until it ends (at most two weeks), the person revokes it at their authorization server, or `tt logout` revokes it; forged signatures from any credential are withdrawn with `tt sign revoke` (*A compromised signing credential*). The OAuth client metadata `tt` uses is served by the configured forge (*tt's OAuth client*), so the person also trusts that forge's operator for the client's identity: an operator could change its redirect URIs, although the person still has to consent at their authorization server; signing.mdx says so. A DID that moves to another PDS keeps its signatures, since the records move with the repository and are proved against the DID's current key.

**Agents and automation.** Tartan is agent-native, and a covered ref judges whatever an agent pushes, so the plan settles how agents sign:
- *Who an agent signs as.* An agent that runs on the person's own machine, as that person's operating-system user, may use the person's `tt` signing session: it is the same credential store and the same locks, and the person is answerable for it. An agent that runs anywhere else (a server, a shared runner) signs as its own ATProto account, a bot DID, which a repository lists in its rule's `signers` if it should be allowed. It never receives a copy of a person's signing session.
- *How it gets a session.* Once, on a persistent host: `tt sign --login --handle <bot> --no-open --port <p>` with `TT_CREDENTIAL_STORE=file` and a persistent `XDG_STATE_HOME`, approving in a browser through a forwarded port (D16, *Remote shells*). The session must be re-authorized about every two weeks (*Lifetime*); `tt status` and `tt sign --flush` warn two days ahead.
- *Not supported in this change.* Ephemeral CI runners without a persistent credential store, and sharing one signing session between machines or containers: refresh tokens are single-use and rotate, so the first copy to refresh breaks every other copy, and `tt` reports that `invalid_grant` as described under *Refresh*. Forge access tokens (`tartan_pat_`, D5) are for the forge's API only and cannot sign.
- *Unsigned agent pushes.* An agent that pushes unsigned commits to a covered ref causes a `ref.signature.violation`, as anyone's would, and on `main` its configuration is refused. Signing without a browser-approved session (for example ATProto service auth or app passwords) is left to a later change.

**Rejected alternatives.**
- *SSH signatures with keys published as ATProto records* (`gpg.format=ssh`, keys as `org.tangled.key.sshKey` records): a second key per person to generate, protect, publish and rotate; a record proves only that the DID published a public key, not that it holds the private one, so copied keys need committer-email pinning and an ambiguity status; and the forge needs a key index, OAuth writes for key management, and its own revocation story. The record-as-signature design needs none of these.
- *OpenPGP*: the same key-management burden, a large and LGPL-licensed implementation (sequoia), and no binding to the DID.
- *Forge-issued X.509 certificates* (a Fulcio-like CA in the forge, as gitsign uses with Sigstore): the forge would become a certificate authority, verification would trust the forge rather than the person's DID, signatures would verify only where that forge's root is trusted, and short-lived certificates need a transparency log to be checked later.
- *Signing with the `#atproto` key directly*: it is held by the PDS, which exposes no "sign these bytes" API; writing a record is the only way to have the repository key sign something.
- *ATProto service-auth JWTs* (`com.atproto.server.getServiceAuth`) as signatures: they are short-lived bearer tokens for a named audience, not durable statements, and they cannot be re-proved later.

### D8. Verifying a pushed object

**Queueing.**
- When the Repo actor records `ref.updated` for `refs/heads/*` or `refs/tags/*`, it inserts `signature_checks(seq, ref_name, old, new, rule)` in the same transaction. `rule` is a copy of the `signing_rule` row in force at that moment, so a push is judged by the rule from before it even when a configuration applies between the push and the check. Ref deletions (`new` all zeros) and other refs are never queued.
- **Durable retries.** The queue is worked by the Repo actor's scheduled action `verify` (handler: `verify_later`), never by a task that relies on the actor staying awake. Rivet's `wait_until` does not block idle sleep (`rivetkit-core` 3.0.6 `work_registry.rs`: `WaitUntil` has `blocks_idle_sleep: false`) and an idle actor sleeps after 30 s plus a 15 s grace period, aborting that work. So:
  - **One pending schedule.** Each Repo actor has at most one pending `verify` schedule. Its Rivet event id and time are kept in a one-row table, `verify_schedule`. Every caller goes through one helper, `ensure_verify_at(t)`, serialised by an actor-level `verify_schedule_lock` so two callers never both register. The stored row counts as pending only while Rivet still holds its event: `ensure_verify_at` checks `ctx.schedule().get(event_id)` (rivetkit 3.0.6 `Schedule::get`), because Rivet claims and deletes a one-shot `At` schedule as it dispatches it (rivetkit-core 3.0.6 `actor/schedule.rs`, `take_due_schedule_dispatches`), so a row whose event has fired, or is firing, names nothing. When the row is missing or its event is gone, the helper clears the row and registers `ctx.schedule().at(t, "verify", …)`; when the event is pending at or before `t` it does nothing; when it is pending later than `t` it cancels it (`ctx.schedule().cancel(id)`) and registers the earlier one. `at` and `next_at` are both Unix milliseconds, the unit of `Schedule::at(timestamp_ms, …)`. This matters because Rivet caps an actor at 1000 pending schedules (rivetkit-core 3.0.6 `DEFAULT_MAX_SCHEDULES`; `at()` fails with `max_schedules_exceeded` beyond it), and the outbox's delivery retries (`outbox.rs`, `schedule_retry`) draw on the same budget. A push of 1500 tags therefore costs one schedule, not 1500.
  - after recording `ref.updated`, the actor calls `ensure_verify_at(now)`;
  - **Serialised runs.** `verify` holds an actor-level `verifying` mutex for its whole run, as `reconcile` holds `reconciling`, because Rivet runs actions, scheduled fires included, concurrently (rivetkit 3.0.6 `start.rs`, `spawn_action_reply`). A wake that finds the mutex held sets an actor-level `verify_rerun` flag and returns; its own schedule is already gone, so it does not touch `verify_schedule`. The running pass, when it has worked its due rows, clears the flag and re-reads the queue while the flag was set and its budget allows. Two wakes never work the same row, so events and hand-offs are not duplicated (subscribers still see at-least-once redelivery, as for every event). Lock order: `verifying` is never acquired while `verify_schedule_lock` is held, and a run releases `verifying` before it calls `ensure_verify_at`, so the two locks are never nested.
  - **Bounded passes.** One run works due rows (`next_at <= now`) at most 50 per run and for at most 5 minutes of wall clock; a run that stops early leaves the remaining due rows for the next run. Before each attempt the run picks the next due row by priority, not by `seq` alone: first the head update (*The head update*), then rows whose copied rule covers their ref, then the rest, each group in `seq` order. A head update pushed while a run is busy is therefore picked as soon as the attempt in progress ends, at most one attempt deadline later (*Bounded attempts*), and updates to uncovered refs never delay the configuration gate by more than that. Rows of one ref may finish out of order (an earlier update can still be retrying when a later one is judged); results are therefore kept per update, see *Per-update results*. Each attempt runs inside the `verify` action, which keeps the actor awake while it runs. A failed attempt writes `attempts`, `next_at` and `last_error` (a short reason such as `PDS pds.example unreachable`; never a secret or a token) and registers nothing itself. The run ends with exactly one `ensure_verify_at` on every exit path, errors and early returns included: the action wraps the pass so that, whatever the pass returned, it releases `verifying` and then calls `ensure_verify_at` at `now` if due rows remain beyond the 50 or the time budget, otherwise at the minimum `next_at` of the rows still queued, or not at all when the queue is empty. Calling it after releasing the mutex closes the last gap: a wake that arrived during the run and set `verify_rerun` too late to be seen has had its schedule consumed, so the validated helper finds no pending event and registers one. Rivet records an error returned by a scheduled action and registers nothing (rivetkit-core 3.0.6 `finish_schedule_dispatch`), which is why the pass's error must not skip this step. If `ensure_verify_at` itself fails (an SQLite error), the action returns that error, and the next push or `on_start` registers the schedule. Rivet puts no action timeout on scheduled fires (in rivetkit-core 3.0.6 `action_timeout` applies only to HTTP-dispatched actions, `registry/http.rs` and `dispatch.rs`, and a scheduled fire runs inside a keep-awake region), so the 5-minute budget is Tartan's own, and it is enforced inside an attempt as well as between rows (*Bounded attempts*). A run cut short by shutdown leaves its rows queued, and `on_start` schedules them again. Liveness rests on one invariant: while any row is queued, either a run holds `verifying` (and will call `ensure_verify_at` on exit) or a `verify` event that Rivet still holds is pending at or before the earliest `next_at`;
  - the backoff is 5s × 2ⁿ capped at 5 min; the attempt that runs one hour or more after the first gives up (below), unless the update is *waiting on its signers*: its copied rule covers its ref, and every object still failing failed its last attempt only because its record is missing (*A missing record is not final*) or its signer's PDS could not be reached, timed out, or answered 5xx or 429, and names a DID the copied rule allows (any DID when the rule lists no `signers`). Such an update stays queued for up to seven days after its first attempt, retried hourly after the first hour, and the attempt that runs seven days or more after the first gives up. A Git host failure, a proof that does not verify, an update to a ref its copied rule does not cover, and an object whose DID the rule does not allow keep the one-hour limit: the seven-day wait exists so that a rule's own signers can publish late, and nothing else needs it. Objects carried over by a bound (*Bounded attempts*) never count as failures, so they neither start nor extend a window;
  - **Bounded attempts.** Each object's signer DID and PDS come from text in the object, which anyone who can push can write, and an attempt must not be stretched by hosts that answer slowly or never. So, for every attempt:
    - *Deadline.* An attempt ends at the earlier of 90 seconds after it started and the run's 5-minute budget. Per-object work runs under `tokio::time::timeout_at` with that deadline, so an in-flight fetch is cancelled at the deadline rather than allowed its full 10-second timeout (D9, *Fetch safety*). Objects not finished by the deadline are *carried*: they get no result and no failure, and the next attempt starts with them.
    - *Progress is kept.* At the end of every attempt, in one transaction, objects whose check completed with a final status (`verified`, `unsigned`, `bad_signature`, `signer_inactive`, `unsupported_format`) are upserted into `object_signatures` and their bundles written, and `RecordSignature` follows for each new `verified` object as in step 6. Statuses are final, so storing them before the update resolves changes no outcome, and the next attempt reuses them instead of proving them again. The update itself is still judged only when it resolves (step 6 or *Giving up*).
    - *Memoised fetches.* A run keeps one `FetchMemo`: each DID is resolved at most once per run, and `RefreshIdentity` runs at most once per DID per run; each host (DID document host or PDS) that failed to connect, timed out, or answered 5xx or 429 fails fast for the rest of the run with the same reason, without another request, like `tt`'s per-host back-off window (D7, *Offline and rate limits*). Objects that fail fast are ordinary transient failures with that `last_error`.
    - *Bounded concurrency.* At most 8 objects are in flight per attempt and at most 2 requests to any one host at a time.
    - *Signer caps.* An attempt fetches for at most 16 distinct signer DIDs whose evidence the run has not already resolved; objects of further DIDs are carried. Over its whole life an update fetches for at most 64 distinct signer DIDs; objects of DIDs beyond the 64th (in walk order, newest first) are *deferred*: they are never fetched, and when the update resolves they are judged `not_checked` with the detail `more than 64 signers in one update`. A legitimate update rarely has more than a handful of signers, and an update with more is non-compliant on a covered ref only until an owner re-checks it (*Statuses are final*), which retries the deferred objects under fresh caps.
    - *Deferred objects are not stored.* A deferred object, and an object still carried when the update gives up, gets no `object_signatures` row, because no check of it happened: a later update that lists it (on any ref) verifies it then, so junk pushed to an uncovered branch cannot fix a status on a commit an allowed signer later lands on `main`. For the resolving update it is judged `not_checked` (non-compliant on a covered ref, problem `<oid> was not checked: <detail>`), listed in `ref.signatures.checked` with that status and detail, and written to `update_objects` with its detail, so an owner's re-check can retry it.
    
    Together these bound one attempt to at most 90 seconds and about 64 outbound requests (16 new DIDs, each one DID-document fetch, one `getRecord` per host before the host fails fast, and one refresh and retry), and one update to 64 signer DIDs over its life, whatever its 1000 objects name. A legitimate update of 1000 commits by a few signers needs a few DID resolutions and 1000 `getRecord` calls at 8 in flight, which fits one or two attempts; when it does not, its progress is kept and the next attempt continues at once;
  - *After an attempt.* An attempt that stored progress or carried objects and had no failures sets `next_at` to now (without increasing `attempts`), so a long update continues in the same run when its priority and the run's budget allow. An attempt with any transient failure takes the backoff above, and its carried objects wait with it;
  - **Giving up.** The attempt that reaches its update's window (one hour, or seven days when waiting on its signers, above), and an attempt that finds `new` no longer served (*Reading objects*), resolve the update instead of leaving it queued, in one transaction like step 6 (*Store*):
    1. Every object to judge whose check completed in this attempt (a final status of `verified`, `unsigned`, `bad_signature`, `signer_inactive`, `unsupported_format` or `not_checked`) is stored as it is. Each object whose check is still failing is stored as `unverifiable`, with `last_error` as its `detail`. Objects still carried or deferred (*Bounded attempts*) are not stored; they are judged `not_checked` for this update with their detail (`not reached before the check gave up`, or the cap's). Objects that already had a row keep it and are judged as reused results.
    2. If no walk succeeded (the Git host failed on every attempt, or `new` is no longer served), `listed` is unknown, so the objects to judge are the tip alone: `new`, and the annotated tag when `new` names one. A tip with no row is stored as `unverifiable`. A tip that already has a row keeps it, but the update is still non-compliant on a covered ref, because the commits it adds were never listed; its problem is `<new> is unverifiable`.
    3. The update is then judged under D11 (*Compliance*), so on a ref its copied rule covers it is non-compliant. The transaction upserts `update_signing` (with the check row's `old` and copied `rule`), writes `update_objects` rows for the update's `unverifiable` objects and its `not_checked` objects that were carried or deferred, with their detail (always the tip when no walk succeeded), upserts `ref_signing` under the `seq` guard, appends `ref.signatures.checked` and, when the copied rule covers the ref, `ref.signature.violation`.
    4. It deletes the `signature_checks` row. When this is the head update, the hand-off runs `reconcile` as for any resolved head update, which refuses its configuration with `signing: <oid> is unverifiable` (D11).

    An owner's re-check of such a tip (*Statuses are final*) re-queues the update, and its next attempt walks `old..new` in full, as the first attempt would have. Results that reached a final status in an earlier attempt are already stored (*Bounded attempts*, *Progress is kept*), so a retry proves only what is still failing or carried.
  - `Repo::on_start` calls `ensure_verify_at(min next_at)` if any row is queued, through the same validated helper (a stored id whose event Rivet no longer holds is cleared), so a schedule lost to a crash is recovered on the next start and a surviving one is not duplicated.
- **Per-update results.** Each judged update writes its own row in `update_signing`, keyed `(seq, ref_name)`, with its `new`, its compliance and its violation. `ref_signing` (the ref's current state, read by `signatures?ref=`, badges and the non-compliance banner) carries the `seq` of the update it describes and is upserted only when the new row's `seq` is at least the stored one. A late result for an older update therefore fills in its own `update_signing` row but never overwrites the result of a newer update.
- **The head update.** `config_head` always holds the `new` of the latest `main` update (`RecordRefEvents`, `crates/tartan-forge/src/actors/repo.rs`), so the *head update* is the `refs/heads/main` update with the greatest `seq`. The configuration gate and the hand-off concern only that update.
- **Hand-off to reconciliation.** When `verify_later` resolves the head update's `signature_checks` row (judged, or by giving up), whatever older `main` rows are still queued, it calls `reconcile` once inside the same `verify` action and, only if that returns `Later`, `reconcile_later`. So the final decision for `main` happens inside a scheduled wake. `reconcile_later` itself still runs in `wait_until`, which does not survive sleep; that is existing behaviour, and `Repo::on_start` recovers it by resuming any unapplied head. `Repo::on_start` schedules `verify` before resuming `reconcile_later`. See D11, *Configuration gating*.
- **Pending is visible.** While a row is queued, `GET …/commits/{sha}/signature` for its `new` answers `{status: "pending", attempts, next_at, last_error, did}` (`did` is the signer the check waits on, when the signature parsed), and so does `GET …/signatures?ref=` while the ref's latest update is queued (an older queued update does not hide the latest result). An oid that is not stored but has a deferred `update_objects` row (*Bounded attempts*) answers `{status: "not_checked", detail}`. A 404 is only for an oid that is neither stored, queued nor deferred. Objects below `new` in a queued update also answer `pending` once the walk has listed them; before that they answer 404.

**Two sets per update.** Each queued update keeps two sets apart:
- *Objects to judge*: always the commit `new` resolves to (the tip), plus the annotated tag if `new` is one, plus every commit in `old..new` (a walk from `new` hiding only `old`), newest first, up to 1000. The tip is included even when `old..new` is empty, so a rewind of a ref to an ancestor is judged on that ancestor. When `old` is zero (a new ref), nothing is hidden, so the walk covers the ref's history up to the same 1000-commit bound. A walk that stops at the bound sets `truncated`, and the commits beyond it are `not_checked`.
- *Objects to verify*: the objects to judge that have no row in `object_signatures` yet, the tip included. Objects already verified for another ref are not verified again, but they are still judged, with their stored result, against this ref's rule.
- *Reused results*: the objects to judge that already had a row when this check started.
- **Standing.** Every `verified` result counts toward compliance only while it is still *standing* when this update is judged (D11, *Compliance*): its record's `signature_records` row is not revoked (D7, *Watching records*), and the DID's status is not inactive (D10). This applies to reused results and to results verified by this check alike, because revocation lives in the forge-wide identity actor while `object_signatures` is per repository: a record revoked on this forge and then re-created with the same CID by whoever holds the create permission proves again, so a commit pushed to another repository would otherwise verify afresh and count. The check asks the identity actor once per update with `SignerStanding{pairs: [{did, rkey}]}` (D3) for every `verified` result it judges, which reads `signature_records` and `people.status` and fetches nothing. Re-proving each reused record instead was rejected: it would put network fetches and transient failures into every fast-forward. A result that is not standing makes the update non-compliant; its `object_signatures` row is stored or left as `verified`, so history is not rewritten, and reads annotate it (*Annotations*).

**Reading objects.**
- `GitHost` gains `read_new_objects(owner, repo, new, hidden: &[oid], limit, skip: &dyn Fn(oid) -> bool) -> Walk{listed: Vec<(oid, kind)>, raw: Vec<RawObject{oid, kind, bytes}>, truncated}`. `listed` is the set to judge; `raw` holds bytes only for listed oids that `skip` does not exclude (those already in `object_signatures`).
- The walgit implementation fetches `new` over smart HTTP with the Git host token, using gix, into a bare cache repository at `TARTAN_STATE_DIR/git/<owner>/<repo>.git` (the Git host's own path, which is what `GitHost` is given). walgit serves a `want` of any commit or tag it holds, not only ref tips, under protocol v2 and v0 (checked against walgit with `git fetch <oid>`), so each object is fetched by id as `<oid>:refs/tartan/fetched/<oid>`. The token reaches gix as a per-fetch `http.extraHeader` (or a credential helper in memory); it is never written into the cache repository's config.
- It walks from `new` hiding only `old`, newest first, up to 1000 commits. `listed` always contains the tip commit (and the annotated tag `new` names, if any), even when the walk yields nothing because `new` is an ancestor of `old`.
- If walgit no longer serves `new` (the ref was force-pushed again before the check ran and `new` is unreachable from every tip), the fetch fails. walgit sends `not our ref`, but gix 0.90 reports only that it could not decode the reply, so after a failed fetch the walgit implementation asks `GET /{owner}/{repo}/api/resolve/{oid}`: a 404 there means the object is no longer served, and any other answer leaves the failure transient. That is not transient: the check gives up at once (*Durable retries*, *Giving up*) with `last_error` `object <oid> is no longer on the host`, rather than retrying for an hour.
- The cache is a disposable optimisation. It is pruned by least-recently-used repository above 2 GiB and rebuilt on demand.
- `GitHost` also gains `is_ancestor(owner, repo, ancestor, head) -> bool`, the walk in the cache repository that D11 *The rule changes only through descent* uses; the walgit implementation fetches `head` first if the cache lacks it.
- `FakeGitHost` stores raw objects per repository, with their parents, so `is_ancestor` works on it.

**Repo actor schema:**

```sql
CREATE TABLE IF NOT EXISTS signature_checks (
  seq INTEGER NOT NULL, ref_name TEXT NOT NULL, old TEXT, new TEXT NOT NULL,
  rule TEXT,                                          -- the signing rule in force at enqueue
  attempts INTEGER NOT NULL DEFAULT 0, next_at INTEGER NOT NULL,
  last_error TEXT,                                    -- last failed attempt's reason, no secrets
  fetched_dids TEXT NOT NULL DEFAULT '[]',            -- signer DIDs this update has fetched for, at most 64
  PRIMARY KEY (seq, ref_name));
CREATE TABLE IF NOT EXISTS object_signatures (
  oid TEXT PRIMARY KEY, kind TEXT NOT NULL,          -- commit | tag
  status TEXT NOT NULL, did TEXT,
  rkey TEXT, record_cid TEXT, record_rev TEXT,         -- the academy.rawkode.tartan.signature record and the revision that proved it
  proof_sha256 TEXT, detail TEXT,
  committed_at INTEGER, checked_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS update_signing (
  seq INTEGER NOT NULL, ref_name TEXT NOT NULL, old TEXT, new TEXT NOT NULL,
  rule TEXT,                                          -- copied from the signature_checks row, for re-checks
  compliant INTEGER NOT NULL, problem TEXT,          -- e.g. "<oid> is unsigned"
  checked_at INTEGER NOT NULL, PRIMARY KEY (seq, ref_name));
CREATE TABLE IF NOT EXISTS update_objects (         -- each judged update's re-checkable objects
  seq INTEGER NOT NULL, ref_name TEXT NOT NULL, oid TEXT NOT NULL,
  deferred TEXT,                                      -- NULL: an unverifiable row; else why it was not checked
  PRIMARY KEY (seq, ref_name, oid));
CREATE INDEX IF NOT EXISTS update_objects_by_oid ON update_objects (oid);
CREATE TABLE IF NOT EXISTS ref_signing (            -- upserted only when excluded.seq >= ref_signing.seq
  ref_name TEXT PRIMARY KEY, seq INTEGER NOT NULL, head TEXT NOT NULL, compliant INTEGER NOT NULL,
  violation_seq INTEGER, checked_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS verify_schedule (
  id INTEGER PRIMARY KEY CHECK (id = 1), event_id TEXT NOT NULL, at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS signing_rule (
  id INTEGER PRIMARY KEY CHECK (id = 1), rule TEXT NOT NULL, config_commit TEXT NOT NULL);
```

`signing_rule` is written in the same transaction as `config.applied`. That transaction lives in `installations::reconcile` (`crates/tartan-forge/src/actors/installations.rs`), so `Repo::reconcile` passes the parsed rule into it. A configuration without `signing`, or an empty root (`Config::default()`), deletes the row, so removing the rule takes effect. A configuration that changes the rule (removing it included) is applied only from a descendant of `config_commit`; otherwise it is refused before this transaction runs (D11, *The rule changes only through descent*). `config_commit` is rewritten only when the rule changes.

**Per object:**
1. **Extract.**
   - For a commit: find the `gpgsig` header (`gpgsig-sha256` for SHA-256 repositories). `tartan-atproto` parses the headers by hand, following Git's `parse_buffer_signed_by_header`, because `gix-object`'s `CommitRefIter::signature` returns only the first `gpgsig` header and knows nothing of the other algorithm's header. The signed data is the object without that header, exactly the bytes Git gave `tt` to sign.
   - For an annotated tag: split at the last line that starts with any signature marker git knows (`-----BEGIN PGP SIGNATURE-----`, `-----BEGIN PGP MESSAGE-----`, `-----BEGIN SIGNED MESSAGE-----` for X.509, or `-----BEGIN SSH SIGNATURE-----`), as git's `parse_signed_buffer` does, which we do by hand because `gix-object` splits only PGP. A tag message that quotes a marker line is still parsed correctly. A tag that carries a `gpgsig` or `gpgsig-sha256` header is handled as Git handles it: newer Git writes that header in a tag only for the *other* hash algorithm of a repository with `compatObjectFormat` (`do_sign` in `builtin/tag.c`), and Git's `parse_signature` removes it from the signed data (`remove_signature`) and never treats it as the tag's own signature, so the signature is still the in-body block and a tag that carries only a header is `unsigned`. Fixtures cover both forms.
   - A commit that carries both `gpgsig` and `gpgsig-sha256` follows git's rule: the header for the repository's hash algorithm is the signature, and both headers are removed from the signed data. A fixture covers this.
   - No signature means `unsigned`. PGP, SSH, or X.509 armour whose second line is not `Tartan-Signature: ` means `unsupported_format`. More than one `gpgsig` (or `gpgsig-sha256`) header is `bad_signature`.
   - `read_new_objects` recomputes each object's oid from its bytes with collision-detecting SHA-1 (gix 0.90's `sha1` feature enables gix-hash 0.28's `sha1` feature, whose hasher is the `sha1dc` crate, the Stevens–Shumow detection Git uses; its `try_finalize` fails on a detected collision) and refuses a mismatch or a detected collision, so a SHAttered-style pair cannot have a signature on one object judged against the other.
   - A tag `new` names is peeled through nested tags; each tag on the way is an object to judge. If the peeled object is not a commit (a tree or blob), the update's tip is `not_checked`, which is never compliant on a covered ref.
2. **Parse** the Tartan signature strictly (D7, *The signature Git stores*): the version, the DID (`did:plc` or hostname-only `did:web`; `did:web` with a port only under dev-identity), the collection `academy.rawkode.tartan.signature`, a TID record key, the CID and the 32-byte salt. Any violation is `bad_signature` with a detail naming the rule. Compute `HMAC-SHA256(key = salt, message = signed data)`, and `sha256(signed data)` for the proof bundle.
3. **Know the signer.** The DID comes from the signature itself, so there is no lookup and no ambiguity: whoever's repository holds the record is the signer. The DID is passed to `KnowDid(did, "signer")` only after the result is `verified` (step 6), within the caps of D3.
4. **Resolve** the DID with evidence (D9). An inactive verified status (D10, *Account status*) means `signer_inactive`, with the status as detail.
5. **Prove** (`tartan-atproto::prove_record`), reusing a bundle fetched at most 10 minutes earlier for the same record. `ReproveSignature` never uses this cache (D7, *Watching records*). The cache is in memory in each process that runs Repo actors (`tartan_forge::proof_cache`, shared with the identity actor and the Jetstream task in the same process), so dropping an entry from another process (below) is best effort; correctness never rests on the drop but on *Confirming before revoking* (a fresh `getRecord` with fresh identity evidence) and on `SignerStanding`. The reuse cache for a DID is dropped when an identity or account event arrives for it, and whenever `RefreshIdentity` finds a changed `#atproto` key or PDS for it, whatever triggered the refresh; a record's cached bundle is dropped when a Jetstream `delete` or `update` arrives for that `(did, rkey)`. A result that would revoke a tracked row (steps 5.4 and 5.5) is first confirmed with fresh evidence (D7, *Confirming before revoking*):
   1. `GET {pds}/xrpc/com.atproto.sync.getRecord?did&collection=academy.rawkode.tartan.signature&rkey`, at most 1 MiB. The reference PDS answers a missing record with 200 and a CAR proving that it does not exist (the signed commit and the MST path without a leaf; `packages/pds/src/api/com/atproto/sync/getRecord.ts` streams `repo.getRecords` and never sends `RecordNotFound`), which step 5.4 handles. A `RecordNotFound` error, which other PDSes may send, is taken as the same signal. `RepoDeactivated`, `RepoTakendown`, `RepoSuspended` and `RepoNotFound` (the account may have migrated or been deleted; it is not a missing record) trigger `RefreshIdentity`; if the status it verifies is inactive the result is `signer_inactive`, otherwise the attempt is a transient failure.
   2. Parse the CAR. Recompute every block's sha2-256 multihash and reject on any mismatch. Allow only CIDv1 with dag-cbor (0x71) or raw codecs. Cap the CAR at 2000 blocks.
   3. Decode the root commit. Require `version == 3`, `did == DID`, and a `rev` not more than 5 minutes in the future. Verify `sig` over the DAG-CBOR of the commit without `sig`, using atrium-crypto with the DID's `#atproto` key. This enforces low-S.
   4. Get the record CID from the signed MST: `jacquard_repo::Mst::load(Arc::new(MemoryBlockStore::new_from_blocks(blocks)), commit.data, None).get("academy.rawkode.tartan.signature/<rkey>")`. Then call `jacquard_repo::commit::proof::verify_proofs(car, [RecordClaim{collection, rkey, cid: Some(cid)}], did, key)` and require the claim in `verified`. Neither call takes depth or fan-out caps; the 2000-block and 1 MiB CAR caps bound the work, since content addressing rules out cycles. `verify_proofs` is async and parses the CAR again internally, so each CAR is parsed twice; with the caps above that is acceptable, and the pre-pass of step 5.2 must stay, because it is the only place every block is re-hashed.
      - **Absent record.** If `Mst::get` returns `None` and every block on the MST path from `commit.data` to where the key would sit is present, call `verify_proofs` with `RecordClaim{collection, rkey, cid: None}` (jacquard-repo 0.12.2 documents `cid: None` as "claiming record does not exist") and require that claim in `verified`. This is a signed proof that the repository does not hold the record *now*; see *A missing record is not final* below. If a block on the path is missing, the proof is incomplete: a transient failure, without the identity refresh.
   5. Require the record block's re-hashed CID to equal the MST's CID, and the MST's CID to equal the signature's `CID`. A proved record with another CID was replaced after signing: once confirmed with fresh evidence (D7, *Confirming before revoking*), it is `bad_signature` with the detail `record … was replaced`, and the stored row in `signature_records`, if any, is marked revoked; an unconfirmed one is a transient failure.
   6. Decode the record strictly (field types; unknown fields ignored, as Lexicon evolution allows) and require `$type` `academy.rawkode.tartan.signature`, `namespace` `git`, `algorithm` `hmac-sha256` and a 32-byte `digest` equal, compared in constant time, to the keyed digest from step 2. Any mismatch is `bad_signature`: the record is proved, so the mismatch is conclusive.

   **When the proof does not verify.** A failed proof is not conclusive on its own, because stale identity evidence makes a valid record look invalid: right after an `#atproto` key rotation or an account migration, the reuse cache, or a PLC directory that lags the PDS's re-signed commit, gives the wrong key. The ATProto sync specification asks for the same handling: "If the signature initially fails to verify, the service should refresh the identity metadata in case it had recently changed. Events with conclusively invalid signatures should be rejected." So:
   - If step 5.3 (the commit's `version`, `did`, `rev` or `sig`) or step 5.4 (a `verify_proofs` claim, for presence or absence, that is not in `verified`) fails, the forge drops the reuse cache for that DID, runs `RefreshIdentity{did}`, which re-resolves the DID evidence with no cache and updates the stored key, PDS and status, and retries steps 5.1 to 5.6 once in the same attempt with that fresh evidence.
   - If the retry fails at step 5.2, 5.3 or 5.4 again, the attempt is a transient failure (*Durable retries*). `last_error` is a short reason such as `proof from pds.example did not verify against did:plc:…'s #atproto key`. The row is retried with the normal backoff and becomes `unverifiable` after one hour (a proof that does not verify never counts as waiting on the signer), which the signer or an owner can re-check. It is never stored as `bad_signature`. A CAR that fails step 5.2 (a block hash mismatch, a disallowed codec, too many blocks), or a record block that fails its re-hash, is the same kind of transient failure without the identity refresh: the PDS answered inconsistently.
   - `bad_signature` comes only from steps 1, 2, 5.5 and 5.6: a malformed or multiple signature, or a proved record that does not sign these bytes. No identity data can change steps 1, 2 and 5.6; step 5.5's other CID is confirmed with fresh identity evidence before it counts (D7, *Confirming before revoking*).

   **A missing record is not final.** A proved absence (step 5.4) or a `RecordNotFound` answer is a transient failure with `last_error` `signature record at://… not found at pds.example`, retried without the identity refresh, and so is a signer's PDS that cannot be reached. The record may still be in the signer's local queue (D7, *Offline and rate limits*), and a commit pushed from a train must verify once its author is back online, even when that is the next morning and nobody flushed before pushing. Such an update, on a ref its copied rule covers and for a signer that rule allows, keeps waiting for up to seven days (*Durable retries*; one hour otherwise), checked at least hourly, so a record published within that window verifies with no owner or signer action, and a `main` configuration waiting on it is applied then (D11). When the check gives up after seven days, the object is stored `unverifiable` with that detail, and the signer (`tt sign recheck`, the `self` class of D4) or an owner re-checks it once the record is published. A record that was deleted on purpose therefore never verifies: it spends up to seven days `pending` and ends `unverifiable`, which is non-compliant on a covered ref (D11); a `main` configuration signed by it waits that long and is then refused, and an owner who does not want to wait pushes a commit signed again.
   - *Rejected: an awaited-records table in the identity actor,* re-checking when Jetstream reports the record's create or the signer calls the refresh route. It recovers faster than an hourly retry, but adds a forge-wide table, makes Jetstream creates matter, and has `tt` call the forge for every record it publishes; a seven-day window with hourly retries reaches the same result with the queue the Repo actor already has. When the record already has a `signature_records` row (it verified the same object before, in this or another repository; a fresh salt per signature means two different signatures never share a record), the proved absence also marks that row revoked, once confirmed with fresh evidence (D7, *Confirming before revoking*).
6. **Store.**
   - Write the bundle to the object store at `proofs/sha256/<hex>.json`, beside the bucket's existing `registry/` and `packages/` prefixes. It is content-addressed and immutable; an existing object is not rewritten. The Repo actor reaches the store, the `tartan-atproto` verifying resolver and fetch-safe client, and `TARTAN_STATE_DIR` through `tartan_forge::Services` (`crates/tartan-forge/src/services.rs`), which today holds only `forge_id`, `git_host` and `extensions`. It gains the `Arc<dyn ObjectStore>` that `crates/tartan/src/main.rs` already builds (`PrefixStore::new(object_store, "tartan")`, so `proofs/` sits beside `registry/` and `packages/`), the resolver and client, and the state directory, and every placement pool's process receives them through `install_services`.
   - Upsert `object_signatures` for the objects verified, judge the update (D11, *Compliance*) using the stored result of every object to judge and the standing of every `verified` result (*Standing*), upsert its `update_signing` row (with the check row's `old` and copied `rule`), replace that update's `update_objects` rows with one row per judged object whose stored result is `unverifiable`, one row with its detail in `deferred` per object judged `not_checked` because it was deferred or still carried (*Bounded attempts*), plus the tip when the update gave up without a walk (*Giving up*), upsert `ref_signing` under the `seq` guard, append `ref.signatures.checked` (listing every judged object), and if the rule is broken, `ref.signature.violation`.
   - Delete the `signature_checks` row, all in one transaction.
   - After the transaction, call the identity actor's `RecordSignature{did, rkey, cid, rev}` for each newly `verified` object, so its record is watched (D7, *Watching records*) and its DID known. It is idempotent, and `on_start` replays it for verified rows whose record has no `signature_records` row, so a crash between the two actors loses nothing.
   - `update_objects` holds only `unverifiable` objects and objects the bounds left unchecked, because only they can be re-checked (*Statuses are final*): any other result is final, so a row for it would never be read. Storage therefore grows with those objects, not with history length, although a new ref lists up to 1000 ancestors.

**Proof bundle (`tartan.signature-proof/2`, JSON, bytes base64):**

```json
{
  "format": "tartan.signature-proof/2",
  "object": { "oid": "…", "kind": "commit", "payload_sha256": "…", "salt": "<32 bytes>" },
  "did": "did:plc:…",
  "identity": { "method": "plc", "audit_log": "<bytes as fetched>", "operation_cid": "bafyrei…" },
  "atproto_key": "did:key:zQ3s…",
  "record": { "collection": "academy.rawkode.tartan.signature", "rkey": "3l…", "cid": "bafyrei…" },
  "repo_commit": { "cid": "bafyrei…", "rev": "3l…" },
  "car": "<getRecord response bytes>",
  "fetched_at": "2026-11-09T12:00:00Z"
}
```

For did:web, `identity` is `{ "method": "web", "url": "https://host/.well-known/did.json", "document": "<bytes>" }`. The trust root there is the TLS fetch at `fetched_at`, so did:web evidence is a record of what was fetched, not an offline proof. `repo_commit.rev` is a TID, so the bundle also shows that the signer's own signed repository held the record no later than that revision's time: evidence of when the signature existed, which `createdAt` (written by the signer's clock) is not.

The bundle stores the salt so that the audit is self-contained; it is served only to the repository's readers (below), who can read the object and its salt anyway. An auditor holding the object checks, offline, that `sha256(object without signature)` is `payload_sha256`, that the object's `Salt` line is the bundle's `salt`, that `HMAC-SHA256(salt, object without signature)` is the record's `digest`, that the CAR proves the record under the commit signed by `atproto_key`, and, for did:plc, that the audit log yields that key.

The proof download route serves only digests referenced by that repository's `object_signatures`.

**Statuses are final.** The only exception is `unverifiable`, which an owner, or the signer whose DID is stored on that result, can re-queue with `POST …/commits/{sha}/signature/recheck` (`tt sign recheck <commit> --repo <org>/<repo>` calls it). The route accepts an oid that has an `update_objects` row, which by construction is an `unverifiable` object, an object the bounds left unchecked (*Bounded attempts*; it has no stored DID, so only an owner can re-check it), or the tip of an update that gave up without a walk; any other oid answers 409 to an owner and 404 to a signer (D4, the `self` class, rate-limited), and a tip with no stored DID can be re-checked only by an owner. A signer's re-check runs exactly the transaction below, so it can make an update compliant only by proving what an owner's re-check would prove. The re-check runs in one transaction:
1. Find every update that judged the object: the `update_objects` rows with that `oid` (through `update_objects_by_oid`). If there are none, nothing changes and the route answers 409.
2. Delete the `unverifiable` rows in `object_signatures` of every object those updates list in `update_objects` (deferred objects have none), so the re-queued checks verify them again rather than reuse them, and one re-check retries everything an update gave up on. Add the updates that list any of those objects, and repeat until no update or object is added (the closure over `update_objects`, which holds only unverifiable objects and so stays small).
3. For each of those updates, insert a `signature_checks` row from its `update_signing` row: the same `seq`, `ref_name`, `old`, `new` and copied `rule`, with `attempts` 0, `fetched_dids` empty (fresh signer caps) and `next_at` now. Each update is judged again by the rule it was first judged by, never by the current `signing_rule`, so a re-check cannot judge a push by a rule applied after it. While the rows are queued, the reads answer `pending`.
4. If one of them is the current head update (above), its copied rule covers `refs/heads/main` and its `update_signing` row is not compliant, reset `config_head.applied` to 0: its configuration was refused and may now be applied.
5. After the transaction commits, call `ensure_verify_at(now)`.

When the re-queued rows are judged, step 6 overwrites their `update_signing` rows and replaces their `update_objects` rows, `ref_signing` is upserted under the same `seq` guard (an equal `seq` replaces it), and the hand-off runs `reconcile` when one of them is the head update. The other objects of those updates keep their stored rows and are judged as reused results.

**Annotations are computed on read.** They come from the identity actor (`signature_records.revoked_at`, `people.status`), so history is never rewritten.

**Alternatives for reading objects.**
- *Read walgit's packs from the bucket*: rejected. It depends on walgit's private manifest format.
- *Add `GET /api/object/{sha}?raw` and a range walk to walgit upstream*: the better long-term source. `GitHost::read_new_objects` hides the choice, so swapping later changes one implementation.
- *Shelling out to `git`*: rejected. It adds a runtime tool dependency.

### D9. Resolving DIDs with evidence

**did:plc:**
1. `GET {plc}/{did}/log/audit`, at most 1 MiB and 1000 entries.
2. Consider the non-nullified entries in order. The first must be a genesis operation: `prev` null, type `plc_operation` (or legacy `create`). Check `did == "did:plc:" + base32lower(sha256(dagcbor(signed_op)))[..24]`.
3. For each operation, recompute its CID and require it to equal the entry's `cid`. Require `prev` to equal the previous accepted operation's CID. Verify `sig` (base64url, low-S, p256 or k256) by one of the previous operation's `rotationKeys` (for genesis, its own). As the PLC specification requires, `sig` must be unpadded base64url with zero trailing padding bits; any other encoding of the same bytes is refused, like a high-S signature. The specification does not say whether historical high-S or non-canonical operations are accepted, so the captured real-world logs (task 2.3) are the check that the rule matches the directory.
4. The DID document comes from the last accepted operation:
   - `verificationMethods.atproto` gives the `#atproto` key;
   - the first `at://` entry of `alsoKnownAs` gives the handle claim (compared lowercased);
   - `services.atproto_pds` gives the PDS.
5. A `plc_tombstone` as the last valid operation leaves no document: no key, handle or PDS. The DID's account status is then `deleted` (D10, *Account status*), matching a PDS's `RepoNotFound`.

A legacy `create` genesis (2022-era) is normalised before step 4, as did-method-plc's `normalizeOp` does: its rotation keys are `[recoveryKey, signingKey]`, its `#atproto` key is `signingKey`, its handle is `handle` with `at://` added when absent, and its PDS is `service` with `https://` added when it has no scheme. The DID hash in step 2 is still taken over the original legacy operation's bytes. A captured legacy log is a test fixture.

We accept the directory's choice of fork (nullified entries). That choice is limited to operations signed by legitimate rotation keys within 72 hours, and we keep the whole log in the bundle so an auditor can re-judge it. The production directory is `https://plc.directory`.

**did:web:**
- Only hostname-level did:web is accepted, as ATProto requires: a DID with a path (`did:web:host:path`) is refused, and a port (`%3A`) is accepted only for `localhost` under dev-identity, matching the `#DID` type (D14).
- `GET https://{host}/.well-known/did.json`, at most 64 KiB, with `id == did`.
- The PDS is the service with id `#atproto_pds` and type `AtprotoPersonalDataServer`, and the signing key is the verification method with id `#atproto` and type `Multikey`, as the ATProto DID specification requires; a document whose `#atproto_pds` service has another type has no PDS.
- Legacy `EcdsaSecp256r1VerificationKey2019` / `EcdsaSecp256k1VerificationKey2019` methods with uncompressed multibase keys are accepted, as ATProto still asks of resolvers. atrium-crypto's `parse_multikey` needs a multicodec prefix, so `tartan-atproto` decodes these forms itself.

**Handles.** `tartan-atproto` resolves DNS TXT and HTTPS in parallel, prefers DNS, and fails on conflicting TXT records (TXT records naming more than one DID). jacquard-identity 0.12.2 cannot do this: its `resolve_handle` tries the steps one after another, takes the first `did=` TXT value without looking for a conflict, and builds its own hickory resolver, which tests cannot replace; so the resolution is written in `tartan-atproto` over a `TxtResolver` trait (hickory in production, a table in tests) and the fetch-safe client, and the verifying resolver answers jacquard's `IdentityResolver::resolve_handle` only for a handle verified in both directions. A handle is accepted only when it matches the document's first `at://` `alsoKnownAs` entry, case-insensitively. DNS TXT lookups go through hickory-resolver (a direct dependency of `tartan-atproto`, at the release jacquard-identity's `dns` feature already uses), not the fetch-safe HTTP client: it uses the system nameservers, and under dev-identity handles resolve only through `TARTAN_DEV_HANDLE_RESOLVER` with no DNS query, so a test asserting that nothing leaves localhost covers handle resolution too.

**Caching and display.** Handles are cached in `people`. `GET /-/api/people` answers from this cache only and never waits on the network:
- a stale handle (older than 24 hours) is still answered, and a background re-verification is scheduled (at most one in flight per DID);
- a transient failure (DNS, PDS or directory unreachable, a timeout) keeps the last verified handle;
- only an affirmative mismatch (the handle no longer resolves to the DID, or the document's `alsoKnownAs` names another handle) makes it `handle.invalid`;
- a DID with no verified handle yet is answered as `{handle: null}`, and a lookup is scheduled; the UI shows a shortened DID such as `did:plc:abcd…wxyz` until the handle resolves.

Sign-in uses a handle at most 10 minutes old, and identity events re-verify at once.

**Fetch safety.** All outbound identity HTTP, including every jacquard-identity and jacquard-oauth fetch (PAR, token, revocation) and every `getRecord` and `getRepoStatus`, uses one reqwest client. `tt` uses the same client from `tartan-atproto` for resolution, local verification, its OAuth flow and its record writes, so a hostile DID document cannot point either at a private address:
- built with `.no_proxy()`, so `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` never move resolution elsewhere;
- before every request and every redirect hop, the URL host is checked: an IP literal must pass the public-address predicate. This is needed because hyper-util's `HttpConnector` connects to an IP literal without calling the custom resolver (`hyper-util` 0.1.21, `client/legacy/connect/http.rs`);
- a DNS resolver that applies the same predicate to every resolved address;
- the predicate refuses loopback, RFC 1918, link-local (including 169.254.169.254), CGNAT (100.64.0.0/10), ULA, multicast, unspecified (`0.0.0.0`, `::`), broadcast, IPv4-mapped and IPv4-compatible IPv6 (judged by their embedded IPv4 address), NAT64 `64:ff9b::/96`, and the documentation and benchmarking ranges;
- `https` only. Under dev-identity (D12) the override also allows `http` and private addresses, and nothing else changes; unit tests cover both modes. `tt`'s loopback callback listener is a server, not a fetch, and is unaffected;
- redirects followed only for handle-resolution and did:web `GET`s; PAR, token, revocation and `tt`'s `applyWrites` and `deleteRecord` never follow a redirect, because a 307 would resend the client assertion or the DPoP-bound body to another host;
- a 10-second timeout per request, and, inside a signature check, the attempt's deadline, per-run host fail-fast, concurrency and signer caps (D8, *Bounded attempts*), so the hosts a pusher names cannot hold a check for longer than one attempt;
- under dev-identity only, the DNS resolver answers every name under `localhost.` with 127.0.0.1 itself (RFC 6761 §6.3), so the devnet can serve many distinct did:web hosts from one listener; a release build refuses those names as loopback;
- body caps enforced while streaming.

### D10. Jetstream as a trigger only

Each gateway process runs a task that:
- connects to `TARTAN_JETSTREAM_URL` (default `wss://jetstream2.us-east.bsky.network/subscribe`; empty disables it; under dev-identity there is no default, see D12);
- on reconnect, rewinds the stored cursor by 5 seconds, as Jetstream recommends (refreshes are idempotent);
- connects to the legacy v1 `/subscribe` endpoint with `wantedCollections=academy.rawkode.tartan.signature&requireHello=true`, and then sends the filter as an `options_update` message, never with the DIDs in the URL (10,000 DIDs would not fit in a query string);
- **every `options_update` carries the whole filter**: `wantedCollections` `[academy.rawkode.tartan.signature]` together with the full `wantedDids` list. The first update after connecting does this, and so does every later change to the DID set. Jetstream's v1 `/subscribe` replaces the connection's whole filter atomically on each `options_update` (bluesky-social/jetstream `internal/subscribe/doc.go`; `filter.go` `ParseUpdatePayload` builds a fresh `Filter`, and an empty list matches everything), so an update without `wantedCollections` would clear the collection filter and deliver every commit by every known DID;
- relies on Jetstream delivering identity and account events whatever `wantedCollections` says, filtered only by `wantedDids` (the Jetstream README: "Regardless of desired collections, all subscribers receive Account and Identity events");
- resumes from the cursor in the identity actor, stored every 1000 events or 10 seconds;
- caps frames and messages at 1 MiB (tokio-tungstenite `max_frame_size` and `max_message_size`, well below the 64 MiB default) and reconnects on a larger one.

**The consumer filters too.** It never relies on the server's filter alone:
- an event for a DID not in `known_as` is ignored, whatever its kind;
- a commit event becomes `ReproveSignature{did, rkey}` (dropping any cached proof bundle for that record first) only when its collection is `academy.rawkode.tartan.signature`, its operation is `delete` or `update`, and `(did, rkey)` has a `signature_records` row that is not revoked (D7, *Watching records*); creates, untracked records and any other collection (a post, a like, a follow) are ignored, so a person signing many commits costs the forge nothing;
- identity events become `RefreshIdentity{did}`, which records `person.handle.changed` and updates the `#atproto` key and PDS (an account migration moves the records with the repository, so nothing else is refreshed);
- account events also become `RefreshIdentity{did}`, with no payload: the event's `active` and `status` fields are never read or stored.

This client-side filter is also what keeps the unfiltered fallback below safe: without it, every identity or account event on the network would become `RefreshIdentity`.

**Account status.** `RefreshIdentity{did}` learns status only from authoritative fetches through the fetch-safe client:
1. the DID's evidence (D9): a `plc_tombstone` as the last valid operation of the verified PLC log makes the status `deleted`;
2. otherwise `GET {pds}/xrpc/com.atproto.sync.getRepoStatus?did=` on the PDS named by the verified DID document. `active: true` is `active`; `active: false` stores its `status` verbatim (`takendown`, `suspended`, `deleted`, `deactivated`, `desynchronized`, `throttled`, or a later value), or `inactive` when absent; a `RepoNotFound` error is `deleted`.

**Inactive** means any stored status other than `active`, `throttled` and `desynchronized`. Those two come from sync 1.1 and describe hosting or relay state, not an action by the account holder, a moderator or the host, so they are kept for display (the person's page shows them as a neutral note) but refuse nothing. `takendown`, `suspended`, `deleted`, `deactivated`, `inactive` and any value this design does not know are inactive, so an unknown future status fails closed.

Only that result is written to `people.status` (and `status_checked_at`), recording `person.status.changed` when it differs. A transport failure or malformed answer keeps the previous status, so an unreachable PDS never locks a person out. Triggers are Jetstream identity and account events, sign-in, the proof-time account errors of D8 step 5.1, and the 6-hourly `Sweep` (D3), which also brings an inactive DID back once its PDS reports it active.

Sessions and tokens of a DID whose verified status is inactive are refused, and a sign-in by it is refused with `account_inactive` (D1, callback step 7) (spec: forge-access), within the 30-second cache window of D4. A forged Jetstream account event therefore costs one `getRepoStatus` fetch and changes nothing.

Sending `wantedDids` tells the Jetstream operator which DIDs use this forge. Operators who mind run their own Jetstream or set `TARTAN_JETSTREAM_URL` empty and rely on the sweep; the configuration docs say so.

Several gateway processes cause duplicate refreshes. These are idempotent and cheap. They also share the one `jetstream` cursor row, so a slower process can move it back, or a faster one past events a slower one has not handled yet. That is safe for the same reason: a replayed event repeats an idempotent refresh, and a skipped one is caught by the 6-hourly sweep. With more than 10,000 known DIDs (Jetstream's limit for `wantedDids`), the task sends `wantedCollections` with an empty `wantedDids`, logs a warning, and relies on its own filter; the 6-hourly sweep covers anything missed. Near the cap an `options_update` is about 320 KB (10,000 DIDs of about 32 bytes). If the server closes the connection or answers with an error after a full update (within 5 seconds of it and before any event arrived), the task falls back the same way (an empty `wantedDids` and its own filter) on the following connections, until the number of watched DIDs changes, and logs a warning; while the forge watches no DID at all it does not connect, since an empty `wantedDids` would ask for every DID; the devnet `/subscribe` accepts updates up to the cap, and a devnet test sends one at 10,000 DIDs.

**Jetstream v2.** Jetstream also serves `/xrpc/network.bsky.jetstream.subscribeEvents` (atproto proposal 0015), which is server-push only, refuses `requireHello` and `options_update`, and takes `dids`, `collections` and `kinds` as query parameters. The forge targets v1 `/subscribe`, because under v2 up to 10,000 DIDs would have to go in the URL. Moving to v2 is a later option.

**Alternatives.**
- *Raw firehose (`subscribeRepos`)*: self-certifying, but there is no server-side filter, so the forge would process the whole network.
- *Tap*: verifies and filters, but adds a Go sidecar.
- Neither is needed, because every trigger is re-verified with a proof anyway.

### D11. The signing rule

The schema is `tartan.rawkode.academy/types@v0.2.0` `#Signing`:

```cue
#Signing: {
	require: [...{
		refs: [_, ...] & [...=~"^refs/[^/ ]+(/[^/ ]+)*$"]
		signers?: [_, ...] & [...#DID]
	}]
}
```

Repositories use it as `signing: types.#Signing & {…}`. `tartan-config::check` parses `signing` next to `extensions`, refuses unknown keys, and also refuses `**` anywhere but as the final segment. `*` matches within one segment, so `refs/heads/release-*` is valid.

**The rule in force** is the `signing_rule` row, written with `config.applied`. A push is always judged by the rule from before it, so a push cannot lift its own rule.

**Coverage.** Whether a ref is covered is decided by the `rule` copied into its queued `signature_checks` row, not by the current `signing_rule` row. The configuration gate uses the row of the head update (D8, *The head update*). `config_head` has no `seq`, so `reconcile` finds it as the `refs/heads/main` row with the greatest `seq` across `signature_checks` and `update_signing` whose `new` equals `config_head.sha`. When there is no such row (a `config_head` left unapplied from before this change was deployed), its copied rule is none, so it is not gated. A deletion of `main` never moves `config_head` (`crates/tartan-forge/src/actors/repo.rs`, `RecordRefEvents`), so deleting `main` alone cannot lift the rule by applying an empty configuration. The recreating push is an ordinary new-ref update, judged on its tip and history; if it lands on a commit whose configuration changes the rule, *The rule changes only through descent* below refuses it.

**Compliance.** A ref is compliant after an update when the update's walk was not truncated and every object to judge (D8, *Two sets per update*) has a stored result that is `verified` and, if the rule lists `signers`, by one of them. A `verified` result, whether reused from an earlier update or verified by this check (D8, *Standing*), counts only if it is still standing when this update is judged: its signature record has not been revoked (D7, *Watching records*), and the DID's status is not inactive (D10). Otherwise the object is non-compliant for this update, with the problem `<oid> signature was revoked` or `<oid> signer's account is not active`; an object the verification bounds left unchecked (D8, *Bounded attempts*) has no stored result and is non-compliant with `<oid> was not checked: <detail>`; which goes into `update_signing.problem` and `ref.signature.violation`. The stored result itself is not changed and still reads `verified` with its annotation. A reused result's signer DID is also checked against this ref's `signers`. So a commit verified on an uncovered branch whose signature is then revoked cannot be fast-forwarded into `main` afterwards: revoking a signature made with a stolen session protects covered refs from every later update, not only from objects checked after the revocation, and it does so in every repository of the forge: a record revoked here and re-created with the same CID by whoever holds the create permission still counts as revoked when the commit is pushed to another repository. The set to judge is never empty, because it always holds the tip: an update is compliant only when its tip, and every commit it adds, is `verified` by an allowed signer. A rewind (the ref moved backwards or was re-pointed at an ancestor, so `old..new` is empty) is therefore judged on the ancestor it lands on. Rewinding `main` to an unsigned commit, such as one from before the rule existed or a configuration commit A that was refused earlier, is a violation, and its configuration is refused with `signing: <oid> is unsigned`. Rewinding to a head an allowed signer verified is compliant while that result still stands, so reverting after a violation keeps working; rewinding to a head whose signature has since been revoked needs a new signed commit on top. Compliance alone does not protect the rule: an allowed signer may have signed commits before the rule existed, or in another project, and those are compliant heads whose configuration has no `signing`. The rule cannot be lifted by rewinding because of *The rule changes only through descent* below, not because of compliance. An update is never compliant merely because its objects were checked elsewhere. So pushing an unsigned commit to an unprotected branch and then fast-forwarding `main` to it is a violation on `main`, and so is a commit verified as a DID allowed on the other branch but absent from `main`'s `signers`.

*Several entries.* A ref is covered when any entry's `refs` matches it; every matching entry that lists `signers` must admit the signer, so the allowed set is the intersection of their `signers` (an entry without `signers` adds no restriction). `**` matches one or more remaining segments.

*A rule without `signers`* is satisfied by any proved DID, and anyone can create an ATProto account for free, so under it `verified` means only "someone signed". This is allowed (a project may only want every commit signed by someone it can name later), but it is stated: signing.mdx says so next to the rule's syntax, and its examples always list `signers`. `tartan-config::check` has no warning channel today, so a lint for such entries is left to a later change.

Compliance is per update, not per history. If an unsigned configuration commit A is refused and an allowed signer then pushes B on top of it, the update `A..B` judges only B (its tip and the only commit it adds), so `main` becomes compliant and B's configuration (which includes A's change) is applied. That is intended: B's signature covers B's whole tree. The rule means "each update to the ref is signed by an allowed signer at its tip and every commit it adds", not "every commit in history is signed".

**Configuration gating.** When the rule covers `refs/heads/main`:
- While the head update's `signature_checks` row exists and its copied rule covers `main`, `reconcile` returns `Reconciled::Done` without applying and leaves `config_head.applied = 0`, unlike the existing `Done` path, which sets it to 1 (`crates/tartan-forge/src/actors/repo.rs`). So `on_start` recovery and the hand-off still see the head as unhandled. Rows of older `main` updates do not hold it back. It does not return `Later`, so it does not spend `reconcile_later`'s retry budget (1 s doubling to 64 s, about two minutes, `crates/tartan-forge/src/actors/repo.rs`), which is shorter than `verify_later`'s hour.
- The scheduled `verify` action re-triggers it: when it resolves the head update's row (judged, or by giving up after an hour, after seven days for an update waiting on its signers, or on an object no longer served, D8 *Giving up*), it runs `reconcile` in the same action (D8, *Hand-off*). Resolving an older `main` update's row does not. Because each retry is a Rivet schedule, this happens even when no other request reaches the actor. After a restart, `on_start` schedules `verify` first.
- Once the head update's row is resolved, `reconcile` reads that update's own `update_signing` row (matching `seq` and `new`), never the ref's latest `ref_signing` row, and if it is not compliant records `config.refused` with the problem `signing: <oid> is <status>`. A head update that gave up is always resolved this way: its `update_signing` row exists and is not compliant, so its configuration is refused with `signing: <oid> is unverifiable`, and an owner's re-check reopens it (D8, *Statuses are final*, step 4). Example: update W (`old..W`) waits on a PDS that is down, and update X (`W..X`) by another signer is then pushed and verified. X's configuration is applied or refused on X's update alone, at once, and the badge shows X; when W later resolves, it fills in W's `update_signing` row only.
- While it waits on the head update, `GET /-/api/orgs/{o}/repos/{r}/config/status` answers `{applied: {commit}|null, pending: {commit, waiting_on: {signature_check: <oid>, attempts, last_error}}|null}`, and the repository page shows "checking signatures…" or "retrying: <last_error>".

**The rule changes only through descent.** Pushes are unattributed (Non-Goals), so the rule is the only protection `main`'s configuration has against people who can push, and compliant updates can still reach a configuration without the rule: a rewind of `main` to a commit an allowed signer signed before the rule existed, a force-push of an unrelated history of signed commits (signatures bind to objects, not to a repository, and the record deliberately names none), or deleting `main` and recreating it at a pre-rule commit. So:
- `signing_rule.config_commit` is the head commit whose configuration last set the rule to its current value: written when a rule is first applied or changed, and left as it is when an applied configuration keeps the same rule.
- When a `signing_rule` row exists and the configuration `reconcile` is about to apply (after the gate above has let it through) has a `signing` value that differs from the row's `rule` (removed, an empty root, `refs/heads/main` no longer covered, `signers` or any other entry changed; compared as the normalised parsed rule that is stored), `reconcile` applies it only if `config_commit` equals the new head or is one of its ancestors. Otherwise it records `config.refused` with `signing: the signing rule can only change in a descendant of <config_commit>`; the rule and the previously applied configuration stay in force, and `config_head.applied` is set as for any refusal.
- The check does not look at `old`, so rewinds, unrelated histories and delete-then-recreate are all covered. A configuration whose `signing` equals the rule in force needs no ancestry check, so reverting to a signed head keeps working for everything else. With no `signing_rule` row, any configuration may set a rule.
- Ancestry is decided by `GitHost::is_ancestor(owner, repo, ancestor, head)` (D8, *Reading objects*): a gix walk in the cache repository from `head`, which `read_new_objects` has already fetched, stopping at `ancestor` or when the history is exhausted (commit-graph generation numbers cut it short where the cache has them). A Git host or cache failure is transient: `reconcile` returns `Later`, and when `reconcile_later`'s retry budget runs out it records `config.refused` with `signing: could not check that <head> descends from <config_commit>`, so the rule stays in force (fail closed).
- A project that really wants `main` on an unrelated history with a different rule makes the change in a signed commit that merges `config_commit` (for example `git merge -s ours <config_commit>`), so the change is made by a descendant. signing.mdx says so.

**Rejected.** *Refusing the push*: walgit has no pre-receive hook and its `policy.json` has no signature rules. An authenticating proxy in front of walgit could do it later, together with per-person push credentials.

### D12. Development and tests: `tartan-devnet`

`crates/tartan-devnet` (AGPL, `publish = false`) is a library and a binary (`tartan-devnet --listen 127.0.0.1:9400 --seed dev`). It serves, from one in-memory process:
- **A PLC directory.** `GET /{did}`, `/{did}/log/audit`, and genuinely signed genesis operations, so D9 runs unchanged. A genesis operation names the handle, the `#atproto` key and the rotation key but no service, so a DID depends only on the seed and the handle, never on the port the devnet listens on; the operation after it adds the PDS endpoint, and every control that changes an identity appends another operation signed by the rotation key.
- **A PDS.**
  - `com.atproto.sync.getRecord` (CARs from a jacquard-repo MST signed with each person's k256 key). For a record that does not exist it answers as the reference PDS does: 200 with a non-existence CAR (the signed commit and the MST path, no leaf). A test switch makes it answer `RecordNotFound` instead, and another drops one block from the path, so both answers and an incomplete proof are tested;
  - `com.atproto.repo.applyWrites` (at most 200 writes, atomic; a plain `create` whose client-chosen `rkey` already exists fails the whole call with 500 `InternalServerError`, exactly as the reference PDS does, so the devnet cannot hide a client that resends a create), `com.atproto.repo.getRecord` (no authorization), `createRecord`, `deleteRecord` and `listRecords`, accepting DPoP-bound tokens it issued and enforcing their granular `repo:` permissions per write, with its own resource-server DPoP nonces;
  - repository write rate limits modelled on the reference PDS's points (create 3, update 2, delete 1), off by default, with a test switch that sets a small budget so a 429 with `ratelimit-reset` is easy to reach;
  - `com.atproto.identity.resolveHandle`;
  - `com.atproto.sync.getRepoStatus`, answering each person's account status, and `RepoDeactivated`/`RepoTakendown` errors from `getRecord` for an inactive repository;
  - `/.well-known/oauth-protected-resource`.
- **An authorization server.**
  - metadata, PAR, PKCE and DPoP nonces;
  - confidential web clients: `private_key_jwt` checked against the client's JWKS fetched over HTTP;
  - public native clients: `token_endpoint_auth_method` `none`, loopback redirect URIs matched without the port (as the reference server does), `refresh_token` grants with single-use rotation, a public-client session lifetime it can be told to shorten, and refusal of a reused refresh token (presenting one also ends the session);
  - the ATProto profile's `http://localhost` development client id: a public client whose metadata comes from the client id's `redirect_uri` and `scope` query parameters, so a development sign-in mode that uses it can be tested;
  - an authorize page that approves at once as the person named by the request's `login_hint`, so following the authorization URL with a plain HTTP client (for example `curl -sL`) completes the redirect to the client's callback; without a hint it lists the seeded people ("Sign in as @bob.test"), and `deny=1` answers `access_denied`;
  - token and revocation endpoints;
  - the granular `repo:` scope, with requested scope tokens checked literally against the client metadata's declared `scope`, as the reference server does, so an undeclared token is refused with `invalid_scope`;
  - test switches to answer PAR or the token request with an OAuth error (`invalid_client`, `invalid_client_metadata`, `invalid_scope`) and to grant a narrower scope than requested;
  - a switch that makes the authorization server's fetch of `tt`'s client metadata fail (as when the forge is down), so every token request, refreshes included, answers `invalid_client_metadata` like the reference server, and a control that shortens access-token lifetime so a refresh happens within a test;
  - a record of each PAR body it received, so tests can assert the exact `scope` sent;
  - for the sign-in failure tests (task 6.3), switches that leave `authorization_response_iss_parameter_supported` out of its metadata and `iss` out of its redirects, that delay `getRepoStatus`, and that take the authorization server or the PLC directory offline separately from the PDS.
- **Jetstream.** A minimal Jetstream-compatible `/subscribe` that emits the devnet's own commits (creates, updates and deletes), identity and account events, so the consumer is tested too. It implements v1's filter semantics, including that each `options_update` replaces the whole filter (an empty list matches everything), and a test control makes a person write a record in an unrelated collection such as `app.bsky.feed.post`, so tests catch an update that drops `wantedCollections`.
- **Test controls.** Test-only endpoints under `/devnet/` write a `academy.rawkode.tartan.signature` record for a person directly (for tests that build signed objects in-process), delete or replace a record, change handles, tombstone DIDs, set a person's account status at the PDS, rotate a person's `#atproto` key with a signed PLC operation while the PDS keeps serving commits signed with the old key for a set number of `getRecord` answers before it re-signs, migrate a person to a second devnet PDS host with a new `#atproto` key (a signed PLC operation, the repository copied, the identity event optionally withheld from Jetstream) while the old host keeps serving its own copy signed with the old key, delete a record from that old copy only, take the PDS offline and back, make the PDS commit a write and then drop the connection without answering (the lost-answer case), revoke every OAuth session a person granted a client (as an account's app-session settings do), and make Jetstream emit an account, identity or delete event whose payload disagrees with the PDS (for example `takendown` while the PDS says active, or the deletion of a record that still exists).
- **Shape.** One origin serves the PLC directory, the handle resolver, the PDS, the authorization server, Jetstream and the controls, so `TARTAN_PLC_URL` and `TARTAN_DEV_HANDLE_RESOLVER` are both the devnet's URL. The second PDS host is a second listener bound at start; both hosts name the one authorization server. A service taken offline closes each connection without answering, as an unreachable host looks to a client. Every control is also a method of `tartan_devnet::Devnet`, for tests that run the devnet in-process.
- **A tarpit.** A control starts a second listener that serves, for `N` distinct hosts `t<i>.localhost:<port>`, a did:web document at `/.well-known/did.json` naming a PDS on that same host, and holds every `/xrpc/` request open without answering. It counts connections and requests per host, so a test can push objects signed as `N` distinct `did:web` signers and assert how many outbound requests one attempt made (D8, *Bounded attempts*; the dev-identity resolver maps `*.localhost` to the listener, D9 *Fetch safety*).

People are derived deterministically from `--seed`, so DIDs are stable. The seed `dev` has exactly the people `demo.sh` uses: `alice.test` (the owner in `dev.sh` and `demo.sh`), and `bob.test`, `carol.test`, `dave.test` and `erin.test` (not owners), so the demo's issues can be assigned to DIDs and the demo can show read-only access and a signature by a signer the rule does not allow next to the owner's. `demo.sh` sets `readers: "signed_in"` so that bob can read; `dev.sh` keeps the private default, so signing in there as anyone but alice shows the private-forge page. `tartan-devnet did <handle>` prints a person's DID (`dev.sh` and `demo.sh` put alice's in `owners`, and `demo.sh` writes DIDs into its issues).

The devnet keeps its state in memory. Seeded people are recreated identically on every start; signature records, handle changes and rotations do not survive a restart. A demo that reuses its state directory therefore shows its earlier commits as `verified` from the stored results, while a re-check after a devnet restart would find their records gone. demo.mdx says so.

**The forge's and `tt`'s dev switches** compile only with feature `dev-identity` (on both `tartan` and `tt`), and act only with `TARTAN_DEV_IDENTITY=1`:
- `TARTAN_PLC_URL`;
- `TARTAN_DEV_HANDLE_RESOLVER` (handles resolve through `com.atproto.identity.resolveHandle` there, since `.test` has no DNS);
- plain HTTP;
- private addresses;
- an HTTP `TARTAN_PUBLIC_URL` with a port (the forge), and an HTTP forge URL serving the CLI client metadata (`tt`).

A release build without the feature refuses to start when the variable is set; a release `tt` refuses to run with it set, with a message that names `TARTAN_DEV_IDENTITY` and says to unset it (running-locally.mdx warns against exporting it from a shell profile or `.envrc`, since the refusal also stops `git commit` and `git log --show-signature` in that shell). `scripts/e2e.sh` builds the test binaries with `--features dev-identity`.

**No public network in dev mode.** With `TARTAN_DEV_IDENTITY=1`:
- `TARTAN_PLC_URL` and `TARTAN_DEV_HANDLE_RESOLVER` are required, by the forge and by `tt`; both refuse to start without them, naming them, instead of falling back to `plc.directory` or public DNS.
- `TARTAN_JETSTREAM_URL` has no default. It must be set (to the devnet's `/subscribe`) or set empty to disable Jetstream; leaving it unset refuses to start. So devnet DIDs are never sent to a public Jetstream as `wantedDids`.
- `dev.sh`, `demo.sh` and the test harness set all of them to the devnet.

**Tests** build signed objects in-process: the test draws a salt, the devnet's control writes the record with the keyed digest for a person, the test builds the six-line signature with the record's URI, CID and salt, writes the object with `git hash-object -w`, and pushes it. End-to-end tests also run the real `tt` binary as `gpg.x509.program` with `git commit -S` and `git verify-commit` against the devnet, with `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` all under the test's temporary directory and `TT_CREDENTIAL_STORE=file`, so a test never reads or writes the developer's `tt` defaults, credentials, queue or verification cache, and two tests never share them. `HOME` is set to the same temporary directory, so a path `tt` derived from `HOME` would also stay inside it.

**The demo's signing story.** `demo.sh` signs alice and bob in to `tt` without a browser: it runs `tt sign --login --handle <h> --no-open --port <p>` in the background, follows the printed URL with `curl -sL` (the devnet authorize page auto-approves for `login_hint`, and its redirect lands on `tt`'s loopback callback), and waits for `tt` to exit. Each person gets their own `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` under the demo's state directory, with `TT_CREDENTIAL_STORE=file`, so the devnet forge (plain HTTP) and devnet DIDs never become the developer's default forge or default signing DID, and the developer's keychain is not touched. Every `tt` and `git` command the demo runs for a person gets that environment. The demo also never writes the developer's Git configuration: it signs with `git -c`, as below. It adds to the demo repository's `tartan.cue` a rule `signing: types.#Signing & {require: [{refs: ["refs/heads/main", "refs/heads/release/*"], signers: [<alice's DID>]}]}`, pushes the configuration commit signed by alice (`git -c gpg.format=x509 -c gpg.x509.program=<the dev-identity tt it built> -c user.signingKey=<alice's DID> commit -S`, never a `tt` found on `PATH`: a release `tt` refuses to run while `TARTAN_DEV_IDENTITY` is set) and waits for `config.applied`. It then pushes a commit signed by bob to `release/1.0`, a covered branch, so `main` stays compliant with its configuration applied, while the repository page shows "Signed by @alice.test" on `main` and a violation banner for `release/1.0` naming @bob.test. The first push is judged by the rule from before it (none), so it applies the rule; bob's push is judged by it. Git 2.19 or later is needed (`gpg.x509.program`), and Git 2.40 or later to see `tt`'s error messages when signing fails; no other signing tool is.

**Time in tests.** The forge reads the time in one place today (`crates/tartan-forge/src/sql.rs`, `now_ms()` over `SystemTime::now()`), and the test harness runs the real Rivet engine, where `ctx.schedule().at(ms)` and `ctx.cron().every` fire on real wall-clock time. Tests of hour-, day- and week-long windows therefore need the forge's own clock to move, and a way to wake the work it would have done. The decision:
- `tartan_forge::Services` gains `clock: Arc<dyn Clock>` with one method, `now_ms()`. Every identity and signing path that compares times reads it, and nothing in them calls `SystemTime::now()`: `signature_checks.next_at` and the backoff, the one-hour and seven-day give-up windows and the hourly retry (D8 *Durable retries*), the `verify_schedule.at` time, the 6-hourly refresh and the 30-day sweeps (D3), session, token and pending-request expiry (D1, D5, D6), the 60-second CLI codes (D16), the outcome records, the proof-reuse window, rate-limit buckets and `revoked_at`/`status_checked_at` stamps. The existing `sql::now_ms()` becomes a call to it.
- The `tartan` binary always installs `SystemClock`. The test harness (`crates/tartan/tests/common`) installs a `TestClock`, wall-clock time plus an offset the test can advance (`clock.advance(Duration)`), through `install_services`, so the actors in its process share it. It is not reachable from a release or `dev-identity` binary, from an environment variable or from any route; `dev.sh` and `demo.sh` run on real time.
- `ensure_verify_at(t)` converts clock time to the real time Rivet schedules on, `t - offset` (always `t` under `SystemClock`), through `tartan_forge::real_time_ms`, which never answers a time before real now, so a schedule whose clock time has already passed after an advance fires at once. A schedule registered before an advance keeps its real time, so after advancing, a test wakes the work explicitly: it calls the Repo actor's `verify` action and the identity actor's `Sweep` action directly, which run exactly what the scheduled wakes run, serialised by the same `verifying` mutex.
- Durations stay as designed (no test-only scaling), so the tests exercise the real windows. That a pending schedule wakes a sleeping actor with no other request is tested on real time with the 5-second first backoff (task 8.2), not with an advanced clock.
- `tt`'s scenarios that span the forge's windows (task 10.8) advance the forge's clock, not the devnet's; the devnet keeps real time, and `tt`'s own two-minute and rate-limit windows are tested with the devnet's 429 switch and real time.

**PLC verifier tests** use the devnet plus a few audit logs captured from plc.directory and committed as testdata. These are public data, and include a log with a rotation and a nullified operation.

**Alternatives.**
- *`@atproto/dev-env` or the Bluesky PDS container*: real implementations, but they need Node or Docker and Postgres-free PLC images that do not exist officially. They remain useful for a manual interoperability check (task 11.3).
- *Mocks at the trait level only*: they would leave OAuth, CAR and PLC parsing untested end to end.

### D13. Owners and the end of the admin token

`Deployment` gains `owners: Vec<Did>`, validated as in the spec, and `readers`, which says who else may read:

```cue
package forge

owners: ["did:plc:abcdefghijklmnopqrstuvwx"]
readers: "owners"          // default: only owners read; everyone else gets a private-forge page
// readers: "signed_in"    // any ATProto account that signs in may read every org and repository
// readers: ["did:plc:…"]  // owners plus these DIDs may read
```

`readers` is optional and defaults to `"owners"`, which keeps an upgraded forge as closed as the admin token kept it. A list must hold distinct valid DIDs, validated like `owners`. Like `owners`, it changes only when the forge restarts with a new configuration, and rights are computed per request from it (D4), so a DID removed from it loses read access within the 30-second cache window. The binary refuses to start in any of these cases:
- `owners` is empty;
- `TARTAN_CONFIG` is unset;
- `TARTAN_ADMIN_TOKEN` is set.

When the identity actor starts, it calls `KnowDid(owner, "owner")` for each owner, so their identity and account status are watched. It reads the owner list from `tartan_forge::Services`, which gains `owners` (from the deployment configuration, alongside the fields task 8.1 adds), because the actor runs in a runner process, not in the gateway. On start it also drops the `owner` tag from DIDs no longer listed, so a removed owner leaves the sweep and `wantedDids` once nothing else keeps it known. Rights are still computed from the in-process deployment configuration (D4), so this is watch-list hygiene, not authorization. At startup the forge logs the read mode in force: `readers: owners` ("only owners can read; other people who sign in see a private-forge page"), `readers: signed_in` ("any ATProto account can sign in and read every org and repository"), or the number of listed reader DIDs.

**Who becomes known.** A sign-in records `person.signed_in` and calls `KnowDid(did, "signed_in")` only for a DID with `read` rights (an owner or a reader). A stranger who signs in to a private forge gets a session (so the web UI can name them and say the forge is private) but leaves no event, no `known_as` entry and no `wantedDids` entry. So on a private forge strangers cannot grow the watch list (Risks, *Signed-in DIDs grow the watch list*).

Operator commands live in `tt admin` (D16):
- `tt admin oauth keygen`: prints a fresh ES256 private JWKS.
- `tt admin token create|list|revoke`. `tt admin token create --did <owner>` needs neither the owner's PDS nor the network, so it is the operator's way in when an owner's PDS is down.

The forge refuses to start when `TARTAN_OAUTH_KEYS_FILE` is readable by group or others (mode broader than 0600), as ssh does with private keys. At startup it logs each owner DID with its resolved handle (or "unresolved"), so a mistyped DID is caught by sight. That resolution, and the identity actor's `KnowDid`/`RefreshIdentity` for owners, run in the background with the 10-second fetch timeout; neither delays nor blocks startup when the PLC directory or a PDS is down.

**Break-glass limit.** `tt admin token create --did <owner>` cannot help when that owner's DID is verified inactive (D10, *Account status*), because tokens of inactive DIDs are refused. The operator must then list a different owner. identity.mdx says so. A forged Jetstream event cannot cause this, since status comes only from the PLC log and the PDS.

**The Rivet engine is an admin boundary.** Anyone who can reach the Rivet engine with `RIVET_TOKEN` can call the identity actor's `CreateToken` and `Authenticate` actions directly (`AdminCreateToken` checks only that the DID is an owner), which is how `tt admin token create` works, so they hold owner rights. deploying.mdx and identity.mdx say the engine endpoint and `RIVET_TOKEN` must stay private and count as admin credentials.

It makes no other `/-/api` call, so it never shows a raw 403.
- **Read-only presentation.** Until membership exists only owners may write (spec: forge-access), so on a forge whose `readers` admits other people, a signed-in reader is the usual visitor. When `rights` holds `read` but lacks `write`:
  - the first-party write controls are hidden or disabled: the New issue button and `IssueNewView`, edits in `IssueView` (title, body, state, properties), Kanban drag and drop and extension `act` buttons, and org and repository creation (`CreateSlugForm` in `OrgsView` and `OrgView`); when `rights` lacks `admin`, org and repository creation is hidden as well;
  - token creation offers only the `read` scope (a token's rights are its scopes intersected with its DID's rights, D4, so `write` or `admin` would be inert);
  - a notice under the header reads "Read-only: only forge owners can make changes until membership exists.";
  - a 403 from a write call (a `tool` or `act` call, or an org or repository creation, including calls the UI could not know in advance) is shown as that same explained message instead of the response body. A 403 is mapped only when `/-/api/me` reports the caller lacks the needed right; any other 403 (such as the CSRF `Origin` mismatch of D4, whose body names the expected origin) keeps the server's text.
- An account menu in the header (handle, owner badge, sign out). A 401 redirects to sign-in. Because anonymous callers get 401 on all of `/-/api`, an anonymous visitor is sent straight to sign-in; there is no public read-only view until membership exists, and identity.mdx and web.mdx say so.
- **Settings** loses the admin-token field and gains:
  - *Access tokens*: create, list, revoke. The `tartan_pat_` secret is shown exactly once, with a copy button and a note that it cannot be retrieved later; the forge stores only its hash (D5).
  - *Signing*: how to sign with `tt`, with the forge URL filled in: install `tt`, `tt login --forge <TARTAN_PUBLIC_URL>`, `tt sign --setup --global` on a personal machine (`tt login` already ran the signing login; what it writes: `gpg.format=x509`, `gpg.x509.program=tt` (or `tt`'s absolute path), `user.signingKey=<their DID>`, `commit.gpgSign=true`, `tag.gpgSign=true`), then, because `--global` cannot install the per-repository `pre-push` hook, `tt sign --setup --hook` in each repository where offline work is pushed (or `tt sign --flush` before pushing), and `tt sign revoke` to withdraw a signature. There is nothing to manage on the forge: no keys are stored or listed.
  - *Sessions*, listing browser and CLI sessions with their device names.
- **CLI approval page** at `/#/-/cli-login` (D16): the device name, the person's handle, Approve and Cancel; a person without a session is sent to sign in and back.
- A `PersonInput` (handle or DID, resolved to a DID, chips show handles) replaces the hard-coded `['admin']` suggestions in `IssueNewView` and `IssueView`. `PersonDisplay` renders the `person` node.
- **Repository overview:** each branch head gets a signature badge ("checking signatures…" or "retrying: <reason>" while pending), a banner names refs that are not compliant, and another says when a `main` configuration waits on a signature check.
- A new **commit signature view** at `/#/:org/:repo/commit/:sha/signature` shows the status, the verified signer separately from the claimed author and committer, the signature record (its `at://` URI and the repository revision that proved it, as "in @alice's repository since <time>"), proof download and annotations (as neutral notes).

### D16. The `tt` command-line interface

`crates/tt` (AGPL-3.0-or-later) builds the `tt` binary, the forge's only command-line interface. It depends on `tartan-atproto` (resolution, the fetch-safe client, record proofs) and, for `tt admin`, on `tartan-identity-api` and `rivetkit-client`; it never links the forge's actors, `tartan-forge` or `tartan-extensions` (and so no wasmtime). The `tartan` binary stays the server and takes no subcommands; given a subcommand, such as `tartan token create`, it exits with an error naming the `tt` command to use.

**Commands.**

| Command | Talks to | Credential | Purpose |
| --- | --- | --- | --- |
| `tt login [--forge <url>] [--set-default] [--no-open] [--port <n>] [--client localhost] [--no-signing]` | forge, then PDS and AS | — | CLI session for the forge (below), then the signing login of *First run* below unless `--no-signing` or a signing session for that DID exists |
| `tt login --with-token [--forge <url>] [--set-default]` | forge | `tartan_pat_` from stdin | act with an access token, for CI and remote machines |
| `tt logout [--forge <url>]` | forge, AS | CLI session, signing session | end the CLI session (`DELETE /-/api/sessions/current`), revoke the signing session, delete local credentials; its help and its confirmation line point to the compromise procedure (D7, *A compromised signing credential*), which must not start with `tt logout` |
| `tt status [--json]` | forge | any | forge, handle and DID, each signing session's DID and the forge whose `client_id` it uses, session expiries (warning when fewer than two days remain), queued signature records and open rate-limit or back-off windows, records reported by a drain, the last signing failure; a warning when the forge session's DID differs from the default signing DID, since covered refs judge the signing DID |
| `tt token create\|list\|revoke` | forge `/-/api/tokens` | CLI session | access tokens (D5); refused locally with a token credential |
| `tt identity resolve <handle-or-DID>` | PLC, DNS, PDS | — | DID, verified handle and PDS (D9); needs no forge |
| `tt sign …` | PDS, AS | signing session | Git signing and verification, setup and `--setup --undo`, login, flush and revoke (D7) |
| `tt sign recheck <commit> --repo <org>/<repo>` | forge | CLI session or token | re-check the person's own `unverifiable` result after publishing its record late (D8, *Statuses are final*) |
| `tt admin token create\|list\|revoke --did <owner>` | Rivet | `RIVET_*`, `TARTAN_FORGE_ID` | operator tokens (D13): the identity actor keyed by `TARTAN_FORGE_ID` (default `forge`, as for `tartan`), which refuses a DID not in the forge's `owners` |
| `tt admin oauth keygen` | — | — | a fresh ES256 private JWKS for `TARTAN_OAUTH_KEYS_FILE` |

`tt` keeps one default forge and one default signing DID in `$XDG_CONFIG_HOME/tt/config.toml` (also `sign.offline`, D7), which holds no secrets; `--forge` and `TT_FORGE` override the forge. Errors name the command that fixes them ("run `tt login`").

*When `config.toml` is written.* A default that changes without being asked for silently redirects every later command (`tt status`, `tt token`, `tt sign recheck`, and signing when `user.signingKey` is unset), so `tt` writes the two defaults only here:
- `tt login` (either form) makes its forge the default forge only when no default forge is set, or when `--set-default` is given. Otherwise it keeps the default and says "signed in to <url>; the default forge is still <default> (`tt login --forge <url> --set-default` to change it)".
- `tt sign --login` makes its DID the default signing DID only when none is set, or when `--set-default` is given, and never changes the default forge: its `--forge` (or `TT_FORGE`) only chooses whose client metadata the session uses. `tt login`'s first-run signing login (step 6 below) follows the same rule.
- Nothing else writes either default, and `tt sign --setup` never does. `tt logout` and `tt sign revoke` leave a default that names what they removed; the next command that needs it fails, naming `tt login` or `tt sign --login`.

`tt sign --setup` writes as `user.signingKey` the DID given with `--did`, else the default signing DID, else the DID of the only stored signing session. With several sessions and no default it refuses, naming `--did`; with none it runs `tt sign --login` first and uses that DID. When signing gets a key that is not a DID (`user.signingKey` unset), it uses the default signing DID's session, and with no default the only stored signing session; otherwise it fails, naming `tt sign --setup` and `user.signingKey`.

**Forge login hand-off.** The forge's web sign-in is a confidential OAuth client that keeps no tokens (D1), so `tt` cannot reuse it to talk to the forge. Instead the forge hands a CLI session to `tt` with a small loopback flow, the pattern of RFC 8252 with the forge as the authority:
1. `tt` binds `127.0.0.1:0` (or `--port`), creates a 32-byte `state` and a PKCE verifier, and opens `<forge>/#/-/cli-login?port=<p>&state=<s>&challenge=<S256 of verifier>&device=<host name, at most 64 characters>`.
2. The page requires a session (else it sends the person to sign in with `return_to` set to the page) and shows "Allow tt on <device> to act as @alice on forge.example?" with Approve and Cancel.
3. Approve sends `POST /-/auth/cli/approve {port, state, challenge, device}`, cookie-authenticated and Origin-checked (D4). The identity actor's `IssueCliCode` stores the SHA-256 of a fresh 32-byte code with the DID, challenge and device, for 60 seconds. The answer is `{redirect: "http://127.0.0.1:<port>/forge?code=…&state=…"}`, always on `127.0.0.1` with the requested port (an integer 1024–65535); the page navigates there. Cancel navigates there with `error=access_denied`.
4. `tt` checks `state` and sends `POST /-/auth/cli/token {code, code_verifier}` (no credential; rate-limited per client address). `RedeemCliCode` deletes the code whatever happens, requires `S256(code_verifier)` to equal the challenge, and creates a session row of `kind = 'cli'` (D6), returning its `tartan_cli_` secret once.
5. `tt` stores the secret (*Credentials*), makes the forge the default forge only when none is set or `--set-default` is given (*When `config.toml` is written*), and calls `GET /-/api/me` to show who it is signed in as.
6. *First run.* Unless `--no-signing` is given or a signing session for that DID already exists, `tt` runs `tt sign --login` (D7, *tt's OAuth client*) for the DID `GET /-/api/me` returned: the same `--forge`, `--no-open`, `--port` (the port is bound again for the second round trip, so one SSH forward serves both) and `--client`, with the DID as `login_hint` and `sub` required to equal it. That DID becomes the default signing DID only when none is set, or with `--set-default` (*When `config.toml` is written*). If the signing login fails or is cancelled (the consent refused, the granular scope refused, the authorization server unreachable), the forge CLI session is kept, `tt` says "signing is not set up: run `tt sign --login`" with the cause, and exits non-zero, so a script notices. `tt login --with-token` never starts a signing login.

The code is useless without the verifier, which never leaves `tt`, and the redirect can only reach the loopback interface, so a malicious page cannot collect a session. A person who is not a reader can complete the flow; their CLI session then has no rights, exactly like their browser session (D4).

*Remote shells.* The loopback redirect reaches the machine that runs the browser. On a server, `tt login --no-open --port 8765` prints the URL and the person forwards the port (`ssh -L 8765:127.0.0.1:8765`); the same flags apply to `tt sign --login`, since ATProto OAuth offers no device-code grant. For CI, `tt login --with-token` takes an access token instead and needs no browser.

*Rejected:* pasting an access token for interactive use (a token cannot manage tokens, and copy-paste of secrets is worse than a hand-off); an OAuth device authorization grant run by the forge (an extra polling protocol for the case port forwarding already covers); and accepting ATProto service-auth JWTs as forge credentials (the forge would need its own DID and `rpc:` scopes, and `tt` still needs a browser once).

**Credentials.** Three kinds of secret live on the person's machine: the forge credential (`tartan_cli_` or `tartan_pat_`), and per signing DID the OAuth session (refresh and access tokens, DPoP private key, nonces).
- They are stored with `keyring` in the OS credential store (macOS Keychain, Windows Credential Manager, the Secret Service over D-Bus via zbus), service `tt`, account `<forge origin>` or `<DID>`.
- When no store is reachable (a headless Linux machine, a container) or `TT_CREDENTIAL_STORE=file`, they are written to `$XDG_STATE_HOME/tt/credentials/<name>.json` with mode 0600 in a 0700 directory, and `tt` says so at login. It refuses to read a credential file or directory that group or others can access, naming it, as ssh does.
- Never in Git configuration, `config.toml`, the environment of child processes, logs or error messages. `tt status` shows expiries, never secrets.
- The signing queue (D7) holds records, not secrets, but is also 0600, since it reveals signing activity before it is published.

**`tt` in Git's process tree.** When Git runs `tt` to sign or verify, Git captures its standard error and shows it only when signing fails, and only from Git 2.40 (D7, *Context*); a terminal may exist but `tt` does not use it. So `tt` never prompts, never opens a browser, and puts every actionable message ("run `tt sign --login`") on standard error before exiting non-zero. On Git before 2.40 a failed signing shows only "gpg failed to sign the data"; signing.mdx says to run `tt status`, which names the last signing failure, or to upgrade Git. A queued record gives no notice during the commit; `tt status`, `tt sign --flush` and the `pre-push` hook report the queue.

**`tt admin` and the identity actor.** The identity actor lives in `tartan-forge`, next to `Services`. Its action message types (serde structs implementing the crate's own `IdentityAction` trait, with their `NAME` and `Output`), the actor name `identity` and the key helper `identity_key(forge_id)` live in a small crate, `crates/tartan-identity-api` (AGPL-3.0-or-later; depends on serde, and on rivetkit only behind its `rivetkit` feature), which `tartan-forge` implements and `tt` calls. The rivetkit server SDK quadruples `tt`'s clean build (D2, *Checked when the dependencies were added*), so `tt` builds the crate without the feature and needs only `rivetkit-client`. With the feature, which `tartan-forge` and `tartan` enable, the crate's `identity_action!` macro also implements rivetkit's `Action` on each message type with the same name and output. The impls must live in `tartan-identity-api` itself: Rust's orphan rule forbids `tartan-forge` implementing rivetkit's trait on another crate's types. `tt admin` sends each action with `rivetkit-client` 3.0.6's untyped `ActorHandle::action(M::NAME, args)`, which is exactly what rivetkit's typed `call` does (`typed_client.rs`), to the actor `get_or_create("identity", [TARTAN_FORGE_ID])`. The typed `call` wraps a non-array argument as `[value]` and turns null into `[]` (rivetkit 3.0.6 `action.rs` `positional_value`, through the crate-private `encode_action_args`); `tt` cannot call that function, so it applies the same positional wrapping itself, and task 10.3 tests one round trip. `tt` reads no deployment configuration: the owner check is the identity actor's (`AdminCreateToken`, D3), against the `owners` that `tartan_forge::Services` already holds (D13), which is the authoritative list. *Rejected:* a cargo feature of `tt` linking `tartan-forge`, which would bring wasmtime and cranelift into a user-facing CLI; and reading `owners` in `tt` through `tartan-config`, which evaluates CUE through `cuengine`, a Go-to-Rust FFI bridge whose build script compiles the Go CUE runtime into a static library, so every signer's `tt` would need Go with cgo to build on every platform, for a check the forge already makes.

## Risks / Trade-offs

- [The PDS can sign as its accounts] A `verified` signature proves that the DID's repository, under its current `#atproto` key, holds the record. That key is normally held by the PDS, so the PDS operator can create signature records for any account it hosts. → This is the trust ATProto already places in the PDS for everything an account does; signing.mdx states it plainly. People who need more run their own PDS. Rotating the `#atproto` key (a PLC operation) is the remedy for a compromised PDS; proofs are always checked against the DID's current key, so a malicious PDS that kept the old key cannot sign after the rotation.
- [Any repository-write credential signs] Any credential with write access to the account's repository can sign Git objects as the account: app passwords, apps granted `transition:generic` or a `repo:` permission covering `academy.rawkode.tartan.signature`, `tt`'s session, and the PDS operator. The repository commit does not record which client wrote a record, so verification cannot tell them apart. → Stated in D7 *Trust* and in signing.mdx, so nobody reads `tt`'s narrow scope as the limit of their exposure; people who need narrower exposure sign with a dedicated ATProto account that no other app is given; the compromise procedure revokes every writing credential before revoking signatures (D7, *A compromised signing credential*).
- [A stolen `tt` session signs] Whoever copies `tt`'s stored signing session can create records until it ends (at most two weeks for a public client) or the person revokes it at their authorization server. → `tt`'s session can only create `academy.rawkode.tartan.signature` records (D7, *tt's OAuth client*), which limits what this one credential exposes; credentials live in the OS store or 0600 files (D16); the compromise procedure revokes every writing credential first and then runs `tt sign revoke` (D7, *A compromised signing credential*); a revoked signature stops counting toward signing rules on later judgements in every repository of the forge, permanently (D8 *Standing*, D11 *Compliance*). The forge cannot tell a forged record from a real one, so revocation is the person's to do.
- [Revocations can be undone elsewhere] Anyone who still holds a credential that can write to the repository can re-create a deleted record with the same CID. → The forge that recorded the revocation keeps it, and `tt sign revoke` withdraws the signature there on the DID's own word, so a re-creation that lands before the forge re-proves cannot win; other forges and `git verify-commit` cannot see the revocation. signing.mdx states this, and the procedure revokes every writing credential before revoking.
- [Agents without a persistent host] Signing needs a browser-approved session kept on a persistent host (D7, *Agents and automation*). → Ephemeral CI cannot sign in this change; its unsigned pushes to covered refs are violations, which is the fail-closed outcome.
- [Signing needs the network] Every signature is a PDS write. → Writes that cannot be made are queued and published with the next signing, `tt sign --flush` or an opt-in `pre-push` hook (D7, *Offline and rate limits*); the forge keeps an update whose records are missing, or whose signers' PDSes are down, pending for up to seven days with hourly retries, so a record published the next day verifies with nobody acting, and the signer (`tt sign recheck`) or an owner can re-check after that. A commit pushed while its record is unpublished shows who it waits for, and a `main` configuration waits on it for up to seven days; a record deleted on purpose therefore holds a `main` configuration for that long before it is refused, which owners avoid by pushing a commit signed again.
- [Queued records that are never published] A person who signs offline and never comes back online, or loses the machine, leaves signatures that never verify. → They end `unverifiable` with the detail "signature record not published", which is non-compliant on covered refs (fail closed); `tt status` and the repository page make the state visible.
- [PDS rate limits] About 1,666 records an hour and 11,666 a day on the reference PDS. → Ordinary work is far below this; a mass rebase queues the overflow without waiting inside Git, and `tt sign --flush` or the hook drains it once `ratelimit-reset` has passed; the hook never blocks a push. Other PDS implementations may meter differently; a 429 is handled the same way whatever its budget.
- [Signatures reveal activity] Signature records are public: anyone can see when, and how often, a DID signs something, even for private repositories, though not what or where (D7, *What the record reveals*). → Accepted and documented; a separate ATProto account for signing hides the link to the person's main identity.
- [Other tools do not understand Tartan signatures] GitHub, GitLab and other forges see an X.509 block they cannot parse and show the commit as unverified; `git log --show-signature` without `tt` installed fails to verify. → Mirrors keep the signature intact, so a Tartan forge or `tt` can still verify it anywhere; signing.mdx says so. A repository cannot use gitsign or gpgsm alongside `tt`.
- [PDSes that do not convert `$bytes`] `tt` computes the record's CID over the data model the reference PDS stores, `digest` as CBOR bytes (D7, *Signing* step 3). A PDS that stores the JSON as written would keep `digest` as the map `{"$bytes": …}` and answer another CID, so signing fails ("a different CID fails signing"), and a forge would refuse the record as malformed. This is not hypothetical: the PDS serving `did:web:rawkode.dev` (not the reference implementation) stores blob `ref` values as the literal map `{"$link": …}` (captured in `crates/tartan-atproto/testdata`, test `owner_pds_stores_link_objects_unconverted`), which suggests it does not convert `$bytes` either. → Signing against such a PDS fails loudly at the CID check, never with a silently wrong signature; the interoperability check (task 11.3) should include it, and a fix belongs in that PDS.
- [Some PDSes accept only `https` client ids] The PDS behind `did:web:rawkode.dev` refuses the `http://localhost` client. → A developer signs in against it with a hosted native client (`TARTAN_DEV_CLIENT_METADATA_URL`) or a tunnel to a public `https` origin (D1, *Development sign-in clients*).
- [Granular scope support varies by PDS] `tt` needs `repo:academy.rawkode.tartan.signature?action=create`. An authorization server without granular scopes refuses it. → `tt sign --login` explains the refusal and never falls back to `transition:generic`; task 11.3 checks the reference PDS. The web sign-in asks only for `atproto`, so it is unaffected.
- [Public-client sessions last two weeks] People re-authorize `tt` about every two weeks. → `tt status` shows the expiry; signing fails with a clear message naming `tt sign --login`, before any object is created.
- [The forge hosts `tt`'s client metadata] A signing session's `client_id` is the forge's metadata URL, and the reference authorization server loads it on every token request, refreshes included, caching it for about 10 minutes, while access tokens last up to 60 (`tt` follows the server's `expires_in`). So signing needs the forge's metadata URL reachable over public HTTPS whenever a token is refreshed. A forge down for longer than the cache makes refreshes fail with `invalid_client_metadata`; a decommissioned forge or a changed `TARTAN_PUBLIC_URL` ends every signing session made through it. → Such refresh failures are transient: the record is queued, and `tt status` names the forge's metadata as the cause (D7, *Refresh failures are split*); once the forge is back, the next signing or `tt sign --flush` publishes the queue. signing.mdx and deploying.mdx say that moving or retiring a forge means `tt sign --login --forge <new>`. `tt sign --login --client localhost` uses ATProto's loopback client_id for forges that are not public, where authorization servers allow it. Under dev-identity, `tt sign --login` first fetches the metadata URL itself and, if it fails, says so ("the forge's client metadata at http://127.0.0.1:4321/… is unreachable; start the web dev server") rather than reporting the authorization server's refusal.
- [Signers without rights could not withdraw] On a private forge (`readers: "owners"`, the default) a contributor whose commits were pushed, or a reader, has no write rights. → The refresh route is its own `self` route class (D4), open to the record's DID whatever its rights; `withdraw` needs a session, never a `tartan_pat_` token, because it is permanent and forge-wide.
- [Revocations need a trigger] The forge learns that a watched signature record was deleted from Jetstream, from `tt sign revoke`'s refresh or withdrawal call, or from a later proof. With Jetstream disabled and a record deleted by another client, a revoked signature can keep counting for a reused result until something re-proves it. → `tt sign revoke` always calls the refresh route; the configuration docs say what disabling Jetstream costs; the refresh route is available to the signer and owners.
- [Single-maintainer jacquard, breaking churn] → Exact pins. It is used behind `tartan-atproto` interfaces. Our own pre-pass covers the gaps we found. atrium is the documented fallback (D2).
- [Non-owners become read-only or locked out] Today anyone with the admin token can do everything. → Owners can be many DIDs, and tokens serve automation. Membership is the next change.
- [Opening a forge to every ATProto account] Sign-in needs `TARTAN_PUBLIC_URL` on public HTTPS, so with `readers: "signed_in"` anyone with a Bluesky or other ATProto account can read every org, repository, issue and proof bundle. → `readers` defaults to `"owners"`, so an upgrade keeps today's privacy; opening the forge is an explicit line in the deployment configuration, the startup log states the mode in force (D13), and configuration.mdx and deploying.mdx say what `signed_in` exposes.
- [A signature binds to an object, not to a repository or ref] Anyone who can push can fast-forward a covered ref to a commit an allowed signer signed for something else (an experimental branch, another project), and it counts. This holds for all Git signing, and the record names no repository on purpose (D7, *What the record reveals*). → signing.mdx says that `signers` controls who signed, not what they meant to land. The rule itself can change only in a descendant of the commit that set it (D11).
- [Reverting restores the whole configuration] Rewinding `main` to an older signed head applies that head's configuration, so extension versions and settings roll back with it, not just the rule. → Intended: the configuration is whatever `main`'s head says, signed by an allowed signer. The rule alone is protected from rollback (D11, *The rule changes only through descent*); signing.mdx says the rest rolls back.
- [A PDS that loses data revokes signatures] A proved absence of a tracked record revokes it permanently (D8 step 5.4), so a PDS restored from an old backup, or one that loses records, revokes the affected signatures for good. → Consistent with revocation being permanent; the signer signs again. signing.mdx tells operators of self-hosted PDSes.
- [walgit cannot refuse pushes] A violating commit lands. → Violations are recorded and shown, and config application is gated on `main`. Rejection is left to a later push proxy.
- [Git object cache disk use] → Bounded LRU in `TARTAN_STATE_DIR`, disposable.
- [Jetstream is unauthenticated JSON] → Used only as a trigger: revocations are proved with `getRecord`, account status comes from the verified PLC log and `getRepoStatus` (D10, *Account status*), and the consumer ignores DIDs it does not know, records it does not track and every other collection.
- [A PDS can replay an old repository state] D8 step 5.3 bounds `rev` only from above. A malicious PDS could serve a signed CAR from before a record was deleted, so a revoked signature could still prove at a later re-proof. → This is inside the custodial-PDS trust above; rotating the `#atproto` key stops it.
- [Revoking a signature does not un-verify history] Results are snapshots (D8). → signing.mdx says that a revoked signature stays `verified` with an amber "withdrawn" label, while no longer counting toward signing rules on later updates (D11, *Compliance*); see Open Questions.
- [Revoked signatures block rewinds and late merges] Because reused results must still stand, a covered ref cannot be rewound or fast-forwarded to a commit whose signature was revoked; a new signed commit is needed on top. signing.mdx says so.
- [Revocation lag across processes] Up to 30 seconds for sessions and tokens (D4, *Lookups*).
- [The PLC directory chooses forks] → Signatures are verified on the chosen chain, and the full log is kept in the bundle. A malicious or compromised directory could also serve an older prefix of the log, from before a `#atproto` or rotation-key rotation, and it would still verify. That is inherent to did:plc; the bundle keeps the evidence for an audit, not prevention.
- [Forge not reachable from authorization servers] A private forge, or a wrong `TARTAN_PUBLIC_URL`, makes every sign-in fail at PAR. → `client_rejected` says the forge's configuration was refused and to tell the operator; deploying.mdx and identity.mdx state the public-HTTPS requirement; operator tokens still work.
- [Pushers choose what the forge fetches] Every signature names its own DID and PDS, so anyone who can push decides which hosts the forge contacts. → Fetches are fetch-safe (D9) and bounded per attempt and per update (D8, *Bounded attempts*); runs work the head update of `main` first, so slow hosts named on other refs delay the configuration gate by at most one 90-second attempt; an update with more than 64 signers is judged with the rest `not_checked` until an owner re-checks it.
- [Signer DIDs grow the watch list] Every DID whose signature verifies becomes known, so anyone who can push can add DIDs. → At most 50 new signer DIDs per push and 5,000 forge-wide are watched; a signer-only DID leaves `known_as` after 30 days without a verified signature (D3). Signatures beyond the cap still verify.
- [Signed-in DIDs grow the watch list] On a forge with `readers: "signed_in"`, DIDs known only as `signed_in` have no cap: someone with their own PDS or did:web and many addresses can sign in as many DIDs, each adding sweep work and a `wantedDids` entry. On a private forge, or one listing its readers, strangers who sign in are never made known (D13). → The per-address sign-in limits slow this, and above 10,000 known DIDs Jetstream falls back to the consumer-side filter (D10). The `Sweep` also drops from `known_as` a non-owner DID known only as `signed_in` that has had no live session or token for 30 days.
- [Shared sign-in capacity] One client could exhaust a global pending-request cap. → A per-address cap of 20 sits under the global 10,000, and the client address is derived only from trusted proxies (D4).
- [Breaking types change] → It is published as `v0.2.0`, and `v0.1.0` stays served.

## Migration Plan

1. Deploy the new binary with `owners` (operators find their DID from their handle with `tt identity resolve <handle>`, or any ATProto tool), `TARTAN_PUBLIC_URL`, and `TARTAN_OAUTH_KEYS_FILE` (from `tt admin oauth keygen`). Remove `TARTAN_ADMIN_TOKEN`. The forge refuses to start until all of this is done, so a half-migrated forge never starts. Decide who may read: leaving `readers` out keeps the default `"owners"`, so the migrated forge is as private as the admin token kept it, and other people who sign in see only a private-forge page; set `readers` to a list of DIDs to admit named people, or to `"signed_in"` to let any ATProto account read everything. The startup log names the mode in force.
2. Replace scripts' admin token with `tt admin token create --did <owner> --scopes admin …`.
3. List `tartan.rawkode.academy/types@v0.2.0` and the new Issues and Kanban versions in `modules`, then bump repositories' dependencies when they want DID persons. Repositories on `v0.1.0` keep working.
4. Existing actor databases gain new tables only (`CREATE TABLE IF NOT EXISTS`). No existing table changes.
5. A dev or demo forge seeded before this change keeps its bare-name person values as plain text (D14). Deleting the `.dev` or demo state directory gives the DID-based demo of task 12.1.
6. Commits pushed before this change are never checked (only updates after it are queued). People who want signatures install `tt` and run `tt login` and `tt sign --setup`; there are no keys to migrate.
7. **Rollback.** Redeploy the previous binary with `TARTAN_ADMIN_TOKEN`. The new tables are ignored, and person values written as `did:plc` or portless `did:web` DIDs stay valid strings under `v0.1.0`'s regex. `did:web:localhost%3A…` values do not (`%` is outside that regex); they occur only in development data. Signature records stay in people's repositories and harm nothing.

## Review notes

An independent review council examined this plan over several rounds. The findings that shaped the retained machinery, each checked against code or specifications:
- *Browser binding of OAuth requests* and *`TARTAN_PUBLIC_URL` as the browser-facing origin* (D1, D4, D15).
- *Literal scope matching* in `@atproto/oauth-provider` `client.ts` (`declaredScopes.includes(scope)`), which is why every requested token is declared verbatim, for the web client (D1) and for `tt` (D7).
- *Signing-rule bypass through another ref* and *rewinds of a protected ref*: objects are verified once but judged on every update of a covered ref, always including the tip (D8 *Two sets per update*, D11 *Compliance*).
- *Retries that do not survive actor sleep* (rivetkit-core 3.0.6: `WaitUntil` does not block idle sleep; one-shot schedules are claimed and deleted before dispatch; at most 1000 pending schedules): one validated `verify` schedule per Repo actor, a `verifying` mutex, bounded passes and the final `ensure_verify_at` on every exit path (D8 *Durable retries*), and the identity actor's named recurring `Sweep` (D3).
- *Per-purpose scope through jacquard*: jacquard-oauth 0.12.2's `start_auth` ignores `AuthorizeOptions::scopes` and `par()` sends the metadata's scope, so the forge builds its metadata and calls `request::par` directly (D1).
- *Out-of-order checks for one ref*: per-update results with a `seq` guard; the configuration gate concerns only the head update (D8, D11).
- *Account status from Jetstream payloads*: status comes only from the verified PLC log and `getRepoStatus`; Jetstream only triggers (D10).
- *Inactive accounts at sign-in*: status refreshed in the callback before a session exists (D1 step 7).
- *Proof failures*: per the ATProto sync specification, a failed proof refreshes identity and retries once, and is never conclusive (D8 step 5).
- *Absent records*: the reference PDS answers a missing record with a signed non-existence proof; jacquard-repo's `RecordClaim{cid: None}` verifies it (D8 step 5.4).
- *Spoofed text from crafted redirect links*: details only through `POST /-/auth/outcome`, bound to the browser (D1).
- *Results that no longer stand*: a `verified` result counts only while its signer still stands, read from local state without fetching (D8 *Standing*, D11); revocation is permanent on the forge and is checked for fresh results too, so a re-created record cannot undo it in another repository.
- *The give-up path* and *the re-check*: `update_signing`, `update_objects` and the re-check transaction (D8 *Giving up*, *Statuses are final*).
- *Upgrades must stay private*: `readers` defaults to `"owners"` (D13).

Findings on the record-as-signature design, each checked against source:
- *Resending a queued create.* On the reference PDS a plain `create` for an existing key fails the whole `applyWrites` with a 500 (`packages/repo/src/mst/mst.ts` throws a plain `Error`), so a lost answer would make the queue grow for ever. Queued records are reconciled by reading before any resend, and the current signature is never sent with them (D7, *Publishing the queue*).
- *Trust is not identity.* `git merge --verify-signatures` refuses a level below `MARGINAL` (`builtin/merge.c`, `commit.c`), so `tt` reports `TRUST_UNDEFINED` unless the DID is in `tt.trustedSigner` (D7, *Verification by `tt`*).
- *Undoing a revocation.* Revocation is permanent on the forge and checked for fresh results too (D8 *Standing*); the compromise procedure ends the session first (D7).
- *Git before 2.40* needs a newline before `SIG_CREATED` and discards the program's standard error (`gpg-interface.c` v2.30.0 against v2.40.0), so `BEGIN_SIGNING` comes first and Git 2.40 is the minimum for seeing `tt`'s messages.
- *Rebase fast-forwards.* Without `--force-rebase` unchanged picks are fast-forwarded and not re-signed (`builtin/rebase.c`, `sequencer.c`).
- *Queue races between processes*, *signing that sleeps on a rate limit*, *`tt admin` and `TARTAN_FORGE_ID`*, *wasmtime in `tt`* and *how agents sign* (D7, D16).
- *Other credentials can sign.* App passwords, `transition:generic` sessions and any matching `repo:` grant can create `academy.rawkode.tartan.signature` records, and the repository commit does not record the client, so `tt`'s narrow scope is not the limit of exposure; D7 *Trust* says so, the compromise procedure revokes every writing credential first, and `tt sign revoke` withdraws on the DID's word so a re-creation cannot race the forge's re-proof (D7).
- *Git's sign argv does not reveal the format.* `sign_buffer_gpg` sends `--status-fd=2 -bsau <key>` for openpgp and x509 alike, and `--keyid-format=long` appears only on OpenPGP verification (`gpg-interface.c`, `openpgp_verify_args`); verification is routed by armour (`get_format_by_sig`). So `tt` checks `gpg.format` itself before signing (D7).
- *cuengine in `tt`.* `tartan-config` evaluates CUE through `cuengine` 0.40.6, whose build script compiles a Go bridge into a static library, so `tt` reads no deployment configuration and the identity actor checks owners (D3, D16).
- *Pusher-chosen fetches held a check open.* Every `refs/heads/*` and `refs/tags/*` update is queued, and each object names its own signer DID and PDS, so 1000 commits naming 1000 slow `did:web` hosts could hold the `verifying` mutex for hours and keep the update waiting for seven days, delaying the head update of `main` behind it. Attempts now have a deadline, per-run memoised fetches with per-host fail-fast, bounded concurrency and signer caps; runs work the head update first; and only a covered ref's allowed signers earn the seven-day wait (D8, *Bounded passes*, *Bounded attempts*).
- *The forge's metadata at refresh time.* `@atproto/oauth-provider` loads the client metadata on every token request (`authenticateClient`) with a 10-minute cache, so a forge outage surfaces as `invalid_client_metadata` on refresh; it is treated as transient and queued (D7, *Refresh failures are split*).

- *Guess confirmation from an unsalted digest.* With a plain SHA-256 of the payload, an observer of the public record could confirm low-entropy guesses (a private merge of public commits, a revert, a tag of a public commit), because `createdAt` and the TID give the committer time. An earlier draft rejected a salt on the belief that a guesser would hold it; that is wrong, because the salt lives in the signature block and Git signs the object without it. The record's digest is now HMAC-SHA256 keyed with a per-signature random salt carried in the signature (D7, *What the record reveals*).
- *Withdrawal by signers without rights.* Under the read/write/admin classes alone, a signer the forge's `readers` does not admit got 403 from the refresh route, so the withdrawal defence was reachable only by owners. The `self` route class (D4) fixes that, and refuses `withdraw` to `tartan_pat_` tokens because it is permanent and forge-wide.
- *`--verify-only` and `gpg.format`.* In git's `gpg-interface.c`, `check_signature` verifies with `get_format_by_sig`, and `use_format` (set by `gpg.format`) is read only when signing, so `--verify-only` writes only `gpg.x509.program` and leaves a reviewer's SSH or OpenPGP signing untouched (D7).

Findings on bounding and recovery, each checked against this plan:
- *Pre-withdrawals that expire.* A sweep that deleted untracked withdrawn rows after 30 days would un-revoke them, contradicting the never-un-revoked rule: a forger whose re-created record still exists could wait and push. `pre_withdrawn` rows are never deleted; storage is bounded by per-DID and forge-wide caps, with half the forge-wide room closed to strangers, and a per-DID rate limit on the `self` calls that insert or fetch (D4, D7 *Watching records*).
- *Re-running hook setup.* Renaming a `tt` hook onto an existing `pre-push.tt-chained` would destroy the person's hook and make the hook call itself. The marker line, the in-place rewrite and the refusal when both an unmarked hook and a chained one exist prevent it, and a shared or tracked `core.hooksPath` is refused unless `--hooks-path-ok` (D7, *Publishing the queue*).
- *Lifting the rule with an older signed head.* A rewind to a commit an allowed signer signed before the rule existed, an unrelated signed history, or delete-then-recreate of `main` were compliant updates that applied a configuration without `signing` and deleted the rule. The rule now changes only in a descendant of the commit that set it, whatever `old` was (D11, *The rule changes only through descent*).
- *Time in tests.* Hour-, day- and week-long windows were tested by "advancing the clock", which the forge did not have and Rivet's schedules ignore. A `Clock` in `Services`, a harness-only offset and direct `verify`/`Sweep` calls make them testable (D12, *Time in tests*).
- *Late records under `--global`.* `--setup --global` cannot install the hook, so offline records were often published after the forge's hour, leaving only an owner able to recover. Updates waiting on missing records or unreachable signer PDSes now stay pending for seven days, and the signer can re-check after that (D8, *A missing record is not final*, *Statuses are final*).

Findings on local state and signature encoding, each checked against this plan:
- *Demo and tests writing the developer's defaults.* Isolating only `XDG_STATE_HOME` left `$XDG_CONFIG_HOME/tt/config.toml` shared, and no rule said which commands write the default forge and signing DID, so `scripts/demo.sh` could make a plain-HTTP devnet forge and a devnet DID the developer's real defaults (and a later `tt sign --setup --global` would write that DID into `user.signingKey`). The defaults are now written only when unset or with `--set-default`, `tt sign --login` never changes the default forge (D16, *When `config.toml` is written*), and the demo and every test give `tt` its own config, state and cache directories (D12).
- *Re-spelled signature blocks.* Base64url with 2 spare bits and a CID accepted in any multibase let the same salt or CID be written several ways, giving a second object id whose signature still verified and hit `tt`'s cache. The parser now requires each field to equal its canonical re-encoding (D7, *The signature Git stores*).

D7 *Rejected alternatives* explains why a signature is a record written by `tt` rather than a key published as a record and used by another signing tool.

## Open Questions

- Which public Jetstream instance to default to. This is a configuration default only.
- Whether walgit upstream accepts a raw-object endpoint, which would let us drop the gix cache. The interface is already isolated.
- Whether a later change should let a person mark a revoked signature "forged", so results it verified show a warning rather than the "withdrawn" label.
- Whether the outbox's delivery retries (`outbox.rs`, `schedule_retry`) should be deduplicated like `verify`. Each failed flush registers its own schedule against the same 1000-schedule budget, and the identity actor adds another outbox that can fail repeatedly while a subscriber is down. This predates this change.
- Whether to expose operator diagnostics (Jetstream connection state and cursor lag, queued signature checks) through an owner-only status route rather than logs alone. Until then, identity.mdx and deploying.mdx list the log lines to check.
- Who publishes the `academy.rawkode.tartan.signature` Lexicon for resolution (`_lexicon.tartan.rawkode.academy` and the schema record), and from which account. Verification does not depend on it.
- Whether `tt` should later offer a deferred mode that publishes records only for objects being pushed (D7, *Rejected: deferring every write to push time*), if the activity that records reveal turns out to matter more than verifiability before push.
