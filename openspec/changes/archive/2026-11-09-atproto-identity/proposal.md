# Proposal

## Why

Every call to the forge acts as one shared principal, `admin`, authenticated by a static token (`TARTAN_ADMIN_TOKEN`, `dev-admin-token` in development). Nobody can be told apart, person properties hold free-form ids, and a pushed commit carries no evidence of who made it. ATProto gives every person a portable, self-certifying identity (a DID) and a public repository signed by a key bound to that DID, so the forge can know who people are, and people can sign their commits with their DID itself, without the forge running accounts and without anyone managing signing keys.

## What Changes

- People sign in with their ATProto identity through ATProto OAuth (the forge is a confidential backend-for-frontend client asking only for `atproto`). The forge keeps its own session cookie and no OAuth tokens; the UI shows handles, and DIDs are the identifiers everywhere else.
- A new command-line interface, `tt` (crate `crates/tt`), is the forge's only CLI. `tt login` signs in to a forge from a terminal through a browser hand-off and keeps a CLI session in the OS credential store; `tt token` manages access tokens; `tt identity resolve` finds DIDs; `tt admin` holds the operator commands that need no signed-in person (`tt admin token create`, `tt admin oauth keygen`).
- Automation and agents act for a person through scoped, expiring, revocable access tokens (`tartan_pat_…`), created by that person in the web UI or with `tt token create`, or by an operator with `tt admin token create`.
- Forge administrators are the DIDs listed in `owners` in the deployment configuration (package `forge`). **BREAKING**: `TARTAN_ADMIN_TOKEN` and the shared admin principal are removed; the forge refuses to start with no owners. A new `readers` setting says who else may read: by default only owners (`"owners"`), so an upgraded forge stays as private as the admin token kept it and other people who sign in see a private-forge page; `"signed_in"` lets any ATProto account read; a list admits named DIDs. Until org and repository membership exist, readers who are not owners may only read, and the web UI shows them a read-only view (write controls hidden or disabled, a short notice, and an explained message for a refused write).
- A new forge-singleton `identity` actor holds people (DID, verified handle, PDS, account status), browser and CLI sessions, access tokens, pending OAuth requests and the signature records the forge relies on, and records its changes as events on a new event source `identity`.
- **Signatures are records in the signer's own ATProto repository.** Git runs `tt sign` as its X.509 signing program (`gpg.format=x509`, `gpg.x509.program=tt`, set up by `tt sign --setup`). For each commit or tag, `tt` writes a `academy.rawkode.tartan.signature` record holding only an HMAC-SHA256 of the exact bytes Git signs, keyed with a random per-signature salt that only the signature carries (and a timestamp) to the person's repository, over an OAuth session that may only create such records; the PDS signs that repository write with the DID's `#atproto` key. The commit carries the record's `at://` URI, CID and salt, so a guess at a private payload cannot be matched to the public record. There are no SSH, OpenPGP or other user-managed signing keys. Writes that cannot be made (offline, rate-limited) are queued without ever blocking Git, reconciled by reading before any resend, and published later; `tt` also verifies Tartan signatures for `git verify-commit` and `git log --show-signature` (a proved signer is trusted for Git's `--verify-signatures` only when listed in `tt.trustedSigner`), and `tt sign revoke` withdraws one. Agents sign as their own ATProto account from a persistent host; ephemeral CI cannot sign in this change. Signing works with Git 2.19 or later; Git 2.40 or later shows `tt`'s error messages when signing fails.
- After each push the forge proves each signature record back to its DID: a `com.atproto.sync.getRecord` CAR proof (every block re-hashed, the repository commit's low-S signature by the DID's verified `#atproto` key, the MST path), a verified DID document (the did:plc operation log is replayed, not trusted), the record's CID against the signature, and the digest against the object. Each result is stored once, at push time, with its proof bundle in the object store, so a later revocation or deactivation annotates history instead of rewriting it. A missing record (still queued on the signer's machine) and a proof that does not verify are retried for an hour, never recorded as bad signatures. Revocations and identity changes arrive from Jetstream as triggers only and are re-proved; account status is read from the person's verified PLC log and PDS, never from the event. An inactive account cannot sign in, its sessions and tokens are refused, and its new signatures are `signer_inactive`. Sign-in failure pages show hosts and server messages only to the browser that ran the flow, never from the link.
- A repository may require signed commits on chosen refs with a top-level `signing` field in its root package `tartan`. walgit cannot refuse a push, so a violation is recorded as an event, shown in the UI, and stops a configuration on `main` from being applied. Each ref update is judged on its own, so a slow check of an older update neither delays nor overrides a newer one. A result verified on an earlier update counts toward a later update of a covered ref only while its signature has not been revoked and the signer is active, so revoking a signature made with a stolen session also stops that commit from being merged into a protected ref later, in any repository of the forge; a revocation the forge has recorded is permanent there. A check that gives up after an hour still judges its update, so a `main` configuration is refused rather than left waiting; an owner can re-check an `unverifiable` result.
- **BREAKING**: `tartan.rawkode.academy/types` v0.2.0 adds `#DID`; `#Person` values become DIDs. Issues stores authors and person values as DIDs; Kanban labels person lanes with handles. A new `tartan-ui@1` node, `person`, lets extensions show a DID as its handle.
- Local development and tests use `tartan-devnet`, an in-process PLC directory, PDS (including signature-record writes and rate limits) and OAuth server (confidential web clients and public native clients like `tt`). The forge and `tt` accept it only when built with the `dev-identity` feature and started with `TARTAN_DEV_IDENTITY=1`; nothing touches the public network.

## Capabilities

### New Capabilities
- `atproto-identity`: resolving and verifying DIDs and handles, showing people by handle, outbound-fetch safety, and the development identity network.
- `sign-in`: ATProto OAuth sign-in asking only for `atproto`, the client metadata the forge publishes, refusing inactive accounts at sign-in, forge sessions and signing out.
- `access-tokens`: scoped, expiring, revocable tokens that let automation act on behalf of a DID.
- `forge-access`: who the caller is (browser session, CLI session, token or anonymous), forge owners and readers, refusing inactive accounts, what each kind of caller may do, and how the web UI shows private and read-only access.
- `tt-cli`: the `tt` command-line interface: signing in to a forge from a terminal, CLI sessions, credential storage, access-token commands, identity resolution and the operator commands.
- `tt-sign`: signing Git objects with `tt sign`: Git's signing-program interface, the `academy.rawkode.tartan.signature` lexicon and the signature Git stores, the narrowly scoped OAuth session, the offline queue, revocation, and local verification.
- `commit-signatures`: verifying Tartan signatures after a push by proving the signature record back to its DID, the stored result and proof, revocations and their annotation, the events and API that expose it, and enforcing the signing rule.

### Modified Capabilities
- `forge-hierarchy`: the admin-token requirement is removed (replaced by `forge-access`), and the new `identity` actor is one of the singletons keyed by the forge id.
- `forge-cue-registry`: the deployment configuration gains `owners` and `readers`.
- `config-types`: `#DID` is added and `#Person` holds a DID; `#Signing` describes the signing rule.
- `repo-config`: the root package may carry a `signing` rule, which is checked.
- `config-reconciliation`: a configuration whose `main` update breaks the signing rule in force is refused, judged on the update that set `main` to it.
- `git-hosting`: the forge reads the commits a push introduced.
- `event-delivery`: `identity` becomes an event source.
- `extension-runtime`: calls carry the caller's principal (a person's DID, or an agent on behalf of one).
- `issues-extension`: person values and authors are DIDs, shown by handle.
- `kanban-extension`: person lanes and groups are labelled by handle.

## Impact

- **Crates**: `tartan` (gateway auth middleware, auth, CLI hand-off, token and signature-record routes, `tt`'s client metadata, Jetstream task; no subcommands), `tartan-forge` (new `identity` actor, Repo actor signature tables, `GitHost` commit reading), `tartan-config` (`owners`, `signing`), new `tartan-atproto` (resolution, PLC log and record proof verification, the signature record and signature formats, shared by the forge and `tt`), new `tt` (the CLI and Git signing program; it links no forge actors and no wasmtime), new `tartan-identity-api` (the identity actor's action types, shared by `tartan-forge` and `tt admin`) and `tartan-devnet` (development only). All AGPL-3.0-or-later.
- **Dependencies** (crates.io, exact pins): jacquard-oauth, jacquard-identity, jacquard-repo and jacquard-common 0.12.2 (MPL-2.0), atrium-crypto 0.1.3 (MIT), gix 0.90.0, hickory-resolver 0.26.3, tokio-tungstenite 0.30.0, p256 0.13.2 and k256 0.13.4, clap 4.6.7, keyring 4.2.0 and webbrowser 1.2.6 (MIT OR Apache-2.0). Details in design.md.
- **Lexicon**: `academy.rawkode.tartan.signature`, published in `lexicons/`.
- **SDK and extensions (MIT)**: `ui::person`, Issues and Kanban person handling; no ATProto dependency.
- **CUE**: `tartan.rawkode.academy/types` v0.2.0; Issues and Kanban republished against it.
- **Web**: sign-in page, CLI approval page, account menu, access-token, signing-setup and session settings, person input and display, signature badges and the commit signature view, a private-forge page for people the forge does not let read and a read-only view for readers who are not owners; the admin-token setting is removed.
- **Operations**: new `TARTAN_PUBLIC_URL` (the browser-facing origin that serves the web UI and proxies `/-/` to the gateway), `TARTAN_OAUTH_KEYS_FILE`, `TARTAN_STATE_DIR`, `TARTAN_JETSTREAM_URL`, `TARTAN_TRUSTED_PROXIES` (reverse proxies whose `X-Forwarded-For` gives the client address for rate limits); `TARTAN_ADMIN_TOKEN` removed; `TARTAN_PUBLIC_URL` must be reachable over public HTTPS by people's authorization servers for sign-in and for `tt`'s client metadata; `scripts/dev.sh`, `demo.sh` and `e2e.sh` run `tartan-devnet`. The demo assigns its issues to five devnet people by DID, applies a signing rule, and pushes commits signed with `tt` by an allowed and a disallowed person (it needs Git 2.19 or later for `gpg.x509.program`, and 2.40 or later to see `tt`'s error messages).
- **Docs**: new identity, `tt`, signing and token pages; configuration, running-locally, demo, web, events and property-types pages updated.
