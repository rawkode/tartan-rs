A forge is one process: the gateway, its share of the actors, and the forge's CUE registry. What it needs besides the variables in [Running locally](/running-locally/#configuration) is a deployment configuration listing the CUE modules it makes available, and `CUE_REGISTRY` pointing at itself.

## The deployment configuration

`TARTAN_CONFIG` names a CUE file, or a directory such as a mounted config map, holding the package `forge`:

```cue
package forge

sources: "tartan.rawkode.academy": "ghcr.io/rawkode/cue"
modules: [
	"tartan.rawkode.academy/types@v0.1.0",
	"tartan.rawkode.academy/issues@v0.6.0",
	"tartan.rawkode.academy/kanban@v0.3.0",
]
owners: ["did:plc:abcdefghijklmnopqrstuvwx"]
readers: "owners"
```

| Field | Meaning |
| --- | --- |
| `modules` | each module version the forge makes available, fully qualified as `path@vX.Y.Z` |
| `sources` | module path prefixes and the OCI registry each is copied from, written as `CUE_REGISTRY` writes one: `host[:port][/repository-prefix]`, with `+insecure` for plain HTTP |
| `owners` | the DIDs of the forge's administrators: at least one, each listed once |
| `readers` | who else may read: `"owners"` (the default when left out), `"signed_in"` or a list of DIDs |

### Owners and readers

People are identified by their [ATProto](https://atproto.com) DID, never by a handle, because a handle can change hands. `owners` and a `readers` list accept `did:plc` DIDs (`did:plc:` and 24 characters from `a-z` and `2-7`) and hostname-level `did:web` DIDs (`did:web:rawkode.dev`); a `did:web` with a path, such as `did:web:example.com:alice`, is refused. Find a person's DID from their handle with `tt identity resolve <handle>`, or any ATProto tool.

`readers` decides who other than the owners may read:

| Value | Who may read |
| --- | --- |
| `"owners"` (the default) | only the owners: the forge stays private, and other people who sign in are told so |
| `"signed_in"` | anyone who signs in with an ATProto account, which anyone can create: they may read every org, repository and issue |
| a list of DIDs | the owners and the DIDs listed |

Until org and repository membership exist, only owners may make changes; readers who are not owners may only read. Both settings change only when the forge restarts with a new configuration.

A module comes from the source whose prefix matches the most whole elements of its path, and its repository there is the source's prefix followed by the module path. A registry on `localhost` or `127.0.0.1` is reached over plain HTTP unless it says `+secure`.

The file is evaluated as `cue export` evaluates it, without a registry, and may import only CUE's standard library. It is the operator's file, so unlike a repository's configuration it needs no `cue.mod/module.cue`: the forge evaluates a file or directory without one in an empty module of its own, which changes nothing it exports. Values must be concrete. The forge does not start when it does not evaluate, has a field other than `modules`, `sources`, `owners` and `readers`, lists a module without a full version (`@v0` is not one) or lists a module no source serves, lists no owner, lists a DID twice or lists anything that is not a DID (a handle such as `alice.bsky.social` is not one), or sets `readers` to anything else; the log names the problem and the entry. Without `TARTAN_CONFIG` the forge starts with no modules.

## The forge's registry

The gateway serves the read half of the OCI Distribution API at `/v2/`: manifests, blobs and tag lists, `GET` and `HEAD`. It is what `CUE_REGISTRY` points at, both for the forge and for people:

```sh
export CUE_REGISTRY=forge.example.com
cue mod tidy
cue export
```

Every write answers 405: only the forge fills its registry. Modules hold schemas and extension packages, never repository data, so the registry needs no token.

The registry serves only the module versions `modules` lists: a version it holds but the deployment no longer lists answers 404, as an unknown one does. A blob, or a manifest asked for by digest, is served under a module's name only when a listed version of that module is or references it.

The forge's process must start with `CUE_REGISTRY` set to its own registry, such as `127.0.0.1:8080+insecure` or its public host. The CUE evaluator reads it once, at startup, and resolves every repository's imports through it, so a configuration that `cue export` accepts against the forge's registry is the configuration the forge applies. The forge refuses to start without it.

## Syncing modules

At startup the forge copies each listed module from its source into its registry, under `registry/` in its object store, and then serves it.

- A version the registry already holds with the source's digest is not copied again.
- A version the registry holds is never replaced. If its source now serves other contents, the forge keeps its copy and logs the mismatch.
- A source that cannot be reached is logged; the forge starts with the modules it holds and tries again at the next start.

A module whose files include `tartan.json` is an extension. Its package becomes installable once it passes the checks in [Extensions](/extensions/#packages), and the forge's log records `package.published`. A module that fails them stays in the registry for `cue`, but its package is not available, and the log says why. No blob larger than 64 MiB is copied, and no module holding more than 64 MiB of files is registered.

Repositories apply configurations pushed while the sync runs once it has finished, so a module the deployment has just started to list is in the registry before any configuration needs it.

Removing a module from `modules` makes it unavailable at the next start: the registry stops serving it, and a configuration naming its package, by importing the module or by writing its version in a plain entry, is refused. What the store holds stays, and an installation of the package keeps running until its repository's configuration changes.

## Upgrading an extension

Publish the new version of its module to a source, add it to `modules`, and restart the forge. Repositories move to it by changing the version their `cue.mod/module.cue` depends on (`cue mod get tartan.rawkode.academy/issues@v0.7.0`) and pushing to `main`.
