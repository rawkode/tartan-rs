An extension is a WebAssembly component of the `tartan:ext@0.1.0` world (`wit/tartan.wit`), shipped as a CUE module and installed on a repository by its [configuration](/configuration/).

## An extension is a CUE module

One module carries both halves of an extension version: the settings schema a repository's configuration imports, and the package the forge runs. A module version is published to an OCI registry with `cue mod publish`, and a forge makes it available by listing it in its [deployment configuration](/deploying/).

```
cue.mod/module.cue      module: "github.com/rawkode/tartan-ext/issues@v0", source: kind: "self"
issues.cue              package issues, with #Extension
tartan.json             the manifest
component.wasm          the component
migrations/0001_init.sql
```

`source: kind: "self"` makes `cue mod publish` include every file in the directory, the component and migrations included. The module's `#Extension` fixes the extension's id and version and types its settings:

```cue
package issues

import "tartan.dev/types"

#Extension: {
	id:      "rawkode.issues"
	version: "0.6.0"
	settings: properties: [N=string]: types.#Property & {name: N}
}
```

A module can import other extensions' modules, so one extension's settings can refer to another's: Kanban's `#Extension` takes the repository's Issues entry and only accepts columns that are its select properties.

## Building and publishing

In this repository an extension crate keeps its module source in `cue/` (`cue.mod/module.cue` and the `#Extension` package). `scripts/build-extension.sh <crate> <out>` builds the component and assembles the module directory: the `cue/` tree, `component.wasm`, `tartan.json` and the manifest's migrations. A crate without `cue/` gets a minimal module, `github.com/rawkode/tartan-ext/<dir>`, whose `#Extension` fixes the id and version and accepts any settings.

```sh
scripts/build-extension.sh extensions/issues out/issues
cd out/issues && CUE_REGISTRY=registry.example.com cue mod publish v0.6.0
```

The module version is `v` followed by `tartan.json`'s version.

## Packages

```json
{
  "id": "rawkode.issues",
  "name": "Issues",
  "version": "0.6.0",
  "api": "tartan:ext@0.1.0",
  "storage": { "scope": "repo", "migrations": ["migrations/0001_init.sql"] },
  "subscribe": [{ "event": "ref.*" }]
}
```

An extension that works with another names it in `requires`, and the tools it calls in `permissions.calls`:

```json
{
  "id": "rawkode.kanban",
  "requires": ["rawkode.issues"],
  "subscribe": [{ "event": "x.rawkode.issues.issue.*" }],
  "permissions": { "calls": { "rawkode.issues": ["update"] } }
}
```

A configuration that installs a package without the extensions it `requires` is refused, naming them (see [Configuration](/configuration/#when-it-applies)).

When the forge syncs a module that holds `tartan.json`, it checks the package before making it installable:

- the manifest targets `tartan:ext@0.1.0` and its id is valid;
- its version is the module's, without the `v`;
- `storage.scope` is `repo`: every extension installs on repositories, with one database each;
- `requires`, if present, lists other extension ids, each once;
- every migration the manifest lists is in the module, and every `.sql` file in the module is listed;
- `component.wasm` is a component of the extension world;
- `id@version` is not already registered with other contents: an `id@version` never changes.

`GET /-/api/packages` lists the available packages. There is no publish route: packages come only from the modules the forge syncs.

## What an extension can do

| Import | Gives |
| --- | --- |
| `sql` | its installation's own SQLite database |
| `kv` | a key-value store in the same database |
| `host` | its configuration, logging, a clock, randomness and ULIDs |
| `effects` | emitting events and setting timers, applied only if the call succeeds |
| `calls` | another installation's tools, when the manifest permits them |

It exports `init`, `on-event`, `on-timer`, `render`, `on-action`, `call-tool` and the rest of the world; the Rust SDK (`sdk/rust/tartan-ext`) supplies defaults.

## Limits

Each call runs in a fresh instance with its own fuel, 128 MiB of memory and 10 seconds. An extension's SQL cannot touch the host's `_tartan_*` tables or run `ATTACH`, `DETACH`, `PRAGMA` or `VACUUM`; during `render` it may only read. `notify` and why-notes answer `unavailable` for now.

## Events

The manifest's `subscribe` patterns decide what reaches `on-event`. An installation receives the matching events of its repository and of the other extensions installed on that repository, never its own and never another repository's; when it is installed, it receives what those sources recorded before. Each event reaches `on-event` once, in order per source; an event the extension fails on is kept as a dead letter and does not block the next. An extension's emitted events appear as `x.<extension-id>.<type>`.

## Calls between extensions

The `calls` import calls another installation's tool, acting for the same principal, when the manifest's `permissions.calls` names the extension and tool. The target must be installed on the caller's own repository, named by its id; a call into any other repository is refused with `denied`.

## Listing and calling installations

```sh
curl -X POST -H "Authorization: Bearer $TOKEN" \
  localhost:8080/-/api/orgs/acme/repos/api/extensions/rawkode.issues/tools/list -d '{}'
```

`GET /-/api/orgs/<org>/repos/<repo>/extensions` lists a repository's installations. Besides `tools/<tool>` there are `render/<slot>` and `actions/<action>`. Extension errors map to statuses: `denied` 403, `not_found` 404, `invalid` 400, `conflict` 409, `unavailable` 503.
