Extensions are installed and configured only by the CUE package `tartan` committed at a repository's root. There is no install API: a push to `main` that changes it is the only way an extension is installed, upgraded, reconfigured or removed.

```cue
// cue.mod/module.cue
module: "example.com/acme-api"
language: version: "v0.14.1"
deps: {
	"tartan.rawkode.academy/types@v0":                     v: "v0.1.0"
	"tartan.rawkode.academy/issues@v0": v: "v0.6.0"
}

// tartan.cue
package tartan

import (
	"tartan.rawkode.academy/types"
	"tartan.rawkode.academy/issues"
)

extensions: "issues.tartan.rawkode.academy": issues.#Extension & {settings: properties: {
	status:   types.#Select & {options: ["todo", "doing", "done"], default: "todo"}
	priority: types.#Select & {options: ["p1", "p2", "p3"]}
}}
```

Each extension is a CUE module, and its `#Extension` fixes the extension's id and version and types its settings, so a typo or a setting of the wrong kind fails in `cue` before it is pushed. The module's version in `cue.mod/module.cue` is the version installed.

## Exactly what cue evaluates

The forge applies exactly what `cue export` gives for the repository's root package `tartan`, with `CUE_REGISTRY` set to the forge (see [Deploying](/deploying/#the-forges-registry)). It adds no file to the evaluation: no schema and no module. Check a configuration before pushing it with:

```sh
export CUE_REGISTRY=forge.example.com
cue export
```

As with `cue export`, every value must be concrete: a field left as a type (`string`), a constraint (`>5`), a disjunction without a default, or a required field never given (`x!`) makes the configuration invalid, and the problem names its path. The evaluator the forge embeds exports such a value as `null`, so the forge also refuses an explicit `null` anywhere in the package; leave a field out instead.

After evaluation the forge checks the exported value: `extensions` maps each extension id to an entry with a semver `version` (`0.6.0`, without a `v`), `settings` that is a struct (`{}` when left out), and optionally `id` equal to its key. Any other key in an entry, an entry without a version, an invalid id, a conflict, or CUE that does not evaluate makes the configuration invalid. Other top-level fields are yours, for helpers and shared values.

An entry does not have to come from an extension's module; plain CUE works too, in the repository's own module, though nothing then checks its settings before they reach the extension:

```cue
package tartan

extensions: "issues.tartan.rawkode.academy": {version: "0.6.0", settings: properties: {}}
```

## A package, not a file

The configuration is every root `*.cue` file that declares `package tartan`, evaluated together the way `cue export` evaluates a package directory. Name the files as you like and split them as you like; `tartan.cue` is only a convention. Root files of other packages, such as a cuenv `env.cue`, are not part of it, and a repository with no `package tartan` file at its root installs nothing.

With `cue.mod/module.cue`, the repository is a CUE module: its dependencies resolve through the forge's registry, and packages of the module itself can be imported:

```cue
// config/props/props.cue
package props

import "tartan.rawkode.academy/types"

all: status: types.#Select & {options: ["todo", "done"], default: "todo"}

// tartan.cue
package tartan

import (
	"example.com/acme-api/config/props"
	"tartan.rawkode.academy/issues"
)

extensions: "issues.tartan.rawkode.academy": issues.#Extension & {settings: properties: props.all}
```

The repository must be a CUE module: a root `package tartan` without `cue.mod/module.cue` is refused. Run `cue mod init example.com/acme-api` once to add one. The forge supplies no module of its own, because its evaluator only evaluates inside a module.

Files embedded with `@embed` are read from the repository too, so JSON or YAML kept beside the CUE can be part of the configuration:

```cue
@extern(embed)

package tartan

import "tartan.rawkode.academy/issues"

extensions: "issues.tartan.rawkode.academy": issues.#Extension & {
	settings: properties: _ @embed(file="config/properties.json")
}
```

Embedded files must be UTF-8 text (JSON, YAML or plain text); `type=binary` is not supported.

The forge reads only what the package needs at the pushed commit: the root's `*.cue` files, `cue.mod/`, the directories of the module's packages that are imported, and the files they embed. A configuration may read at most 500 files, 64 directories and 4 MiB in all. A dependency the forge's registry does not serve cannot be resolved, so a configuration depending on a module the deployment does not list is refused.

## When it applies

When `refs/heads/main` moves, the forge loads the configuration at the new commit and applies it. Other branches never apply. When pushes arrive quickly, the latest commit wins.

Every entry is checked first: its version's package is in a module the deployment lists, and the extensions its manifest `requires` are installed by the same configuration (Kanban requires Issues, for example). If any check fails, nothing changes and `config.refused` records the problems.

Then each extension is installed, upgraded or reconfigured in turn, the extensions it requires first. If one of them fails (a migration error, say), the extensions already handled stay as they are and the forge tries the same configuration again, with a growing delay, for about two minutes; nothing is recorded until it is applied. A failure that may pass, such as the Git host or the forge's registry not answering, is retried the same way rather than refused. A configuration still not applied after that is tried again when the forge restarts or `main` moves. When the forge starts, repositories apply their configurations once it has copied the modules its deployment lists into its registry.

| Change | What happens |
| --- | --- |
| A new entry | the extension is installed: its migrations run, then `init` |
| A new `version` | the extension is upgraded: the new migrations run, then `init` again |
| New `settings` | the installation's configuration changes; its data is untouched |
| A removed entry | the extension is disabled: calls answer 404, its data is kept |
| The entry again | the same installation comes back, with its data |

Every extension installs on the repository whose configuration names it.

## Events

| Event | Source | When |
| --- | --- | --- |
| `config.applied` | repo | a configuration was applied; `data.changes` lists what changed |
| `config.refused` | repo | a configuration was refused; `data.problems` says why |
| `extension.installed` | repo | an extension was installed or re-enabled |
| `extension.upgraded` | repo | an installation moved to a new version |
| `extension.configured` | repo | an installation's configuration changed |
| `extension.uninstalled` | repo | an installation was disabled |
