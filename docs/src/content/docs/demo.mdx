`scripts/demo.sh` runs the whole forge on one machine with its development identity network, seeds it with an org, a repository, its configuration, a dozen issues and signed commits, and starts the [web interface](/web/). It needs the same tools as [Running locally](/running-locally/#what-you-need), `tt` built with `dev-identity` included.

```sh
WALGIT_BIN=/path/to/walgit REGISTRY_BIN=/path/to/registry CUE_BIN=/path/to/cue scripts/demo.sh
```

When it is ready it prints the addresses and the handle to sign in with. The script chooses the web interface's port before it starts the forge (4321 when it is free), makes `http://127.0.0.1:<web port>` the forge's `TARTAN_PUBLIC_URL`, and starts the web interface on exactly that port, which sign-in needs; the printed addresses say which port it is.

| What | Where |
| --- | --- |
| Web interface | `http://127.0.0.1:4321/#/acme/api` |
| Triage board | `http://127.0.0.1:4321/#/acme/api/boards/triage` |
| Web app board | `http://127.0.0.1:4321/#/acme/api/boards/web` |
| Gateway API | `http://127.0.0.1:8080/-/api`, with an [access token](/tokens/) |
| Identity network | `http://127.0.0.1:9400`: the devnet's PLC directory, PDS, authorization server and Jetstream |
| Git | `http://127.0.0.1:9200/acme/api.git`; pushes send `Authorization: Bearer dev-git-host-token` |

Press Ctrl-C to stop every process it started. The credentials are for development only.

## What runs

| Process | Address | Role |
| --- | --- | --- |
| RustFS | `127.0.0.1:9100` | the object store for Git, the forge's registry and extension packages |
| walgit | `127.0.0.1:9200` | the Git host, posting ref events to the gateway |
| distribution | `127.0.0.1:9300` | the source registry the extension modules are published to |
| Rivet engine | `127.0.0.1:6420` | started by the forge for its actors |
| Tartan gateway | `127.0.0.1:8080` | the API, and the forge's own CUE registry |
| tartan-devnet | `127.0.0.1:9400` | the development identity network: five people, their PDS and its authorization server |
| Web interface | `127.0.0.1:4321`, or the port the script chose | the Astro dev server, forwarding `/-/` and `/v2/` to the gateway |

The script builds Issues and Kanban as modules with `scripts/build-extension.sh` and publishes them, with `tartan.rawkode.academy/types`, to the source registry. The forge's [deployment configuration](/deploying/#the-deployment-configuration) lists the three modules, so at startup the forge copies them into its own registry and registers the extension packages inside them. The forge runs with `CUE_REGISTRY=127.0.0.1:8080+insecure`: every configuration's imports resolve through the forge itself.

## What it seeds

- Org `acme` and repository `acme/api`.
- A configuration pushed with `git push` through walgit, as a person would: `cue.mod/module.cue` depends on the types, Issues and Kanban modules, and `tartan.cue` installs both extensions through their `#Extension`s. Before pushing, the script evaluates it with plain `cue export` against the forge's registry, which is exactly what the forge applies.
- Issues' properties, one of each [property type](/property-types/) the demo uses: `status` (a select with labels), `priority` (select), `assignee` (person), `estimate` (number), `due` (date), `notes` (Markdown long text), `link` (URL), `budget` (money in GBP) and `labels` (multi-select).
- Two [Kanban](/kanban/) boards: **Triage**, with columns by status, lanes by priority and groups by project; and **Web app**, the `web` project's board, with some of the status columns, lanes by label and groups by assignee.
- Twelve issues across the projects `web`, `crates/api` and `crates/cli` (and some with none), with a mix of properties; one is closed. They are assigned to the devnet's five people by DID, and the interface shows them as `@alice.test`, `@bob.test`, `@carol.test`, `@dave.test` and `@erin.test`.
- A [signing rule](/signing/) on `main` and `release/*` with alice as the only signer. The configuration commit that adds it is signed by alice; it is judged by the rule before it (none), so the demo then pushes a second commit signed by alice to `main`, which the rule judges: `main`'s badge reads "Signed by @alice.test" and it complies. `release/1.0` has a commit signed by bob, so the overview shows it as a violation by @bob.test, and the forge's event stream has one `ref.signature.violation` for it.
- alice and bob are signed in to `tt` without a browser: the script runs `tt sign --login` and follows the printed address with `curl`, which the devnet approves at once. Each has their own `tt` configuration, state and file credential store under `.dev/demo/people/<name>`, and the script signs with `git -c`, so the demo never touches your own `tt` setup, keychain or Git configuration.

## Signing in

Open the web interface and use **Sign in as @alice.test**, or type a handle: `alice.test` is the forge's owner, and `bob.test` (or carol, dave or erin) is a signed-in person who is not an owner. The devnet approves every sign-in at once, so there is no password. A non-owner sees what the forge's `readers` setting allows: the demo admits them to read, so bob can browse issues and boards (through the tools Issues and Kanban declare read-only) but sees the read-only notice and no write controls, and a write he forces anyway is refused with that explanation.

For scripts, an owner's token comes from the operator command, which needs no browser:

```sh
tt admin token create --did <alice's DID> --name script --scopes read,write --expires-in-days 1
```

## Signing your own commits

To sign commits as one of the devnet's people, sign `tt` in to the devnet and set Git up to sign with it:

```sh
# In this shell only: the devnet as the identity network.
export TARTAN_DEV_IDENTITY=1 TARTAN_PLC_URL=http://127.0.0.1:9400 TARTAN_DEV_HANDLE_RESOLVER=http://127.0.0.1:9400
tt sign --login --forge http://127.0.0.1:<web port> --handle bob.test
tt sign --setup                # in the cloned repository
```

Use the `tt` the demo built (`target/debug/tt`): a release `tt` refuses to run while `TARTAN_DEV_IDENTITY` is set. The script prints the command that signs as alice with her demo state.

The devnet keeps everything in memory: its signature records do not survive a restart, so a commit signed before a restart can no longer be proved, and a new demo signs its commits again.

The configuration is the repository's own: clone it, change a board or a property, and push again to see the forge apply it. A configuration that does not evaluate (for example a board whose columns are not one of Issues' select properties) is refused, and the repository keeps what it had.

```sh
git clone http://127.0.0.1:9200/acme/api.git && cd api
CUE_REGISTRY=127.0.0.1:8080+insecure cue export
git -c "http.extraHeader=Authorization: Bearer dev-git-host-token" push origin main
```

## State

Everything the demo keeps is in `.dev/demo`: the object store, the source registry, the Rivet engine's data, the logs (`.dev/demo/logs`) and the seeded repository's working copy.

- `scripts/demo.sh` starts from nothing: it deletes `.dev/demo` and seeds again, so every run shows the same demo.
- `scripts/demo.sh --keep` reuses the previous demo's state, with the changes made in it (the web client's key included), and seeds only when an earlier run never finished seeding. The devnet's authorization server starts empty, so the demo signs alice and bob in to `tt` again. The devnet itself starts empty each time, so commits signed in an earlier run show their stored results but could not be proved again. A state directory seeded before people were DIDs keeps its bare-name assignees (such as `admin`), shown as plain text; delete `.dev/demo`, or run without `--keep`, for the DID-based demo.

The demo uses the same ports as `scripts/dev.sh`, so run one at a time; the script stops early if one of the forge's ports is taken.

## With your own identity

```sh
scripts/demo.sh --owner did:web:example.com
scripts/demo.sh --owner did:web:example.com --client-metadata-url https://example.com/tartan-dev.json
```

With `--owner`, the demo runs against the real ATProto network instead of the devnet: that DID is the forge's only owner, `readers` keeps its default (only owners read), and you sign in to `http://127.0.0.1:<web port>` as yourself. It seeds the same repository and issues, assigned to you, but no signing rule, and keeps its state in `.dev/demo-owner`. Nothing in it is offline: the forge resolves your DID and handle, reaches your PDS and its authorization server, and follows the public Jetstream.

Your authorization server cannot reach a forge on `127.0.0.1`, so the forge cannot use its normal client. It uses a [development sign-in client](/identity/) instead:

- By default, ATProto's `http://localhost` client. Servers that follow the reference implementation, such as bsky.social, accept it.
- Some self-hosted servers accept only `https` client ids and refuse it; sign-in then shows that your server refused this forge's configuration, with the server's message ("client_id must be a safe https metadata URL"). For those, run the demo once with `--client-metadata-url <https URL>`, publish exactly what `http://127.0.0.1:<web port>/-/auth/client-metadata.json` then serves at that URL (keep the same web port), and sign in again.

Both are public clients, acceptable only on your own machine.

Signing commits as yourself needs a `tt` signing session, which uses the same kind of development client: `tt sign --login --client localhost --handle <your handle>` where your server accepts that client, or, where it does not, `tt sign --login --client-metadata-url <https URL> --handle <your handle>` with a `tt` built with `--features dev-identity`. Run that once to have `tt` print the JSON to publish at that URL (it differs from the web client's), publish it, and run it again. Your authorization server must also grant the granular scope `repo:academy.rawkode.tartan.signature?action=create`; one that offers only `atproto` and `transition:generic` refuses it, and `tt` never asks for broader access. See [Signing](/signing/#setting-up).
