Issues installs on a repository, from the repository's configuration. Each repository's issues are numbered from 1, open or closed, and may be filed against a project (a root path such as `crates/lsp`). Issues has the typed properties the configuration gives it.

## Installing

Issues is the CUE module `tartan.rawkode.academy/issues`. Its `#Extension` fixes the extension's id and version and types its settings with [`tartan.rawkode.academy/types`](/property-types/), so the module version a repository depends on is the Issues version it installs:

```cue
// cue.mod/module.cue
module: "example.com/acme-api"
language: version: "v0.14.1"
deps: {
	"tartan.rawkode.academy/types@v0":                     v: "v0.2.0"
	"tartan.rawkode.academy/issues@v0": v: "v0.7.0"
}
```

```cue
// tartan.cue
package tartan

import (
	"tartan.rawkode.academy/types"
	"tartan.rawkode.academy/issues"
)

extensions: "issues.tartan.rawkode.academy": issues.#Extension & {settings: properties: {
	status:   types.#Select & {options: ["todo", "doing", "done"], labels: todo: "To do", default: "todo"}
	priority: types.#Select & {options: ["p1", "p2", "p3"]}
	tags:     types.#MultiSelect & {options: ["bug", "docs"]}
	owner:    types.#Person & {label: "Owner"}
	notes:    types.#LongText & {label: "Notes"}
	spec:     types.#URL
	budget:   types.#Money & {currency: "GBP"}
	due:      types.#Date
}}
```

Run `cue export` with `CUE_REGISTRY` set to the forge to see exactly what the forge applies. A property name is a lowercase identifier of up to 32 characters (`^[a-z][a-z0-9_]{0,31}$`). Each property records its own name (`properties.status.name` is `"status"`), so another extension's configuration, such as a [Kanban](/kanban/) board, can refer to the property itself and CUE checks the reference.

## Values

| Kind | Values | Shown as |
| --- | --- | --- |
| `shorttext` | one line, at most `maxLength` characters (200) | text |
| `longtext` | Markdown, at most `maxLength` characters (20000) | rendered Markdown |
| `number` | a number within `min` and `max` | number |
| `date` | a real day, `YYYY-MM-DD` | date |
| `boolean` | `true` or `false` | Yes or No |
| `select` | one of `options` | the option's label, or the option |
| `multiselect` | distinct options | their labels |
| `person` | a person's DID, such as `did:plc:ewvi7nxzyoun6zhxrhs64oiz` or `did:web:rawkode.dev` | their handle, `@alice.bsky.social` |
| `url` | an `http` or `https` URL | a link, for `https` |
| `money` | an integer of minor units in the property's currency | `GBP 12.50` |

A value is checked when it is written: one that does not fit its property is refused with `invalid`, and so is a property the configuration does not define. `null`, an empty string and an empty list all mean no value: on `update` they clear the property, and on `create` they leave it unset, so an unset property is always absent from what Issues stores. A default fills in when an issue is read. Changing the configuration never rewrites stored values: a removed property or option stays on the issues that have it.

## People

A `person` value is a DID, never a handle: handles change, DIDs do not. The web interface lets you type a handle (`alice.bsky.social` or `@alice.bsky.social`) or a DID, asks the forge to resolve a handle to its DID (`POST /-/api/people/resolve`, checked both ways), and stores the DID; it shows the person as `@handle`, or a shortened DID until the forge knows the handle. Over the API or MCP, send the DID. Anything else, such as `admin`, is refused with `invalid`. Person values stored by Issues before 0.7.0 (bare ids such as `admin`) are kept and shown as plain text, and the next edit of that property must set a DID.

Every issue's `author` is whoever called `create`: a signed-in person is `{"kind": "user", "id": <their DID>}`, and an access token is an agent acting for its person, `{"kind": "agent", "id": "token:<id>", "onBehalfOf": <their DID>}`, shown as `@handle (agent)`. Issues' own views show people with `person` nodes (`ui::person`), which the interface resolves to handles.

## Tools

| Tool | Does |
| --- | --- |
| `list` | issues newest first, without bodies (`state`, `limit`, `project`, `before`), with the counts and the properties |
| `get` | one issue with its body |
| `properties` | the configured properties: `name`, `kind`, and `label`, `options`, `labels`, `default`, `min`, `max`, `maxLength` and `currency` where set |
| `create` | a new issue (`title`, `body`, `project`, `properties`) |
| `update` | title, body, `properties` or state in one write (`expectedVersion` guards against concurrent edits) |
| `close`, `reopen` | change the state |

An issue is `{number, title, project, state, author, createdAt, updatedAt, closedAt, properties, version}`, with `body` from `get`, `create` and the issue view. `properties` holds the stored values with the configured defaults filled in.

## Views

The repository's Issues tab (slot `issues`) shows the counts, the newest issues with up to six properties as columns, and a form that opens an issue. The `issue` slot (`props: {number}`) shows one issue: its body and each long text property rendered as Markdown, and its other properties.

## Events

Every write emits `x.issues.tartan.rawkode.academy.issue.created` or `.updated` with the issue's number, title, project, state, stored `properties`, version and update time, but not its body. Other extensions keep a copy by keeping the highest version.
